## Abstract

An exchange holds one HTTP/3 response stream open per client and writes a short
frame to it whenever something that client is entitled to see changes: an entry
in a channel it is in, a signal addressed to it, a read mark that moved, a
membership that changed, a profile it can see, an admission request it can act
on. A frame names what moved and never carries it. The client answers by making
the request it would have made anyway. This replaces polling as the way a client
learns that anything happened, and leaves polling as the repair for anything the
stream failed to deliver.

## Motivation

Nothing in this stack has ever told a client something. Every service answers
questions, and a client that wants to know whether the answer has changed asks
again. SIP-16 softened that with a held `Fetch` — one request may wait up to 25
seconds for one channel — but a client with several conversations open has
several questions, and one held request answers one of them.

The reference chat client polled. Each open conversation cost two round trips
every 700 ms, because a fetch does not carry membership and the client needs
both; three conversations was roughly nine requests a second, indefinitely, to
be told nothing had happened. Read marks were a third request every three
seconds. "Has anybody started talking to me" was a fourth every five. And a
profile — the one fact in the set that a person changes deliberately and then
watches for — was cached for an hour, because SIP-21 caps updates at 32 an hour
and asking oftener could not learn much. The result was a client that generated
constant traffic while idle and was still, by construction, up to an hour stale
about somebody's name.

Both halves of that are the same defect. Traffic is proportional to how long a
client has been running rather than to what has happened, and staleness is
whatever cadence somebody picked. Neither improves by picking better numbers.

The exchange already knows all of it. It assigns the sequence numbers, enforces
the membership, stores the profiles and routes the signals. It has simply never
had a way to say so.

### Why not the pieces that exist

**SIP-16's held fetch** is per channel, and a held request occupies the client's
request path for as long as it is held. Holding one per conversation is possible
over HTTP/3 — streams multiplex — but it scales the number of parked requests
with the number of conversations, and it still cannot carry a profile change, a
new conversation, or an admission request, none of which belong to a channel.

**SIP-12's datagrams** are already carried, already fanned out by identity at
the exchange, and would need no new route at all. They are rejected here for
what they are good at: a datagram is unreliable and MTU-bounded, which is the
right trade for media, where a late packet is worth less than a lost one. Every
event would become a hint that might not arrive, so the polling floor would have
to stay tight enough to cover the loss — which is the thing this SIP is for.
Datagrams keep media.

**A server-opened unidirectional stream** would be the shape a push protocol
usually takes. HTTP/3 reserves unidirectional stream types for its own use and
leaves unknown ones to the peer's discretion, so this would depend on how each
end's HTTP/3 layer treats a type it does not recognise. A response body is
specified, universally implemented, and already flows in the right direction.

## Specification

### The route

A client opens the stream with `POST /events`. The request body is:

```
offset  size  field
0       1     0x01   type marker
1       1     version
```

The version is 1. An exchange that does not speak the requested version MUST
answer `400` and MUST NOT open a stream.

The caller MUST have advertised an Ed25519 identity on the connection (SIP-3).
An exchange MUST answer `403` otherwise: every event is scoped to an account,
and there is no account on an anonymous connection.

An exchange MAY limit how many streams one identity holds at once and MUST
answer `429` past that limit. The limit MUST be at least 2, because SIP-22 gives
a person several devices and each runs a client.

On acceptance the exchange answers `200` with content type
`application/vnd.sqex.events`, **no `content-length`**, and does not end the
response. The client MUST NOT close its own send side before it has sent the
body; the exchange reads the body to its end before answering.

### Frames

The response body is a sequence of frames:

```
offset  size  field
0       4     length of everything after this field, big-endian
4       1     kind
5       ...   payload
```

An exchange MUST NOT write a frame longer than 1024 bytes. A client MUST refuse
a length above that and MUST treat it as fatal to the stream: once a length is
wrong the client no longer knows where the next frame begins.

HTTP/3 body chunk boundaries are not frame boundaries. An implementation MUST
reassemble frames from the byte stream and MUST NOT assume one read yields one
frame; two frames written in quick succession may arrive in one chunk, and one
frame may arrive across two.

| kind | payload | meaning |
|---|---|---|
| `0x01` | `[32]` channel, `[8]` last_seq | entries exist in this channel |
| `0x02` | `[32]` channel | a signal is waiting for the caller here |
| `0x03` | `[32]` channel | a read mark moved here |
| `0x04` | `[32]` channel, `[32]` account, `[1]` what | a membership changed |
| `0x05` | `[32]` account | this account published a profile |
| `0x06` | — | an admission request is waiting |
| `0x07` | — | heartbeat |
| `0x08` | — | resync |
| `0x09` | `[32]` channel, `[8]` seq | a call is ringing here (SIP-36) |

`what` is `0x01` joined, `0x02` left, `0x03` removed, `0x04` role changed.

`last_seq` MAY be `0`, meaning "something changed and the exchange is not saying
what" — a redaction changes an entry that is already numbered. A client MAY skip
a fetch when `last_seq` is non-zero and not above its cursor. A client MUST
fetch when it is zero.

**A client MUST ignore a kind it does not recognise, and MUST NOT treat it as an
error.** This is SIP-15's rule, inherited by SIP-19, and it is the whole reason a
later kind of event can be added without a flag day. A client MUST, however,
treat a kind it *does* recognise at an unexpected length as malformed: that is a
broken peer rather than a newer one, and accepting it would make every
truncation look like a feature it has not learned yet.

### What an event carries

**A frame names what changed and never carries it.** An exchange MUST NOT put an
entry body, a profile, a signal payload or a member list in a frame.

This is the central constraint and everything else follows from it. The fetch
routes remain the sole authority on membership, retention, visibility and the
reset sequence space of SIP-16; an event cannot contradict them because it
asserts nothing. It also makes loss and duplication survivable by construction:
acting on a hint twice is a wasted request, and missing one is repaired by the
next hint or by the client's own floor. An implementation that added payloads
would have to reproduce every authorization rule in a second place and keep the
two in agreement.

### Who is told

An exchange MUST NOT send an event to an account that could not obtain the same
fact by asking.

- `0x01`–`0x04`: the accounts **presently** in that channel. A `0x04` naming a
  removal MUST also go to the account removed; it is the one party that cannot
  find out by asking again.
- `0x02` and `0x03` MUST NOT go to the account that caused them. A client does
  not need telling that its own keyboard is in use.
- `0x05`: accounts sharing at least one channel with the publisher, which is the
  reach SIP-21 gives a profile. An exchange MUST NOT send it to an account that
  has blocked, or is blocked by, the publisher.
- `0x06`: accounts that can act on an admission request.

### Ordering, and the one rule that cannot be recovered from

**The subscription is registered before the response head is sent, and a client
reconciles only after receiving that head.** An exchange MUST register the
subscription before answering. A client MUST NOT begin its reconciling fetches
until the head has arrived.

Together these mean an event occurring during a client's reconcile is queued
behind the subscription rather than falling between the two. The worst case is a
redundant fetch. Reversed — reconcile first, subscribe second — a client loses
every change that landed in the gap, permanently, and nothing at either end
reports it. There is no repair for this other than the client's slow floor, and
no way to detect it having happened.

This is the same discipline SIP-16's held fetch already states for itself: the
notifier is taken before the first read.

### Falling behind

An exchange MUST bound what it queues for one subscriber. On overflow it MUST
discard the queued events and deliver a single `0x08` resync in their place,
before any further event.

A resync replaces the backlog and does not follow it. The queued events describe
a world with holes in it, and delivering them first would have the client act on
hints it can no longer make sense of.

A client receiving `0x08` MUST re-read everything it holds, as if it had just
subscribed.

### Silence

An exchange MUST write `0x07` when it has had nothing to say for an interval it
chooses, and that interval MUST be shorter than the connection's idle timeout.

A QUIC connection outlives an application that has stopped speaking, so without
this a working stream and a dead exchange are indistinguishable from the client.
A client SHOULD treat a stream that has been silent for several intervals as
dead, and resubscribe.

### The floor

**A client MUST retain a periodic reconcile and MUST NOT rely on the stream
alone.** Events are dropped on overflow by design, a stream can die between
heartbeats, and an exchange may not implement this SIP at all. A client that
polled only when told to would be silently frozen against any of the three.

The floor exists to repair, not to poll: it should be slow enough that an idle
client is quiet.

## Rationale

**Why hints and not payloads.** Discussed above under *What an event carries*: it
keeps one authority for every rule, and it makes loss and duplication cheap
rather than corrupting. The cost is one round trip per change, which makes
traffic proportional to activity — the property that was wanted.

**Why one stream and not one per channel.** Three of the eight kinds do not
belong to a channel at all. A per-channel subscription would also be a list the
exchange has to keep in step with a membership it already holds; deriving the
reach from membership at publish time cannot drift.

**Why the subscription names nothing.** The identity is on the connection
(SIP-3) and everything the caller may hear follows from it. A subscription that
named channels would let a client ask about a channel it is not in, which is a
question the exchange would then have to refuse rather than one that cannot be
asked.

**Why `429` rather than closing the oldest stream.** A client that has leaked
subscriptions and one that has four legitimate devices look identical from here.
Refusing the new one fails safe for the second; closing the oldest fails badly.

**Why a length prefix when HTTP/3 already frames.** Because it frames
*transport* chunks. An implementation that treated a chunk as a message would
work until two events were produced close enough together to be coalesced, and
would then silently drop one — a failure that appears under load and not under
test.

## Compatibility

Additive. The route is new; every existing route is unchanged. A client that
does not know about this SIP behaves exactly as before, and an exchange that
does not implement it answers `404`, which a client MUST treat as "keep
polling" rather than as an error.

Both ends need not move together, in either direction. A new client against an
old exchange degrades to its floor. An old client against a new exchange never
opens a stream and is served exactly as it was.

## Security considerations

**What the stream discloses.** A subscriber learns the *timing* of things it is
already entitled to know the content of. Every one of them is obtainable by
polling, so nothing new is revealed about *what*; the stream sharpens *when*. The
clearest case is `0x05`: a peer learns the moment somebody changed their profile
rather than learning it within the hour. An exchange that regards this as
significant may delay or coalesce events, since a hint carries no content and
delaying one costs only latency.

**What it must not disclose.** The reach rules above are load-bearing. A fan-out
that loses its channel filter turns this route into a way to learn that a
conversation exists between two accounts, which no fetch route will tell you.
An implementation should test the negative directly — that an account not in a
channel receives nothing about it — and should test it with a subscriber that
*would* be reachable by a broken filter, or the test proves nothing.

**Denial of service.** A held stream is state the exchange keeps on a client's
behalf. The queue bound and the per-identity limit are what keep that state
constant per subscriber rather than proportional to how slow the subscriber is.
Neither prevents an attacker from opening streams under many identities, which
is the same exposure every other route has and is bounded by the same
whitelisting (SIP-8).

**What this does not protect against.** Nothing here is authenticated beyond the
connection. An exchange can withhold events, invent them, or lie about the order
— exactly as it can withhold, invent or reorder answers to a fetch. The trust
boundary is unchanged: an exchange controls availability and ordering and cannot
read a sealed entry (SIP-17). A false `0x01` costs a client a wasted fetch; a
withheld one costs it latency up to its floor. This is why the floor is
mandatory.
