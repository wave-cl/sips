## Abstract

A SIP — sQUIC Improvement Proposal — is a design document describing a change
to sQUIC or to a service built on it. This SIP describes what a SIP is, how one
is proposed, and how it moves between statuses.

## Motivation

sQUIC has two independent implementations, in Rust and in Go, and a growing set
of services built on it: sqns for naming, sqssh for remote shells, sqex for
exchange. Changes on the wire have to be agreed before they are written, not
discovered afterwards.

This is not hypothetical. In August 2026 the MAC2 cookie mechanism was found to
have never worked in either implementation: the client hashed one field twice,
used a ciphertext where a plaintext was required, and the reply was encrypted
under a key the client could not possibly hold. Each implementation was
internally consistent and neither matched the other, because the design existed
only as code. A specification either side could have been checked against would
have caught it.

## Specification

### Format

A SIP is a Markdown file, `sip-NNNN.md`, opening with a fenced preamble:

```
SIP: 4
Title: Liveness beacon
Author: A. Name <a@example.com>
Status: Draft
Type: Standards Track
Layer: Exchange
Created: 2026-08-24
Requires: 2
```

`Requires` names SIPs that must be Active first. `Replaces` and `Replaced-By`
record supersession. Sections follow `template.md`; a Standards Track SIP must
have Specification, Rationale, Compatibility and Security considerations.

### Types

- **Standards Track** — anything two implementations must agree on: wire
  formats, cryptographic constructions, public API shape.
- **Informational** — guidance that binds nobody.
- **Process** — how the project works. This SIP.

### Layers

Which stratum a proposal touches, and therefore which repository changes:

| Layer | Repository |
|---|---|
| Transport | squic-rust, squic-go |
| Naming | sqns |
| Exchange | sqex |
| Application | sqssh |
| Process | sips |

### Statuses

```
Draft ──> Proposed ──> Active
  │           │
  └───────────┴──> Withdrawn | Rejected

Active ──> Replaced
```

- **Draft** — written down, open to change in any part.
- **Proposed** — the author considers it complete and is seeking agreement.
  Wire formats should be considered unstable until Active.
- **Active** — agreed and implemented. See below.
- **Rejected** — considered and declined. Kept, with the reasoning, so it is
  not proposed again unaware.
- **Withdrawn** — abandoned by its author.
- **Replaced** — superseded, with `Replaced-By` naming the successor.

### Reaching Active

A Standards Track SIP requires a reference implementation before it can become
Active. **If it touches the wire, it requires an implementation in both Rust
and Go.**

That bar is deliberately high, and it is set by experience. The two
implementations have drifted more than once: the cookie mechanism above, and a
separate case where one honoured a configuration value the other silently
coerced. A wire format with one implementation is a specification nobody has
checked.

Proposals that touch only one layer with only one implementation — a change
within sqns, say — need only that one.

### Numbering

Numbers are assigned by an editor when a proposal is first merged as Draft, and
are never reused. A number is not a queue position: SIP-8 may be Active while
SIP-5 is still Draft.

### What belongs in a SIP

A SIP is for decisions that outlive their implementation, or that another
implementer must reproduce. Bug reports, refactors and anything with a single
obvious answer belong in an issue.

The test: **would a second implementer, with no access to our code, need this
written down?** If yes, it is a SIP.

## Rationale

The structure follows Bitcoin's BIPs and BitTorrent's BEPs, which have both
survived long enough to be worth copying. The `Layer` field is an addition
suited to this ecosystem, where the strata are unusually distinct and a reader
wants to know immediately which codebase is affected.

Requiring implementations in both languages before Active is the one place this
process is stricter than its models, for the reason given above.

## Compatibility

None. This SIP describes the process and constrains no software.

## Security considerations

Only indirectly: the process exists so that cryptographic constructions are
reviewed as specifications rather than discovered as code. The MAC2 failure was
a security mechanism that had never once worked in production, and it went
unnoticed for months precisely because there was nothing to check the code
against.
