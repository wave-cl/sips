## Abstract

A sQUIC server may be configured with a set of client X25519 public keys, and
will then silently drop any Initial whose key is not in the set. The check runs
before the Diffie-Hellman, so a caller outside the set costs the server a hash
lookup and gets no response of any kind. This SIP specifies what the set
contains, where in SIP-6's validation order it sits, what the three
configuration states mean, and — because the code says so in a comment and no
document said so anywhere — how much of the transport's security has been
resting on it.

## Motivation

MAC1 answers "does this caller know my public key". For a great many deployments
that is not the question. sqsshd wants to talk to the handful of keys in
`authorized_keys` and to nobody else; a service behind a private exchange wants
its own operators. Those servers know their callers in advance, and the
publication of a public key — which is what a public key is for — should not
entitle the world to make them do elliptic-curve arithmetic.

The whitelist is also load-bearing in a way that was never written down. SIP-6
requires a server to reject small-order client keys, because a small-order key
makes the Diffie-Hellman non-contributory and lets a caller who has never seen
the server's public key forge a MAC1. That check was added late. Before it, the
only thing standing between a stranger and a forged MAC1 was whether the
deployment had a whitelist — a fact recorded in a source comment and nowhere
else. A control that has been carrying that much weight deserves a specification.

## Specification

### What the set contains

The whitelist holds **X25519 public keys**, 32 bytes each — the same key that
appears in the Initial envelope and the same key MAC1 proves possession of.

It does not hold Ed25519 identities. At the point the check runs, the Ed25519
field has not been validated: SIP-3's derivation check happens after MAC1, which
happens after this. An application that thinks in Ed25519 identities MUST
convert them forward with the Ed25519-to-X25519 map and whitelist the results,
exactly as SIP-2's R2 describes for naming a caller. sqsshd does this: it builds
its transport whitelist by converting `authorized_keys` forward.

The forward direction is the only one available. The reverse map is two-to-one,
so a server cannot recover the Ed25519 identity from a whitelisted X25519 key,
and MUST NOT try.

### Where the check runs

The whitelist is SIP-6 step 4: after the length, timestamp and MAC2 checks, and
**before** the Diffie-Hellman.

This position is normative. Placing it after MAC1 would admit and reject exactly
the same callers while making an unauthorised caller cost a curve operation
instead of a hash lookup, which is most of the reason to have a whitelist at
all.

### What the check proves, and what it does not

Passing the whitelist proves only that the key in the envelope is in the set.
It is **not** proof of possession: the key is plaintext on the wire, so anyone
who has observed an authorised client's Initial can copy the key and pass this
check. MAC1 is what proves possession, and it still runs afterwards. An
implementation MUST NOT treat the whitelist as authentication, and MUST NOT
short-circuit MAC1 for a whitelisted key.

### Configuration states

There are three, and the difference between the last two matters:

| State | Behaviour |
|---|---|
| Disabled | Every caller that passes MAC1 is admitted |
| Enabled, populated | Only keys in the set are admitted |
| Enabled, empty | No caller is admitted |

An enabled but empty whitelist MUST block everyone. It is not a synonym for
disabled, and treating it as one would turn a deployment that had just removed
its last authorised key into an open server.

A server MAY allow the set to be changed at runtime: adding a key, removing a
key, enabling the whitelist with an initial set, and disabling it. Adding a key
while the whitelist is disabled MUST enable it, since the alternative — silently
recording a key that has no effect — is a configuration change that appears to
work and does not.

Changes MUST take effect for subsequent Initials, and MUST NOT affect
connections already established. A whitelist is admission control, not
revocation; a server that needs to end an existing connection must close it.

### Failure is silence

A caller whose key is not in the set MUST receive nothing: no error, no close,
no cookie reply. It is indistinguishable from a closed port, which is the same
guarantee SIP-6 makes for a failed MAC1 and for the same reason.

## Rationale

**Why in the transport rather than the application.** The application cannot
refuse cheaply. By the time a connection is accepted the server has done the
Diffie-Hellman, run a TLS handshake and allocated connection state — all the
work the whitelist exists to avoid — and an application-layer rejection is also
a response, which forfeits silence.

**Why X25519 and not the Ed25519 identity.** The Ed25519 field is optional
(SIP-3), unvalidated at this point in the order, and absent entirely for
ephemeral clients. The X25519 key is always present and is the key the rest of
the step operates on. Whitelisting on a field a caller may omit would mean
either rejecting every anonymous caller or having no rule for them.

**Why not a signed authorisation token instead.** A token would let a server
admit callers it had not enumerated, which is a genuinely useful thing and is
what SIP-24's admission requests are for at the exchange layer. It does not
belong here: verifying a signature is more expensive than the DH it would be
saving, so a token cannot occupy step 4.

**Why runtime mutation at all.** Because the alternative is restarting a server
to add a user, and a restart drops every existing connection.

## Compatibility

No wire change: the whitelist consumes a field already present in every Initial,
and a client cannot tell whether a server has one. Per SIP-1, a proposal that
does not touch the wire does not require both implementations to move together —
though both have had this since before either had a SIP.

The API differs in shape between the two implementations and not in behaviour.
squic-rust holds an `Option<HashSet<[u8; 32]>>` behind a lock and exposes
`allow_key`, `remove_key`, `has_key`, `allowed_keys`, `enable_whitelist` and
`disable_whitelist` on the listener; squic-go holds a
`map[[32]byte]bool` and exposes `AllowKey`, `RemoveKey`, `HasKey`,
`AllowedKeys`, `EnableWhitelist` and `DisableWhitelist`. Both express the same
three states.

## Security considerations

**The whitelist is the only defence a deployment has against a stranger reaching
the Diffie-Hellman.** Everything before step 4 is a syntactic check on a packet
anyone can produce. With no whitelist, any caller holding the server's public
key can make the server do unbounded curve operations, bounded only by SIP-7's
cookie defence once the rate crosses the threshold.

**It has been carrying more than that.** Until the non-contributory check of
SIP-6 step 5 existed, a small-order client key produced an all-zero shared
secret that a caller could predict without ever having seen the server's public
key — a forged MAC1 from a total stranger. A whitelisted deployment was
protected, because the attacker's key was not in the set. An unwhitelisted one
was not protected at all. Both checks are now in place; this is recorded because
a reader deciding whether they need a whitelist should know what the history
was, and because the same shape of defect will recur.

**Membership is not confidential, but it is not disclosed either.** A server
reveals nothing about its set: an authorised and an unauthorised caller both
receive silence, and the two are distinguishable only by whether the handshake
subsequently completes, which requires the caller to hold the corresponding
private key. An attacker cannot probe for whether a given key is authorised
without holding it.

**The key is on the wire, so the set is observable from the outside.** A passive
observer watching an authorised client connect learns a member of the set. That
is inherent in SIP-6's plaintext envelope rather than introduced here, and it is
harmless on its own: the observer still cannot pass MAC1 with the key it copied.

**SIP-2's contested-DCID bound depends on this.** SIP-2 argues that poisoning a
contested connection-ID entry is tolerable partly because an attacker must pass
MAC1 in its own right — "under a whitelist, an already-authorised peer, not a
stranger". That mitigation is only as strong as the whitelist, and is absent for
a deployment without one.

## Reference implementation

- squic v0.16.0 — `src/whitelist.rs`, checked at step 4 of
  `ServerSocket::validate_and_strip` in `src/conn.rs`, exposed on
  `ServerListener`. Integration tests cover the known client, the unknown
  client, runtime add and remove, and enabling with an initial set.
- squic-go v0.61.0 — `allowedKeys` in `conn.go`, checked at the same step,
  exposed on `ServerListener`. The same tests, plus one asserting that a
  whitelisted key does not let a caller skip MAC1.

Both now carry that last test; squic-rust gained it while auditing against this
SIP, which is the rule under "What the check proves, and what it does not" and
the one a reader is most likely to get wrong about a whitelist.
