## Abstract

An exchange that rotated its key (SIP-40) receipted everything before
the rotation under the old one, and a verifier that never held the old
key calls all of it repudiated. SIP-40 left such a verifier where a new
client stands: it can hold the earlier key only if it was there when the
handover was published, or if an operator typed it. Since SIP-59 a peer
meets an origin on an account's word alone, days or years after the
window closed, and finds a history it cannot verify. This document has an
exchange **keep every handover it has signed** and serve the chain --
its *lineage*, each link the SIP-40 record the retiring key signed --
to anyone who asks; a verifier that holds the current key checks the
chain back from it and verifies receipts and signatures under every key
in it. No new signature, no new trust: the same records SIP-40 published
in DNS for thirty days, published by the exchange for as long as the
history they cover.

## Motivation

The first live run of SIP-63 put a laptop exchange, listed nowhere, in
the position of an account's home at an origin that had rotated four
days earlier. It pulled the account's three channels; in the oldest, the
first four entries were refused `Repudiated` -- receipted under the
origin's earlier key, which the laptop had never seen and had no way to
learn. The handover record was in fact still in the zone, but nothing
told the laptop to look, and a week later nothing would have been there.

SIP-40 §Consumers says how a holder of the earlier key verifies: under
the current key first, then each key the current one moved from. It
says where a *client* gets that history (its pin store, which watched
the handover happen) and where a *configured replica* gets it (the
operator's `predecessors`). It has no answer for a verifier that met
the exchange after the window closed, and says so: "a holder that has
forgotten it cannot, which is the same position a new client is in
today". SIP-59 and SIP-60 made that verifier the ordinary case -- a home
finds an origin by an account's hint, a client's exchange locates a
domain it never listed -- and every one of them meets an origin with a
past it cannot read.

The fact needed is one the retiring key already signed. A handover is
a statement by the old key that the new key is its successor, bound to
the domain, and it does not stop being true when the window it was
published for closes; what closed was the period in which a *pin* would
move on it. The exchange that holds the successor key held the old one
when it signed, and can keep the statement. Serving it costs nothing and
asserts nothing the old key did not.

## Specification

All integers are unsigned big-endian. **Handover** is SIP-40's record;
**origin** and **replica** are SIP-35's; **place** is SIP-31's.

### Lineage

An exchange's lineage is the ordered list of handovers from its oldest
key to its current one, each link's `to` being the next link's `from`,
and the last link's `to` its current key. An exchange with no rotation
behind it has an empty lineage.

```
Link    | dom_len: u8 | domain | from[32] | to[32] | until: u64 | sig[64] |
Lineage | count: u8 | count × Link |
```

`domain`, `from`, `to`, `until` and `sig` are the handover's fields as
SIP-40 defines them, `domain` being the one the signature is bound to,
lowercased with no trailing dot. `count` is at most `MAX_LINEAGE = 16`.

`GET /exchange/lineage` (a `POST` with an empty body is the same
request, for a peer whose client only posts) answers with the exchange's
lineage, to any caller, identified or not: every link in it was published in a public
zone, and the current key is published there today. An exchange MUST
keep every handover it signs (SIP-40 §Producing a handover, step 3) and
serve it here from the moment the successor key is in use; an exchange
MAY also be given a link by its operator, for a rotation done before this
document. An exchange from before this document answers SIP-21
`not_found`, and a verifier treats that as an empty lineage.

### Verifying a lineage

A verifier holds a key `K` for an exchange -- pinned by SIP-33, named by
an account's Move (SIP-59), configured -- and, usually, the domain `D` it
holds it for. It accepts a lineage when:

1. every link's signature verifies under its `from` for the link's
   `domain`, by SIP-40's signing input;
2. no two links share a `from`, and each link's `to` is the next link's
   `from`;
3. the last link's `to` is `K`;
4. where the verifier holds `D`, every link's `domain` is `D`.

`until` is **not** checked against the clock. It bounded the window in
which a pin would move on the record (SIP-40 §Resolution); the record's
statement -- this key handed to that one -- has no expiry, and a lineage
is history. A lineage that fails any rule is discarded whole and the
verifier proceeds with what it had, which is what SIP-40 already
requires of a bad handover: silently, and never as a fault in the
verifier's own state.

The accepted lineage's `from` keys, newest first, are the exchange's
**predecessors**, and a verifier uses them exactly as SIP-40 §Consumers
says a holder of the moved-from key does: a receipt (SIP-34) verifies
under the current key or any predecessor; a signed entry (SIP-31)
verifies under the place naming the key it was signed under, and its
chain link is taken under that key; **a key envelope (SIP-32) likewise**,
since its signature names the place it was published to. Predecessors
learned this way are
added to any the verifier already holds -- an operator's `predecessors`,
a pin store's moved-from key, a channel's origin history (SIP-53) -- and
replace none of them.

### When a replica asks

A replica (SIP-35, and a home acting as one under SIP-59) SHOULD ask an
origin's lineage before its first pull from it, and MUST ask again when
a pull refuses an entry as repudiated: a rotation since the last ask is
the ordinary reason for one. What it learns it keeps with the origin,
so a restart does not ask again and an origin that has since gone away
still has its past verified. An entry refused before the lineage was
learned is a hole a later pull fills (SIP-62's holes), and a replica
that learned a lineage SHOULD pull once from the lowest hole in each of
that origin's channels.

A client (SIP-40's store scoped by exchange key) MAY ask its exchange's
lineage, and SHOULD when it holds a channel whose origin is not its own
exchange (SIP-43) and no history for that origin; a client that moved
its pin by the operator's word (`sqex discover --replace`) has the same
gap and the same remedy.

### Limits

`MAX_LINEAGE = 16` links. A `Link` is at most 1 + 255 + 32 + 32 + 8 + 64
bytes; a `Lineage` at most 1 + 16 × that.

## Rationale

**Why the handover record and not a new statement.** A new "these were
my keys" record signed by the current key would prove only that the
current key says so. The handover is signed by the *retiring* key, and
a chain of them is a chain of consents: each key vouched for its
successor at the time. The current key cannot forge a link into that
chain without the old key, which is SIP-40's whole property, kept.

**Why the current key is the anchor and not the oldest.** A verifier
knows the current key -- that is what it holds, discovered or named --
and knows nothing older; a chain is checked from what is known toward
what is not. Rule 3 is what makes a stolen old key inert here as it is
in SIP-40: a thief holding a retired key can sign a link from it to any
key they like, and no verifier accepts it unless the thief's key is the
one it already holds for the exchange, which no lineage granted.

**Why `until` is not checked.** SIP-40 bounded `until` for the signer's
protection during the window: a handover in the zone moves pins, and a
pre-signed one in a thief's pocket must be worth little. A link served
as history moves nothing; it lets a verifier read receipts under a key
that no longer signs anything. Checking `until` here would make every
lineage expire thirty days after the rotation, which is precisely the
population this document exists for.

**Why the exchange keeps the record rather than the zone.** The zone is
where a handover does its work and the operator withdraws it when the
window closes, as SIP-40 tells them to. The exchange is the party that
signed it, holds the successor, and answers for the history; asking it
is asking the right party, and costs a round trip a peer is already
making.

**Why not walk chains in SIP-40's resolution.** SIP-40 refused to walk
`A→B→C` on resolution because a pin should move one deliberate step at a
time and each step is a live key in the zone. A lineage is not
resolution: nothing moves, every key in it is retired but the last, and
the verifier's own key is the anchor. The two rules answer different
questions and do not conflict.

**Why the replica keeps what it learned.** An origin can be unreachable
later, or gone (SIP-53), and its copies still hold entries under its old
keys. A lineage learned once is as durable as the copy it verifies.

## Compatibility

Additive. An exchange from before this document answers `not_found` and
a verifier proceeds with the predecessors it has, which is today's
behaviour; a verifier from before this document never asks, and the
exchange's answer is never sent. A `Link` is the SIP-40 record in fixed
fields; nothing about the record, its signing input or its resolution
rules changes. An operator who rotated before this document gives the
exchange the record by hand; it is the line `sqexd handover` printed.

## Security considerations

**A lineage grants nothing.** It lets a verifier accept, under an earlier
key, what it would already accept under the current one: receipts and
entries the exchange served. A forged lineage could at most make a
verifier accept a receipt under a key that never was the exchange's --
and to serve such a lineage the forger must hold the current key (rule
3) and a signature from the claimed earlier key (rule 1). Holding both,
they could have signed the receipt under the current key instead.

**A stolen retired key.** SIP-40 says a thief with the old key and the
zone is total and that a thief with the old key alone can sign and not
publish. Here a thief with a retired key can sign a link and serve it
only from an exchange whose current key a verifier already holds, which
means an exchange the thief runs and the verifier chose -- by discovery
of the thief's own domain, or by an account's Move naming it. What the
thief gains is the ability to present, under that exchange, entries the
real exchange receipted under the stolen key: entries the thief had to
have obtained as a member or a peer, presented to peers of the thief's
own exchange. That is the thief's own copy of what they could read,
served as their own history, and the same disclosure the member made by
choosing them.

**The lineage is public.** So was each link, in the zone, for up to
thirty days. What this adds is the duration, and that the rotation
history of an exchange is readable by anyone at any later time. An
operator who rotates because a key was stolen publishes, by this, that a
rotation happened on that date; SIP-40's window already did.

**Domain binding.** Rule 4 keeps a link signed for one zone from being
served as another zone's history by an exchange that holds the same key
for both, where the verifier knows which zone it came through. A
verifier holding a key alone accepts the domain the chain states, which
is the current key's own account of itself -- the same trust a receipt
already places in it.

## Reference implementation

`sqex` 0.81.0. `sqex-proto::lineage::{Link, Lineage, MAX_LINEAGE}` with
`Lineage::predecessors_for(current, domain)` applying the four rules
(the signing input is SIP-40's, checked byte-for-byte against
`sqex-discovery`'s). `sqexd handover` appends the record it prints to
`lineage` beside the key file; the daemon reads that file on start,
verifies the chain ends at its own key, logs the count, and serves
`GET /exchange/lineage`. A replica asks before its first pull from each
origin and again on a repudiated entry, keeps what it learned in the
channel store (`lineage(origin, predecessor, position)`), folds it into
`take_under`'s predecessors, and pulls from the lowest hole once it has
learned something new. `sqex exchange lineage` shows an exchange's
chain. Tests: a rotated origin's pre-rotation entries are repudiated at
a home learned by hint and verified once the lineage is served; a link
whose signature fails, whose chain breaks, whose last key is not the
origin's, or whose domain is another's is discarded whole and the
verifier stays where it was; the daemon refuses to serve a lineage that
does not end at its own key.

Run live on 2026-09-18 against trunk.exchange, which had rotated on
2026-09-14 and whose handover record was still in the zone. The laptop
exchange of SIP-63's run, homed by the same account, refused the first
four entries of trunk.exchange's oldest channel as repudiated on every
pull while trunk.exchange ran 0.80.0; the record was written to
trunk.exchange's lineage file from the zone, and ten minutes after the
laptop's first ask -- the bounded re-ask a repudiated entry earns -- it
learned the earlier key and the next pull stored the four. `sqex
lineage` at trunk.exchange shows the one link, verified back from the
pinned key.

One finding beside the document. trunk.exchange's key is a systemd
credential, so the lineage file's default beside the key resolved to a
path nothing writes, and a missing file is legitimately "no rotation":
the first start looked healthy with nothing served. An operator sets the
path explicitly in that case, and 0.81.1's startup line says where the
daemon looked.

A second finding, five days later (2026-09-19, sqex 0.97.1). This
document said "receipts and signatures" and the reference implementation
read it as receipts and entries: key envelopes went on being checked
under the current key alone, at the copy and in the chat client. The
account of trunk.exchange's own operator moved home to ex, ex pulled a
direct message trunk.exchange had ordered before its rotation, and
refused both of its envelopes on every pull -- 640 warnings in three
hours, and a copy with no key for its members. Envelopes now verify
under predecessors as entries do, the sentence above says so, and the
lineage test publishes one under the earlier key.
