## Abstract

sQUIC appends an authenticated trailer to every QUIC Initial packet: 69 bytes
from an anonymous caller, 101 from one asserting an identity. The trailer
carries the caller's X25519 public key, optionally its Ed25519 identity, a
timestamp, two 16-byte tags and a header byte. A server that cannot verify them
drops the packet in silence, so a caller who does not already hold the server's
public key gets no response and no evidence the server exists. This SIP
specifies that trailer byte by byte, the two tag constructions over it, the
order in which a server checks it, and the single Ed25519 seed from which every
key in the scheme is derived.

The first tag is the **gate**: one HMAC, keyed on the server's public key or on
a cookie, verified before any elliptic-curve work. The second is **MAC1**, keyed
on the Diffie-Hellman shared secret. The gate replaces the separate MAC0 of
SIP-37 and MAC2 of SIP-7, which were two states of one proof — a cookie is
delivered encrypted under a key derived from the server's public key, so
producing a valid MAC2 already demonstrated the knowledge MAC0 existed to
prove. Envelope version 3 spent 32 bytes on both. Version 4 spends 16 on one and
this SIP absorbs SIP-37 entirely.

None of this was written down. SIP-2 exposes the key MAC1 verifies and SIP-3
adds a field to the envelope, so both are specified in terms of a mechanism that
existed only as code — which is the condition this repository exists to end.
This SIP is therefore written after the two SIPs that depend on it, and is the
normative statement they should have been able to cite.

## Motivation

A silent server is the whole premise. sQUIC exists so that a service can be
reachable to callers holding its public key and invisible to everyone else: no
handshake response, no error, no TLS alert, nothing that distinguishes a sQUIC
server from a closed UDP port. That property has to be established before the
QUIC state machine sees a packet, because QUIC itself will happily answer a
stranger.

The mechanism is a trailer on the Initial packet carrying a MAC that only a
caller who knows the server's public key can compute. It is WireGuard's MAC1
idea moved onto QUIC, and it has been shipped in two implementations for a year.
What has never existed is a description of it. SIP-2 says a client "proves
possession of the matching private key by MAC1, computed over a Diffie-Hellman
shared secret" and stops there. SIP-3 reproduces the envelope diagram and points
at `squic-rust/src/mac.rs` for the rest, then changes the layout — so the only
normative record of the field order is a SIP about something else, and the only
record of MAC1's input is a Rust source file.

A second implementer working from the SIP set could not build a client. That is
the test SIP-1 sets, and the envelope fails it.

## Specification

All integers are unsigned big-endian.

### The identity key and its derivations

Every participant in this ecosystem is named by one **Ed25519 key**, held as a
32-byte seed. Three keys are derived from that seed, and an implementation MUST
derive all three exactly as follows or it will not interoperate with anything.

```
seed (32)  ──> Ed25519 signing key      the identity; also the TLS
           │                            certificate key (SIP-9)
           └─> X25519 static secret     the transport key; MAC1's DH input
```

The Ed25519 signing key is the seed used directly, per RFC 8032.

The X25519 static secret is `SHA-512(seed)[0..32]`, clamped per RFC 7748:

```
scalar     = SHA-512(seed)[0..32]
scalar[0] &= 248
scalar[31] &= 127
scalar[31] |= 64
```

This is the standard Ed25519-to-X25519 private key conversion, and it means the
two public keys are one scalar's point in two coordinate systems — the fact
SIP-3's derivation check depends on.

An implementation MUST treat the X25519 static secret as being exactly as
sensitive as the Ed25519 private key, because it is: both are the same scalar,
and an Ed25519 signature needs only the scalar. It is not a session key and MUST
NOT be handled as one.

### Which packets carry the envelope

A packet is a QUIC Initial for the purposes of this SIP when it is at least 5
bytes long and `first_byte & 0xF0 == 0xC0` — long header form, fixed bit set,
packet type `0b00`.

A client MUST append the envelope to every Initial datagram it sends, and MUST
NOT append it to any other packet. A server MUST validate the envelope on every
Initial and MUST pass every non-Initial packet through untouched.

**Every Initial, not only the first.** A server drops an Initial that fails MAC1
without any response, so an unstamped retransmission is indistinguishable from
an attack and is dropped too. A client that stamped only its first Initial could
never recover from losing that packet: it would retransmit unstamped, be
dropped, and stall until the handshake timed out.

Handshake and short-header packets carry no envelope and are not checked. This
is sound because neither can begin a connection: they are only meaningful
against connection state the QUIC layer established from an Initial that did
pass MAC1, and a packet referring to no such state is discarded by QUIC itself.
The envelope guards the door, not every room behind it.

**0-RTT is the exception, and MUST be dropped.** It carries no envelope either,
but unlike the other two it *does* begin something: it is application data, and
a stack configured to accept it will deliver a stranger's payload having checked
no gate, no MAC1, and no whitelist — SIP-8 filters the X25519 key in the
envelope, and a 0-RTT datagram carries none. The envelope cannot be extended to
cover it: 0-RTT is sent before the handshake this transport authenticates, so
there is no shared secret yet to key MAC1 with. A server MUST therefore drop any
datagram whose first packet is 0-RTT (long header, packet type 0x01), before the
QUIC stack sees it. A datagram that coalesces an Initial ahead of 0-RTT begins
with an Initial, is checked as a whole, and is unaffected.

### The envelope

The trailer is appended to the QUIC datagram. Its width depends on one flag in
the header byte: **69 bytes** without an asserted identity, **101** with one.

```
[ QUIC datagram ][ X25519 pub (32) ][ Ed25519 pub (32, only if flagged) ][ ts (4) ][ gate (16) ][ MAC1 (16) ][ hdr (1) ]
```

| Field | Width | Meaning |
|---|---|---|
| X25519 pub | 32 | The caller's transport public key |
| Ed25519 pub | 32 or 0 | The caller's asserted identity, present only when `hdr` says so (SIP-3) |
| ts | 4 | Epoch seconds, for the replay window |
| gate | 16 | Proof of the server's public key, or of a cookie |
| MAC1 | 16 | Proof the caller holds the private key for the X25519 field |
| hdr | 1 | Version and flags (SIP-29) |

The **header byte** is last, and that position is normative: it is the only
offset a receiver can read without already knowing the trailer's width, and
knowing the width is what the marker is for. Its high nibble is the envelope
version — `4` for this document — and its low nibble is flags. Bit 0 set means
an Ed25519 field is present. Bits 1 to 3 are reserved. A sender MUST
set them to zero and **a receiver MUST drop a datagram that sets one.**

The receiver half is the load-bearing one, and it is not about tampering. A bit
flipped in transit already fails: both tags cover the header byte as received,
so the tag no longer verifies. The case it closes is a caller that sets a
reserved bit *and computes its tags over it* — internally consistent, and
therefore admitted by any receiver that merely ignores the bits, because nothing
else looks at them.

That is a one-way door. A receiver that admits these bits with no meaning
attached cannot later be given a version that assigns them one: it would have no
way to tell a peer asserting the new flag from an older peer that set the bit
for no reason. Rejecting them is only free while none of them are wanted, which
is why it is specified now rather than when the first flag is needed.

**The Ed25519 field is present or absent, not zero or non-zero.** Version 3
carried 32 zero bytes on every anonymous Initial to say what the flag now says
in one bit. Absence and an all-zero field mean the same thing to a consumer —
no identity asserted — so SIP-3's semantics are unchanged; only the encoding is.

A server reads `hdr`, derives the trailer width from it, and MUST drop any
Initial whose length is not greater than that width. It MUST drop a datagram
whose header names a version it does not implement, and MUST NOT attempt any
other layout: guessing a second layout for one datagram is what let a single
packet be parsed twice under the version-1 fallback SIP-29 originally defined.

### The covered range

Both tags are computed over the same bytes, in one pass, contiguously from
offset 0:

```
covered = quic_datagram || x25519 || [ ed25519 ] || ts
```

That is the whole datagram as written so far — everything before the two tags
and the header byte. The Ed25519 segment appears only when the flag says it
does. Both tags additionally prefix the header byte, so a tag computed under one
version or flag combination is unrelated to one computed under another:

```
tag = HMAC-SHA256(key, hdr || covered)[0..16]
```

Prefixing rather than appending is deliberate: the header is the first thing a
receiver reads and the first thing it feeds the hash, so the layout it names is
bound to the tag before any field parsed under that layout is.

### The gate tag

```
gate = HMAC-SHA256(Kg, hdr || covered)[0..16]
```

with the key depending on what the caller holds:

```
Kg = SHA-256("squic-gate-v1" || server_x25519_pub)   caller holds no cookie
Kg = the 16-byte cookie                              caller holds one (SIP-7)
```

The gate is the cheap check that must precede the curve operation. Verifying
MAC1 costs a Diffie-Hellman, so without something in front of it a server cannot
distinguish a caller who knows its public key from a stranger, and under load
must challenge both — which is how a silent server ends up answering everybody
exactly when it matters most.

**The server rule, and it MUST NOT soften.** The server knows its own load
state, so there is nothing on the wire for an attacker to flip:

- **Under load**, three outcomes and the middle one is the point. A
  cookie-keyed gate proves the key *and* the source address: accept. A
  key-keyed gate proves the key but not the address: answer with a cookie
  challenge and drop. Neither: silence. A server MUST NOT fall back to the
  key-keyed form as grounds for *acceptance* under load — that fallback returns
  the caller to an unvalidated address, which is the one thing the cookie exists
  to establish and the one thing a single datagram cannot demonstrate.
- **Not under load**, either form is accepted: the key-keyed form first, then
  the cookie. A client that answered a challenge during an earlier burst still
  holds a cookie and MUST NOT be made to re-handshake because the load
  subsided. Two HMACs at worst, still far below one X25519.

A server MUST NOT issue a cookie challenge to a caller whose gate verifies under
neither key. Challenging on a failed cookie check alone answers strangers, which
is the defect this construction exists to close.

### MAC1

```
shared = X25519(client_x25519_priv, server_x25519_pub)
MAC1   = HMAC-SHA256(shared, hdr || covered)[0..16]
```

MAC1 covers exactly the range the gate covers, under a different key. The two
cannot be merged: verifying MAC1 requires the Diffie-Hellman that the gate
exists to avoid, so collapsing them would defeat the arrangement entirely.

**The X25519 field is in the covered range.** In version 3 it was not — it was
bound implicitly, as the input to the shared secret, on the reasoning that
altering it changes `shared` and MAC1 fails. That reasoning still holds, and the
field is included anyway, because the gate also covers this range and the gate
is *not* keyed on the shared secret. Under a cookie-keyed gate, nothing else
would bind the caller's key to the tag. One contiguous range hashed once by both
tags is cheaper than two ranges and much harder to get wrong.

### Server validation, in order

A server MUST perform these steps in this order, and MUST NOT reorder them.

1. **Header and length.** Read the last byte. Drop if it names a version this
   server does not accept, if it sets a reserved flag bit, or if the datagram is
   not longer than the trailer width the flags imply.
2. **Replay window.** Drop if `|now - ts| > 120` seconds.
3. **Gate.** As above: under load, cookie-keyed only, with a challenge for a
   key-keyed tag and silence for neither. Not under load, either key.
4. **Whitelist.** Drop if a whitelist is enabled and the X25519 field is not in
   it (SIP-8).
5. **Diffie-Hellman.** Compute `shared`. Drop if the exchange is
   non-contributory — that is, if the result is all zeros, which happens exactly
   when the client's key is of small order.
6. **MAC1.** Drop if MAC1 does not verify, compared in constant time.
7. **Identity.** Apply SIP-3's derivation check to the Ed25519 field, when the
   header says one is present.

The order is normative because it is the defence. Every step before 5 is a
comparison or a hash; step 5 is the only expensive operation, and the point of
the arrangement is that an attacker cannot make a server do elliptic-curve work
by sending rubbish. An implementation that validated MAC1 first and consulted
the whitelist afterwards would be correct in what it admits and useless as a
defence, and the difference is invisible in any functional test.

**The gate is step 3 and not step 5** for the same reason, and this is the step
whose placement was measured rather than argued: on an instrumented build,
junk that satisfies steps 1 and 2 costs the server one HMAC and zero curve
operations. Before the gate existed, the same junk bought a Diffie-Hellman.

A server MUST NOT respond to a packet it drops at any of these steps — no error,
no close, no ICMP it can suppress. Silence is the property being defended. The
cookie challenge of step 3 is the single exception in the whole protocol, and it
is answerable only by a caller who has already proved knowledge of the server's
public key.

### The replay window, and the nonce that was removed

`ts` is checked against a symmetric 120-second window, so a clock skewed either
way by up to two minutes still connects. The window is the only replay defence
in the envelope.

Version 3 also carried 8 random bytes as a nonce. **Version 4 removes it**, and
nothing was lost: the SIP that defined it already said it was not tracked and
not a replay defence, and neither implementation read it outside the MAC input.
Its only job was to keep two identical datagrams in the same second from
producing the same tag — and the QUIC datagram underneath, carrying its own
random connection IDs and encrypted crypto frames, already differs per attempt.
Eight bytes for entropy that the covered range supplies anyway.

A server keeps no set of tags it has seen, so an Initial captured from the wire
can be replayed verbatim to the same server for as long as its timestamp remains
in the window, and it will be accepted.

This is deliberate, and the cost is bounded. Accepting a replayed Initial makes
the server do one Diffie-Hellman and start one QUIC handshake that the replayer
cannot complete: it holds no private key, so it cannot finish TLS, and the
connection dies at the handshake timeout. What it cannot do is authenticate as
the original caller, learn anything about the server it did not already know, or
create state that outlives the timeout. Under a flood, the cookie defence of
SIP-7 engages on the DH rate and replayed Initials are challenged like any
other.

The alternative — a seen-tag cache — would give the server per-caller state
before MAC1 has verified anything, which is precisely the state an
unauthenticated attacker gets to allocate. A stateless gate that admits a
bounded replay is a better trade than a stateful one that admits a
memory-exhaustion attack.

### Degenerate keys

The server MUST reject a client X25519 key of small order (step 5). A small-order
key makes the exchange non-contributory: the shared secret is all zeros whatever
the server's private key is, so a caller who has never seen the server's public
key can compute it in advance and forge a MAC1 that verifies. This is SIP-2's
R6, restated here because this SIP owns the step that enforces it.

## Rationale

**Why a trailer and not a QUIC extension.** The envelope has to be verifiable
before QUIC parses anything, by code that owns the UDP socket. A transport
parameter or a new frame type is inside the encrypted handshake, which is far
too late: by then the server has answered.

**Why HMAC-SHA256 truncated to 16 bytes.** It is WireGuard's choice for the same
job and needs only a hash, which every implementation already has for other
reasons. Sixteen bytes is not a signature and does not need to be: forging it
requires the shared secret, and the secret requires the server's public key.

**Why one covered range for both tags.** Version 3 gave each tag its own input
and left the X25519 key out of MAC1's, on the reasoning that the key is bound
implicitly by being the shared secret's input. That reasoning is sound for MAC1
alone and does not survive a second tag keyed on something else: under a
cookie-keyed gate nothing would bind the caller's key to the tag. One
contiguous range from offset 0, hashed once by each tag, is cheaper than two
ranges, and it removes a class of defect where the two sides of an
implementation disagree about which bytes a tag covers.

**Why both keys are on the wire in plaintext.** MAC1 must be checkable without
state, so the server has to be told which key to do the DH against. The cost is
that a persistent client presents a stable identifier to a passive observer;
SIP-2 records this and SIP-3 makes the Ed25519 half optional so a caller can
decline it. The X25519 half is not optional, because there is no MAC without it.

**Why the header byte goes last.** It is the only offset a receiver can find
without already knowing the trailer's width, which is precisely what the marker
is for. Put at the front it would be unreachable; put at the back, any receiver
can read it and then know what it is looking at. This is SIP-29's finding, and
the reason a version marker looked impossible for as long as it was assumed to
belong at the front.

**Why the identity field is flagged rather than zeroed.** `advertise_identity`
defaults false, so the common Initial carried 32 bytes of nothing. A flag says
the same thing in one bit and costs the anonymous caller nothing — which is the
caller this protocol is built around.

**Why the validation order is normative rather than advisory.** An
implementation that gets it wrong passes every functional test: the same packets
are admitted and the same packets are dropped. Only the cost profile changes,
and only under attack, which is when nobody is reading the code. A rule that can
be broken invisibly has to be stated as a requirement.

## Compatibility

**Versions 1, 2 and 3 are retired and MUST NOT be accepted.** Version 4 is the
only layout this document defines and the only one either implementation
parses. This was a coordinated cut with no overlap release: nothing speaks
version 3 after it, in either direction, and every failure during the window was
silent, because a refused envelope draws no reply at either end. Serving `[3, 4]`
while clients moved would have made it safer at the cost of one extra release;
that was offered and declined, and the cut carried the window knowingly.

The retirement is not housekeeping. Versions 1 and 2 carried no gate at all, so
a server accepting them performed a Diffie-Hellman for any caller who sent a
plausible Initial — the defence SIP-37 added was simply absent for those
layouts. A default accept set that included them was measured doing exactly
that. A version that must be narrowed *away from* in order to be safe will be
left wide somewhere, so the versions were removed rather than deprecated.

**A server MUST refuse to start on an accept set it cannot parse**, and MUST
refuse an empty one. This is SIP-29's rule and it is repeated here because this
document owns the silence that makes it dangerous: such a server binds, reports
itself healthy, and drops every Initial without a word. The exchange at
`ex.squic.org` was configured for version 3 up to the cut, and installing a
version 4 binary without editing that line in the same breath would have taken
it down without one error anywhere.

**The Initial still exceeds the segment size.** A 1200-byte QUIC Initial plus 69
bytes is 1269 — down from version 3's 1325, and from 1308 for the original
108-byte envelope — but still above the 1200-byte segment size implementations
use. On Linux with GSO enabled, sending it through the ordinary
batched path is ambiguous and the datagram may be silently segmented and
dropped. Both implementations therefore bypass their batched send path for
Initials and write them as single raw datagrams, losing GSO, ECN marking and
`sendmmsg` batching for those packets only. This is acceptable because Initials
are in flight only during the handshake.

It cannot be fixed by shrinking the envelope further, and the reason is
structural: QUIC requires an Initial datagram to be at least 1200 bytes and
sQUIC wraps it, so any trailer at all puts the UDP payload above the segment
size. Version 4 makes the overshoot 56 bytes smaller; it cannot make it zero.

**0-RTT MUST NOT be offered at all.** This is stricter than the earlier rule,
which required only that it default to off and permitted a per-deployment
opt-in. That opt-in was unsound: an implementation exposing it had a switch
whose effect was to disable its own authentication, and the replay exposure it
was documented as accepting was the lesser half of the cost. The greater half is
that a 0-RTT datagram reaches the QUIC stack having passed no check in this
document. Both implementations now refuse 0-RTT in the transport, and neither
exposes a switch: squic-rust also disables it in the TLS configuration, and
squic-go's `Enable0RTT` is removed.

**Connection migration is a QUIC-level setting the two implementations expose
differently.** squic-rust offers a switch to disable active migration;
squic-go does not, and takes quic-go's default. Neither choice is visible on
the wire or changes the envelope, and the one place migration touches sQUIC is
already specified: SIP-2 requires the peer-key join to be made on the
destination connection ID rather than the source address, precisely so that a
migrating or NAT-rebound peer is not misidentified.

**Both implementations must move together** for any change to this SIP, per
SIP-1: it is entirely wire.

## Security considerations

**MAC1 authenticates knowledge of the server's public key, not the caller's
identity.** Anyone holding the server's public key can compute a valid MAC1 with
a freshly generated keypair. That is the intended property: MAC1 decides whether
the server responds at all, and SIP-2, SIP-3 and SIP-8 decide who the caller is
and whether they may proceed. Treating a passed MAC1 as authorisation would be a
serious error.

**The server's public key is a shared secret in one narrow sense.** It is public
in every ordinary meaning, but the invisibility property rests on an attacker not
having it. A deployment that publishes the key gives up silence and keeps every
other guarantee.

**An Initial is replayable inside the timestamp window**, as specified above. The
gain to an attacker is one Diffie-Hellman and one handshake that times out.

**The gate is not authorisation, and neither is a cookie.** A valid gate proves
only that the caller holds the server's public key, or a cookie the server
issued to that address. Both are cheap to check and neither says anything about
who the caller is; MAC1, SIP-3 and SIP-8 do that. A gate that verifies buys the
caller one Diffie-Hellman, which is exactly what it is for.

**Truncating the gate to 16 bytes is sound for what it defends.** Forging one
without the server's public key means guessing 128 bits. Forging one *with* the
key is trivial and irrelevant: a caller holding the key is entitled to pass the
gate, and everything that follows still has to hold.

**A small-order client key forges MAC1 outright** if the non-contributory check
is missing, because the shared secret is then all zeros and predictable without
any knowledge of the server. Step 5 is the only thing preventing this for a
deployment with no whitelist. It is worth being blunt: the check was added after
the fact, and until it was, silence rested entirely on SIP-8's whitelist for the
deployments that had one and on nothing at all for the deployments that did not.

**The envelope is not confidential.** Both public keys and the timestamp are
plaintext, and an observer can identify a persistent client by its X25519 key
across connections and networks. SIP-3's optional Ed25519 field is
the part a caller can withhold; the X25519 key is not withholdable.

**Timing.** MAC comparisons MUST be constant-time. The validation order leaks
coarse information by construction — a caller can learn that it passed the
whitelist by observing that the server spent time on a DH — but this requires
the attacker to already hold the server's public key, and what it reveals is
what the whitelist would reveal anyway.

## Reference implementation

- squic v0.25.0 — `src/mac.rs` (envelope constants, the gate and MAC1
  constructions, `trailer_len`, the replay window), `src/conn.rs`
  (`ClientSocket::build_initial`, `ServerSocket::validate_and_strip` and
  `validate_envelope`), `src/crypto.rs` (the seed derivations and the
  non-contributory check).
- squic-go v0.70.0 — `mac.go` and `conn.go`, with the same structure and the
  same field names.

Tests added while auditing the two against this SIP: an end-to-end refusal of a
small-order client key (Rust had none, so step 5 was untested), a check that the
envelope is the width this document states (Go had none), and, in `src/mac.rs`
and `mac_internal_test.go`, the MAC1 round trip and the replay window on both
sides. Version 4 added compile-time assertions that the two trailer widths are
69 and 101, a test that a flipped header byte is refused rather than parsed
under another layout, and — as the measurement behind the gate's placement — a
test asserting that junk costs zero curve operations.

The two are held to the same wire behaviour by the cross-implementation test
described in SIP-2 (`scripts/cross_peerkey_test.sh` in squic-go), which runs the
full server/client matrix across both implementations and asserts they agree on
the key each envelope carried. It exercises the layout, the MAC1 input ordering
and the derivation check across the language boundary, and runs in CI on both
repositories.
