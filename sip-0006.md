## Abstract

sQUIC appends a 108-byte authenticated trailer to every QUIC Initial packet.
The trailer carries the caller's X25519 public key, its optional Ed25519
identity, a timestamp, a nonce and two MACs; a server that cannot verify MAC1
drops the packet in silence, so a caller who does not already hold the server's
public key gets no response and no evidence the server exists. This SIP
specifies that trailer byte by byte, the MAC1 construction over it, the order in
which a server checks it, and the single Ed25519 seed from which every key in
the scheme is derived.

None of this was written down. SIP-2 exposes the key MAC1 verifies and SIP-3
adds a field to the envelope, so both are specified in terms of a mechanism that
existed only as code — which is the condition this repository exists to end.
This SIP is therefore written after the two SIPs that depend on it, and is the
normative statement they should have been able to cite.

## Motivation

A silent server is the whole premise. sQUIC exists so that a service can be
reachable to callers holding its public key and invisible to everyone else: no
handshake response, no error, no TLS alert, nothing that distinguishes a sQUIC
server from a closed UDP port. That property has to be established before the
QUIC state machine sees a packet, because QUIC itself will happily answer a
stranger.

The mechanism is a trailer on the Initial packet carrying a MAC that only a
caller who knows the server's public key can compute. It is WireGuard's MAC1
idea moved onto QUIC, and it has been shipped in two implementations for a year.
What has never existed is a description of it. SIP-2 says a client "proves
possession of the matching private key by MAC1, computed over a Diffie-Hellman
shared secret" and stops there. SIP-3 reproduces the envelope diagram and points
at `squic-rust/src/mac.rs` for the rest, then changes the layout — so the only
normative record of the field order is a SIP about something else, and the only
record of MAC1's input is a Rust source file.

A second implementer working from the SIP set could not build a client. That is
the test SIP-1 sets, and the envelope fails it.

## Specification

All integers are unsigned big-endian.

### The identity key and its derivations

Every participant in this ecosystem is named by one **Ed25519 key**, held as a
32-byte seed. Three keys are derived from that seed, and an implementation MUST
derive all three exactly as follows or it will not interoperate with anything.

```
seed (32)  ──> Ed25519 signing key      the identity; also the TLS
           │                            certificate key (SIP-9)
           └─> X25519 static secret     the transport key; MAC1's DH input
```

The Ed25519 signing key is the seed used directly, per RFC 8032.

The X25519 static secret is `SHA-512(seed)[0..32]`, clamped per RFC 7748:

```
scalar     = SHA-512(seed)[0..32]
scalar[0] &= 248
scalar[31] &= 127
scalar[31] |= 64
```

This is the standard Ed25519-to-X25519 private key conversion, and it means the
two public keys are one scalar's point in two coordinate systems — the fact
SIP-3's derivation check depends on.

An implementation MUST treat the X25519 static secret as being exactly as
sensitive as the Ed25519 private key, because it is: both are the same scalar,
and an Ed25519 signature needs only the scalar. It is not a session key and MUST
NOT be handled as one.

### Which packets carry the envelope

A packet is a QUIC Initial for the purposes of this SIP when it is at least 5
bytes long and `first_byte & 0xF0 == 0xC0` — long header form, fixed bit set,
packet type `0b00`.

A client MUST append the envelope to every Initial datagram it sends, and MUST
NOT append it to any other packet. A server MUST validate the envelope on every
Initial and MUST pass every non-Initial packet through untouched.

**Every Initial, not only the first.** A server drops an Initial that fails MAC1
without any response, so an unstamped retransmission is indistinguishable from
an attack and is dropped too. A client that stamped only its first Initial could
never recover from losing that packet: it would retransmit unstamped, be
dropped, and stall until the handshake timed out.

Handshake, 0-RTT and short-header packets carry no envelope and are not checked.
This is sound because none of them can begin a connection: they are only
meaningful against connection state the QUIC layer established from an Initial
that did pass MAC1, and a packet referring to no such state is discarded by QUIC
itself. The envelope guards the door, not every room behind it.

### The envelope

The trailer is appended to the QUIC datagram, and is 108 bytes:

```
[ QUIC datagram ][ X25519 pub (32) ][ Ed25519 pub (32) ][ ts (4) ][ nonce (8) ][ MAC1 (16) ][ MAC2 (16) ]
```

| Field | Width | Meaning |
|---|---|---|
| X25519 pub | 32 | The caller's transport public key |
| Ed25519 pub | 32 | The caller's asserted identity, or all zeros (SIP-3) |
| ts | 4 | Epoch seconds, for the replay window |
| nonce | 8 | Random, from a CSPRNG |
| MAC1 | 16 | Proof the caller knows the server's public key |
| MAC2 | 16 | Cookie proof, or all zeros (SIP-7) |

Field widths and order are fixed. There is no variable-length form and no
version marker; see Compatibility.

The Ed25519 field's semantics — when it is zero, what a server must check when
it is not — are SIP-3's, and are not restated here.

A server computes `quic_len = datagram_len - 108` and MUST drop any Initial
whose length is not greater than 108.

### MAC1

```
shared = X25519(client_x25519_priv, server_x25519_pub)
MAC1   = HMAC-SHA256(shared, quic_datagram || ed25519 || ts || nonce)[0..16]
```

`quic_datagram` is the packet before the trailer — bytes `0..quic_len`.
`ed25519` is the 32-byte field exactly as it appears on the wire, all zeros
included.

The X25519 field is **not** in the MAC1 input. It is bound implicitly: it is the
key the shared secret is computed from, so altering it changes `shared` and MAC1
fails. The Ed25519 field is **explicitly** in the input, and MUST be, because it
does not feed the shared secret — SIP-3 gives the attack that omitting it
enables.

### Server validation, in order

A server MUST perform these steps in this order, and MUST NOT reorder them.

1. **Length.** Drop if the datagram is not longer than 108 bytes.
2. **Replay window.** Drop if `|now - ts| > 120` seconds.
3. **MAC2.** If the server is under load, require a valid MAC2 or answer with a
   cookie and drop (SIP-7). Skipped entirely when not under load.
4. **Whitelist.** Drop if a whitelist is enabled and the X25519 field is not in
   it (SIP-8).
5. **Diffie-Hellman.** Compute `shared`. Drop if the exchange is
   non-contributory — that is, if the result is all zeros, which happens exactly
   when the client's key is of small order.
6. **MAC1.** Drop if MAC1 does not verify, compared in constant time.
7. **Identity.** Apply SIP-3's derivation check to the Ed25519 field.

The order is normative because it is the defence. Every step before 5 is a
comparison or a hash; step 5 is the only expensive operation, and the point of
the arrangement is that an attacker cannot make a server do elliptic-curve work
by sending rubbish. An implementation that validated MAC1 first and consulted
the whitelist afterwards would be correct in what it admits and useless as a
defence, and the difference is invisible in any functional test.

A server MUST NOT respond to a packet it drops at any of these steps — no error,
no close, no ICMP it can suppress. Silence is the property being defended.

### The replay window, and what the nonce is not

`ts` is checked against a symmetric 120-second window, so a clock skewed either
way by up to two minutes still connects. The window is the only replay defence
in the envelope.

The nonce is 8 random bytes contributing entropy to MAC1. It is **not** tracked:
a server keeps no set of nonces it has seen, so an Initial captured from the
wire can be replayed verbatim to the same server for as long as its timestamp
remains in the window, and it will be accepted.

This is deliberate, and the cost is bounded. Accepting a replayed Initial makes
the server do one Diffie-Hellman and start one QUIC handshake that the replayer
cannot complete: it holds no private key, so it cannot finish TLS, and the
connection dies at the handshake timeout. What it cannot do is authenticate as
the original caller, learn anything about the server it did not already know, or
create state that outlives the timeout. Under a flood, the cookie defence of
SIP-7 engages on the DH rate and replayed Initials are challenged like any
other.

The alternative — a seen-nonce cache — would give the server per-caller state
before MAC1 has verified anything, which is precisely the state an unauthenticated
attacker gets to allocate. A stateless gate that admits a bounded replay is a
better trade than a stateful one that admits a memory-exhaustion attack. This is
worth revisiting only alongside a versioned envelope.

### Degenerate keys

The server MUST reject a client X25519 key of small order (step 5). A small-order
key makes the exchange non-contributory: the shared secret is all zeros whatever
the server's private key is, so a caller who has never seen the server's public
key can compute it in advance and forge a MAC1 that verifies. This is SIP-2's
R6, restated here because this SIP owns the step that enforces it.

## Rationale

**Why a trailer and not a QUIC extension.** The envelope has to be verifiable
before QUIC parses anything, by code that owns the UDP socket. A transport
parameter or a new frame type is inside the encrypted handshake, which is far
too late: by then the server has answered.

**Why HMAC-SHA256 truncated to 16 bytes.** It is WireGuard's choice for the same
job and needs only a hash, which every implementation already has for other
reasons. Sixteen bytes is not a signature and does not need to be: forging it
requires the shared secret, and the secret requires the server's public key.

**Why the X25519 key is not in the MAC1 input.** It cannot be tampered with
usefully — it is the input to the shared secret, so changing it changes the key
MAC1 is computed under, and the MAC fails. Including it would cost bytes to
hash and buy nothing. The Ed25519 field is the opposite case and is included for
exactly that reason.

**Why both keys are on the wire in plaintext.** MAC1 must be checkable without
state, so the server has to be told which key to do the DH against. The cost is
that a persistent client presents a stable identifier to a passive observer;
SIP-2 records this and SIP-3 makes the Ed25519 half optional so a caller can
decline it. The X25519 half is not optional, because there is no MAC without it.

**Why a fixed 108-byte layout with no version field.** Because the first version
did not have one and every version since has inherited the omission. It is a
defect, not a decision, and it is recorded as such in Compatibility.

**Why the validation order is normative rather than advisory.** An
implementation that gets it wrong passes every functional test: the same packets
are admitted and the same packets are dropped. Only the cost profile changes,
and only under attack, which is when nobody is reading the code. A rule that can
be broken invisibly has to be stated as a requirement.

## Compatibility

**The envelope has no version marker, so every change to it is a flag day.** A
peer computes `quic_len = len - 108` with a hardcoded width; a peer using a
different width misparses the packet completely, and because the failure mode is
a silent drop there is no diagnostic. SIP-3 moved the trailer from 76 to 108
bytes this way, with both implementations shipping together and every deployment
cutting over at once.

This should be fixed, and fixing it is out of scope here: a version marker has
to be introduced by a flag day of its own, and designing it — where the marker
sits so that an old peer's misparse is at least detectable, what an unknown
version does — is a SIP in its own right. It is the outstanding follow-up SIP-3
named, and it remains outstanding.

**The Initial exceeds the segment size.** A 1200-byte QUIC Initial plus 108
bytes is 1308, above the 1200-byte segment size implementations use. On Linux
with GSO enabled, sending it through the ordinary batched path is ambiguous and
the datagram may be silently segmented and dropped. Both implementations
therefore bypass their batched send path for Initials and write them as single
raw datagrams, losing GSO, ECN marking and `sendmmsg` batching for those packets
only. This is acceptable because Initials are in flight only during the
handshake, and it can be removed if a future envelope fits within 1200 bytes.

**0-RTT MUST be disabled by default.** The envelope's replay window admits
replayed Initials by design, and 0-RTT turns a replayed flight into replayed
application data. An implementation MAY offer 0-RTT as an explicit per-deployment
opt-in, and a deployment that takes it accepts the replay exposure; an
implementation that offers no such switch is conforming. squic-rust offers none
(0-RTT is disabled in the TLS configuration outright); squic-go offers
`Enable0RTT`, defaulting false.

**Connection migration is a QUIC-level setting the two implementations expose
differently.** squic-rust offers a switch to disable active migration;
squic-go does not, and takes quic-go's default. Neither choice is visible on
the wire or changes the envelope, and the one place migration touches sQUIC is
already specified: SIP-2 requires the peer-key join to be made on the
destination connection ID rather than the source address, precisely so that a
migrating or NAT-rebound peer is not misidentified.

**Both implementations must move together** for any change to this SIP, per
SIP-1: it is entirely wire.

## Security considerations

**MAC1 authenticates knowledge of the server's public key, not the caller's
identity.** Anyone holding the server's public key can compute a valid MAC1 with
a freshly generated keypair. That is the intended property: MAC1 decides whether
the server responds at all, and SIP-2, SIP-3 and SIP-8 decide who the caller is
and whether they may proceed. Treating a passed MAC1 as authorisation would be a
serious error.

**The server's public key is a shared secret in one narrow sense.** It is public
in every ordinary meaning, but the invisibility property rests on an attacker not
having it. A deployment that publishes the key gives up silence and keeps every
other guarantee.

**An Initial is replayable inside the timestamp window**, as specified above. The
gain to an attacker is one Diffie-Hellman and one handshake that times out.

**A small-order client key forges MAC1 outright** if the non-contributory check
is missing, because the shared secret is then all zeros and predictable without
any knowledge of the server. Step 5 is the only thing preventing this for a
deployment with no whitelist. It is worth being blunt: the check was added after
the fact, and until it was, silence rested entirely on SIP-8's whitelist for the
deployments that had one and on nothing at all for the deployments that did not.

**The envelope is not confidential.** Both public keys, the timestamp and the
nonce are plaintext, and an observer can identify a persistent client by its
X25519 key across connections and networks. SIP-3's optional Ed25519 field is
the part a caller can withhold; the X25519 key is not withholdable.

**Timing.** MAC comparisons MUST be constant-time. The validation order leaks
coarse information by construction — a caller can learn that it passed the
whitelist by observing that the server spent time on a DH — but this requires
the attacker to already hold the server's public key, and what it reveals is
what the whitelist would reveal anyway.

## Reference implementation

- squic v0.15.0 — `src/mac.rs` (envelope constants, MAC1, the replay window),
  `src/conn.rs` (`ClientSocket::build_initial`, `ServerSocket::validate_and_strip`),
  `src/crypto.rs` (the seed derivations and the non-contributory check).
- squic-go v0.60.0 — `mac.go` and `conn.go`, with the same structure and the
  same field names.

The two are held to the same wire behaviour by the cross-implementation test
described in SIP-2 (`scripts/cross_peerkey_test.sh` in squic-go), which runs the
full server/client matrix across both implementations and asserts they agree on
the key each envelope carried. It exercises the layout, the MAC1 input ordering
and the derivation check across the language boundary, and runs in CI on both
repositories.
