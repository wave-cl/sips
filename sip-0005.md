## Abstract

An identity leaves a message for another at an exchange; the recipient collects
it when next connected. Both ends are authenticated by their connection. The
payload is sealed to the recipient so the exchange cannot read it.

## Motivation

Two identities that both know each other's keys still cannot exchange anything
unless they are online simultaneously, and sQUIC's silent-server property means
neither can even reach the other without prior knowledge. An exchange both can
reach solves the scheduling problem without either running a reachable service.

## Specification

*Sketch. Not ready to implement from.*

Sender opens a connection, names the recipient by Ed25519 identity, and
supplies a sealed payload. The exchange stores it against the recipient and
acknowledges. The recipient, on a later connection, lists and collects.

Sealing uses X25519 ECDH between sender and recipient keys with an AEAD, so the
exchange handles ciphertext only. The sender derives the recipient's X25519 key
from its Ed25519 identity — the conversion the exchange cannot run in reverse
runs perfectly well forwards.

Open questions this SIP must settle before Proposed:

- **Quotas and TTL.** Without both this is free storage for anyone who can
  register. Per-identity byte limits, message counts and an expiry.
- **Delivery semantics.** At-least-once with explicit acknowledgement, or
  delete-on-read. Whether the sender learns that collection happened.
- **Ordering.** Whether messages are a queue or a set.
- **Size.** A ceiling low enough that the exchange is not a file host. SIP-5 is
  a mailbox, not a CDN, and the number should make that structural.

## Rationale

Sealing to the recipient rather than trusting the exchange follows from the
premise of the whole stack: the exchange is a rendezvous point, not a confidant.

## Compatibility

New protocol. Requires SIP-2.

## Security considerations

**The exchange sees metadata even though it cannot read payloads.** Sender,
recipient, size and time, for every message. Over a period that is a social
graph with timing. Sealing the payload does not conceal that anyone is talking
to anyone, and this SIP must not be described as private communication.

**Storage is attacker-reachable** — see quotas above.

**No forward secrecy** if sealing uses long-lived identity keys directly. A
recipient key compromised later decrypts every message ever stored under it.
Whether to introduce ephemeral keys is the main cryptographic decision
outstanding.
