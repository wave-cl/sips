Author: Colin Lyons <wave-cl@pm.me>
Status: Active
Type: Standards Track
Layer: Exchange
Created: 2026-08-24
Requires: 2, 3

## Abstract

An identity leaves a message for another at an exchange; the recipient collects
it when next connected. Both ends are authenticated by their connection, so
nothing is signed. The payload is sealed to the recipient with a fresh ephemeral
key, so the exchange handles ciphertext only and a later compromise of the
sender's key reveals nothing.

## Motivation

Two identities that both know each other's keys still cannot exchange anything
unless they are online simultaneously, and sQUIC's silent-server property means
neither can even reach the other without prior knowledge. An exchange both can
reach solves the scheduling problem without either running a reachable service.

Naming is the same problem the beacon had: a mailbox belongs to an identity, and
the exchange must know which identity is acting without having registered it
first. SIP-3 supplies that, which is why this SIP now `Requires: 3` — the
original draft predated it and assumed SIP-2 alone.

## Specification

All integers are unsigned big-endian. Every operation is bound to the caller's
transport identity (SIP-3): a **sender is whoever connected**, and a **mailbox
belongs to whoever can connect as its key**. A connection carrying no identity
has no mailbox and cannot send; it MUST be refused rather than served an empty
result.

### Sealing

```
shared = X25519(ephemeral_secret, recipient_x25519)
okm    = SHA-512(SEAL_CONTEXT || ephemeral_pub || recipient_x25519 || shared)
key    = okm[0..32]      nonce = okm[32..44]
ciphertext = ChaCha20-Poly1305(key, nonce, plaintext)
```

`SEAL_CONTEXT` is the ASCII string `sqex-mailbox-v1`. `recipient_x25519` is the
forward derivation of the recipient's Ed25519 identity — the conversion the
exchange cannot run in reverse runs perfectly well forwards.

The sender MUST generate a **fresh ephemeral keypair for every message** and
MUST NOT use its long-lived identity key in this exchange. The nonce is derived
rather than transmitted: a fresh ephemeral key makes the message key unique, so
there is nothing for a nonce to disambiguate. Both sides MUST reject a
non-contributory (small-order) exchange.

### Messages

```
Send        | type=0x01 | recipient[32] | ephemeral[32] | ciphertext      |
SendAck     | id: u64   | now: u64      |
List        | (empty body)              |
Listing     | now: u64  | count: u32    | count × Entry                   |
Entry       | id: u64   | sender[32]    | received: u64 | len: u32        |
Fetch       | type=0x03 | id: u64       |
Fetched     | found: u8 | sender[32]    | received: u64 | ephemeral[32] | ciphertext |
Delete      | type=0x04 | id: u64       |
Deleted     | deleted: u8               |
Status      | type=0x05 | id: u64       |
StatusReply | state: u8 | received: u64 | collected: u64 | now: u64       |
```

`state` is 0 unknown, 1 waiting, 2 collected. `sender` in an `Entry` or
`Fetched` is the identity **the exchange observed connecting** — see Security
considerations; it is not a cryptographic fact.

### Delivery

Delivery is **at-least-once**. A recipient lists, fetches, then deletes by id.
Fetching MUST NOT remove the message: a connection lost mid-collection must cost
a retry, never a message. Deleting is what completes collection.

Messages are a **queue**: `Listing` returns them oldest first by arrival.

### Collection is visible to the sender

Deleting drops the payload but MUST retain a record — id, sender, recipient and
the time of collection — until the message's TTL expires. A sender MAY ask
`Status` about a message **it sent**; any other caller MUST receive `unknown`,
which is the same answer given for a message that never existed.

### Quotas

An exchange MUST bound storage. This SIP fixes:

| Limit | Value |
|---|---|
| Plaintext per message | 32 KiB |
| Messages waiting per recipient | 64 |
| Stored bytes per recipient | 1 MiB |
| TTL (message and its collection record) | 7 days |

A send that would exceed a recipient's message count or byte allowance MUST be
refused and distinguishable from a malformed request. Because the exchange
cannot see plaintext, it enforces the size limit on **ciphertext**, allowing for
the AEAD tag.

The numbers are deliberately small. A mailbox is a rendezvous for messages, not
a file host, and the ceiling should make that structural rather than a matter of
operator restraint.

## Rationale

**Why seal to the recipient rather than trust the exchange.** The premise of the
whole stack: the exchange is a rendezvous point, not a confidant.

**Why an ephemeral sender key.** The draft left forward secrecy as "the main
cryptographic decision outstanding". Three options were weighed. Static-static
ECDH between the two identity keys is simplest and authenticates the sender in
the crypto, but has no forward secrecy in either direction — either key
compromised later opens every message. Published one-time prekeys (X3DH-style)
give real forward secrecy on both sides, at the cost of prekey upload, serving,
and exhaustion policy, and make the exchange trusted to hand out honest prekeys.
The ephemeral-sender construction was chosen: it costs nothing beyond one
keypair per message, keeps the sender's long-lived key out of the exchange
entirely, and bounds the recipient-compromise window by the TTL. Its price is
stated plainly below.

**Why fetch-then-delete rather than delete-on-read.** Delete-on-read is
self-cleaning but loses a message whenever the network fails between the
exchange sending and the recipient storing. Requiring an explicit delete makes
the failure mode a retry. The cost — a recipient that never deletes holds its
allowance until TTL — is bounded by the quota, which is why both exist.

**Why collection is visible to the sender.** This is a genuine trade, taken
deliberately. Knowing whether what you left was taken is useful for retry and
for not re-sending; the cost is that it discloses recipient behaviour. It is
scoped as tightly as it can be: only the sender of a specific message, only for
that message, and never as a way to enumerate. An exchange that considers even
this too much may report `collected` as `waiting`, at the cost of conformance.

**Why a queue rather than a set.** Order of arrival is information the exchange
has for free and a recipient usually wants; discarding it would be a choice, not
a simplification.

## Compatibility

New protocol; nothing to break. Requires SIP-2 and SIP-3 — the latter is what
lets an exchange serve identities it has not registered, which is the difference
between a mailbox anyone can use and one with a membership list.

## Security considerations

**The exchange sees metadata even though it cannot read payloads.** Sender,
recipient, size and time, for every message. Over a period that is a social
graph with timing. Sealing the payload does not conceal that anyone is talking
to anyone, and **this SIP must not be described as private communication.**

**The ciphertext does not prove who sent it.** This follows directly from the
ephemeral-sender construction: the sender's long-lived key is not in the ECDH,
so the recipient learns the payload but not, cryptographically, its author. The
`sender` reported alongside is the **exchange's observation of a connection** —
the same class of claim as SIP-4's `last_seen`, and equally dependent on the
exchange being honest. An application that needs end-to-end sender
authentication MUST sign inside the plaintext; this SIP deliberately does not,
because doing so would put a signature on every message for the benefit of the
applications that need one.

**Forward secrecy is one-sided.** A later compromise of the *sender's* identity
key decrypts nothing. A compromise of the *recipient's* key opens every message
still stored under it — which the TTL bounds, and nothing else does. Deployments
where that residual window matters want the prekey construction rejected above,
and should say so rather than assume this one covers them.

**Storage is attacker-reachable.** Anything that can connect can consume a
recipient's allowance, and under SIP-3 that is anyone. The quotas are the whole
defence: they are per-recipient, so filling one mailbox cannot deny another, and
a recipient can always recover its allowance by collecting. There is no
per-sender limit, so a determined sender can occupy a target's mailbox until
TTL; an exchange that needs more than this should gate sending on its own
policy.

**Collection timing is disclosed to senders**, by design — see Rationale. A
recipient cannot suppress it.

**Deletion is not erasure.** Collecting drops the payload, but the record that a
message existed, from whom and when, survives until TTL.

## Reference implementation

Shipped in [sqex](https://github.com/wave-cl/sqex) v0.4.0, on squic v0.15.0
(SIP-3):

- `sqex-proto::mailbox` holds the layouts above and the sealing. `sqexd` links
  that module but never calls `seal` or `open` — the exchange handles ciphertext
  only, and the code layout says so.
- `sqexd::mailbox` stores messages keyed by recipient identity, enforces the
  quotas, expires on every operation (no background task), and keeps the
  collection record after the payload is dropped.
- Routes: `POST /mailbox/{send,list,fetch,delete,status}`, each refusing a
  connection with no advertised identity.
- `sqex mail send|list|fetch|delete|status|collect`. `collect` fetches, prints
  and deletes each waiting message in order, deleting only once the plaintext is
  in hand.

Integration tests cover two unregistered identities exchanging a message without
ever being connected simultaneously, the sender seeing collection, a third
identity being unable to list, fetch, delete or ask after someone else's
message, anonymous connections having no mailbox at all, and oversized or
malformed sends being refused.

**Known limitation: storage is in memory**, so a restart drops undelivered mail.
Unlike SIP-4, where in-memory state is principled — a restart is an honest gap
in observation — here it is simply unfinished. Persistence is the next step and
does not require a wire change.
