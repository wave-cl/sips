## Abstract

A blob is a file — an image, a video, a voice note, anything — stored at an
exchange in independently sealed chunks, named by the hash of its ciphertext,
and encrypted under a key the exchange never receives. A message carries a
**reference**: the blob's name, its key, its size and shape, and a small preview
that renders before a byte of the file has been fetched. A blob belongs to the
channels it has been attached to and is pruned on their retention windows, which
lets the exchange expire an attachment and the message that points at it
together without ever being able to read the pointer.

## Motivation

SIP-16 caps an entry body at 32 KiB, and that cap is not arbitrary: there is no
streaming path in either direction in this stack, so a `Post` has to fit inside
one request body whole. A hundred-megabyte video is four thousand times that.

Putting the file in the message is therefore not available, and the question is
what to put there instead. Three things make the answer more than "a URL".

**It has to be encrypted, and the key has to travel with the reference.** A link
to a file the exchange can read would undo SIP-17 for the part of a conversation
most likely to matter. If the key is inside the sealed message body, anyone who
can read the message can read the file and nobody else can — including the
exchange, which stores the bytes.

**It has to survive being forwarded.** A message forwarded into another channel
should not re-upload a hundred megabytes. If the reference carries the key, a
forward is a copy of forty or so bytes and the second channel's members read the
same stored blob.

**It has to expire without the exchange being able to read the reference.** This
is the awkward one. The natural rule — delete a blob when the last message
referencing it is pruned — requires counting references the exchange cannot see,
because in a private channel they are inside ciphertext. So the lifetime has to
be arranged some other way, and this SIP arranges it by attaching blobs to
channels rather than to messages.

## Specification

All integers are unsigned big-endian. Every operation is bound to the caller's
transport identity (SIP-3). A connection carrying no identity has no membership
and MUST be refused.

`BLOB_CONTEXT` is the ASCII string `sqex-blob-v1`.

### Chunks, keys and names

A blob is split into chunks of `CHUNK` bytes; the last chunk may be shorter and
MUST NOT be empty unless the blob is empty. Each is sealed independently under
one key for the whole blob:

```
key      = 32 bytes, generated uniformly at random, per blob
nonce    = chunk_index(8) || 0(4)
sealed_i = ChaCha20-Poly1305(key, nonce(i), plaintext_i)
blob_id  = SHA-256(BLOB_CONTEXT || sealed_0 || sealed_1 || ... || sealed_n-1)
```

`chunk_index` counts from 0. `size` is the plaintext length; the stored length is
`size + 16 × chunks`.

**The key MUST NOT be sent to the exchange, and an implementation MUST NOT
provide any operation that would transmit it.** No message in this SIP has a
field for it and none may be added: a blob is uploaded already sealed, and the
key reaches its readers inside the attachment reference below, which travels in
a message the exchange cannot read. This is SIP-13's rule about a room secret,
restated here because it is the load-bearing property of the whole document —
everything else is bookkeeping about bytes the exchange is holding blind. A
convenience endpoint that accepted a key, for server-side thumbnailing or
scanning or transcoding, would break this SIP while conforming to every other
rule in it.

Independent per-chunk sealing is what lets a client verify and render as it goes
— a video plays before it has finished downloading, and a chunk that fails to
open is one chunk to re-request rather than a whole file to discard.

The name is the hash of the **ciphertext**, not of the plaintext, and that choice
does a specific piece of work: the exchange can verify the name it is asked to
store. It hashes the bytes it received, compares, and refuses a mismatch, so
nobody can claim a name they do not have the bytes for, and a fetched blob is
self-verifying against a name that arrived inside a sealed message.

### Uploading and fetching

```
Begin   | type: u8 = 0x01 | channel[32] | size: u64 | chunks: u32
        | expires_after: u32 |
Put     | type: u8 = 0x02 | upload: u64 | index: u32 | sealed |
Commit  | type: u8 = 0x03 | upload: u64 | blob[32] |
Abort   | type: u8 = 0x04 | upload: u64 |
Head    | type: u8 = 0x05 | blob[32] |
Get     | type: u8 = 0x06 | blob[32] | index: u32 |
Attach  | type: u8 = 0x07 | channel[32] | blob[32] | expires_after: u32 |
Detach  | type: u8 = 0x08 | channel[32] | blob[32] |
Limits  | type: u8 = 0x09 |

Begun    | upload: u64 | now: u64 |
Ack      | now: u64 |
Committed| stored: u8 | blob[32] | now: u64 |
Headed   | found: u8 | size: u64 | chunks: u32 | attached: u64 | now: u64 |
Chunk    | found: u8 | index: u32 | len: u32 | sealed |
Bounds   | chunk: u32 | max_blob: u64 | max_chunks: u32 | now: u64 |
```

Endpoints, each refusing a connection with no advertised identity:
`POST /blob/{begin,put,commit,abort,head,get,attach,detach,limits}`.

`Limits` reports what this exchange will accept, and is answerable to anybody.
It exists because `CHUNK` is a recommended value rather than a fixed one — an
exchange that has not raised its request cap conforms by choosing a smaller one
— and a client therefore has to ask rather than assume. Without it that
instruction cannot be followed: a client picking 256 KiB against an exchange
holding a uniform 64 KiB limit fails on its first `Put` with nothing to tell it
why, which is a bad failure for the most common misconfiguration this SIP has.

`Begin` requires the caller to be a member of `channel` and reserves an upload
against that channel's blob quota. `Put` writes one chunk; chunks MAY be sent in
any order and MAY be repeated, and a repeat overwrites. `Commit` assembles what
was received, hashes it, and **MUST** refuse a result that does not equal the
claimed `blob_id`, answering `stored: 0` — distinguishably from a malformed
request. An upload with a missing chunk is refused the same way.

A `Commit` naming a `blob_id` the exchange already holds succeeds without storing
a second copy and attaches the existing blob to the channel. The uploader
therefore cannot tell whether the bytes were already there; see Security
considerations.

`Get` returns one chunk to a member of any channel the blob is attached to, and
to anybody at all if one of those channels is public. `Head` answers the same
audience and reports whether the blob is still stored, which is how a client
distinguishes an attachment that has been pruned from one that is merely slow.

`Attach` adds an existing blob to a second channel: the caller MUST be a member
of that channel and MUST already be able to fetch the blob. This is what a
forward does. It costs the reference, not the file. The new attachment carries
its own `attached` time and its own `expires_after`, so a blob forwarded into a
channel with a longer window lives longer there, and one forwarded into a
disappearing message goes when that message does.

`Detach` removes an attachment. The caller MUST be the account that uploaded the
blob into that channel, or an admin of it. Detaching from the last channel
deletes the blob outright.

Detach exists because **deleting a message must delete what it carried**.
Redacting an entry (SIP-16) removes the body, and the body is where the
reference lives — so the exchange, which cannot read the reference, has no way
to know a blob just lost its last mention. Only the redacting client knows,
because only it can read the message it is deleting, so it issues the detach
alongside the redaction. This is the one place the exchange's inability to read
costs an extra round trip rather than costing nothing, and it is worth the
trade: the alternative is an exchange that can see which entries have
attachments.

An incomplete upload is discarded after `UPLOAD_TTL`. `Abort` is a courtesy that
returns the quota sooner.

### Lifetime

A blob is not owned by a message. It is **attached to channels**, and each
attachment carries the time it was made and an `expires_after` in seconds. An
attachment expires at

```
attached + min(expires_after, channel retention_secs)     when expires_after > 0
attached + channel retention_secs                         when expires_after = 0
```

and a blob with no attachments left is deleted.

That gives the property the motivation asked for. A message and its attachment
are posted within moments of each other and age against the same window, so they
expire together, and the exchange arrives at that without ever reading a
reference it could not read. Forwarding into a channel with a longer window
extends the blob's life honestly, because someone there can still see the message
that points at it.

An exchange MUST prune blobs on the same schedule as entries, and MUST NOT rely
on a member touching the channel.

**`expires_after` is how a disappearing message's attachment disappears with
it.** SIP-16 lets an entry carry its own timer, and without a matching one here
the entry would be pruned on schedule while its image stayed fetchable by every
member for the rest of the channel's retention — which is the case people most
want a disappearing message for, failing in the way least likely to be noticed.
The exchange cannot infer it, because the reference is inside the entry it
cannot read, so the uploader declares it: a client posting an entry with
`expires_after` **MUST** `Begin` or `Attach` its blobs with an `expires_after`
no greater than the entry's.

That is a requirement on the client and not something an exchange can check,
which puts it in the same family as pairing a redaction with a detach. The
asymmetry is the same and so is the reason for it.

### The attachment reference

This is what a SIP-19 message carries. It is defined here because it names
things only this SIP knows.

```
Attachment | kind: u8 | blob[32] | key[32] | size: u64 | chunks: u32
           | mime_len: u8  | mime
           | meta_len: u16 | meta
           | prev_len: u16 | preview |
```

| `kind` | Meaning | `meta` |
|---|---|---|
| 0x01 | Image | `width: u16 \| height: u16` |
| 0x02 | Video | `width: u16 \| height: u16 \| duration_ms: u32` |
| 0x03 | Voice note | `duration_ms: u32 \| bars: u8 \| level: u8 × bars` |
| 0x04 | File | `name_len: u8 \| name` |

A `kind` a reader does not know MUST be treated as `0x04`, a file with opaque
`meta`: it can still be named, sized, fetched and saved. This keeps the same
promise SIP-19 makes about message types, at the one place inside a message
where a new kind is most likely to be wanted.

`preview` is a still image — a thumbnail, a poster frame — of at most `PREVIEW`
bytes, rendered while the blob is fetched or in place of it. It is optional and
`prev_len` MAY be 0.

A voice note's `bars` are its waveform, so it draws before any audio is fetched.
Each `level` uses **SIP-15's scale**: half a decibel below full scale per unit,
255 for digital silence. Reusing it rather than inventing a second loudness
encoding means one function in a client renders both a live call and a voice
note.

Note that the entry cap binds here. Four attachments each carrying a full
`PREVIEW` will not fit in a 32 KiB entry alongside any text, and an exchange will
refuse the entry rather than truncate it. A client MUST size previews to fit what
it is actually sending.

### Media

An exchange stores bytes and does not transcode, inspect, re-encode or scan.
`mime` is the sender's declaration and travels for the reader's benefit.

Voice notes **SHOULD** be Ogg-encapsulated Opus (RFC 7845), mono, RECOMMENDED
24 kbit/s — the rate the reference voice implementation settled on. A voice note
is a file and not a stream: it carries no SIP-15 framing, no timestamps and no
comfort frames. SIP-14 made this argument in passing and it holds — a file
transfer has no timestamp and wants none.

Images and video have no required format. A client SHOULD prefer formats it can
expect a peer to decode and SHOULD state the true `mime`.

### Limits

Recommended values:

| Limit | Value |
|---|---|
| `CHUNK` | 256 KiB |
| `MAX_BLOB` | 100 MiB (400 chunks) |
| `PREVIEW` | 8 KiB |
| Attachments per message | 4 |
| `mime` | 128 bytes |
| Blob bytes per channel | 2 GiB |
| Channels one blob may be attached to | 64 |
| Concurrent uploads per identity | 8 |
| `UPLOAD_TTL` | 1 hour |

An overrun MUST be refused distinguishably from a malformed request.

`CHUNK` at 256 KiB is larger than the 64 KiB request cap the rest of the
exchange uses, and an implementation of this SIP has to raise that ceiling on
these routes and only these. The size was chosen between two costs: at 64 KiB a
hundred-megabyte video is 1 600 requests, and at 1 MiB a single request no longer
sits comfortably inside a QUIC stream receive window that is 1 MiB by default in
the reference transport. 256 KiB gives 400 requests for the largest permitted
blob, which is a few seconds of pipelining on any usable connection.

## Rationale

**Why the id is over ciphertext rather than plaintext.** Hashing the plaintext
would be the more usual content address, and it cannot be checked by a party who
holds only ciphertext — which is every exchange. Hashing what is stored lets the
exchange verify the name at `Commit`, so an identifier cannot be squatted and a
fetched blob verifies against a name that arrived sealed. The cost is that two
identical files uploaded with different keys are different blobs.

**Why a random key per blob and not convergent encryption.** Deriving the key
from the plaintext hash would deduplicate globally: the same file uploaded by
two people would be one blob. It was rejected, because it also lets anyone
holding a candidate file confirm whether it is stored, which is precisely the
attack that matters for images. Forwarding still deduplicates under a random key,
because the key travels inside the reference — so the case that actually recurs
in a chat system is covered, and the case that leaks is not offered.

**Why the reference is in the message rather than in the entry header.** Putting
it in the header would let the exchange manage blob lifetime by counting real
references. It would also tell the exchange which entries have attachments, how
many, of what kind and what size, and would put the key somewhere it must not
be. Attaching to channels achieves the lifetime management with a coarser rule
and no disclosure.

**Why a preview is inline and not a second blob.** A thumbnail as its own blob
would be tidier and would mean an extra round trip before anything is on screen
— for every image in a scrollback. Eight kilobytes inside the message is the
difference between a conversation that renders at once and one that renders in
pieces. The larger cost, that four attachments no longer fit one entry, is real
and is stated rather than designed around.

**Why chunks are sealed separately rather than the whole blob at once.** One
AEAD over a hundred megabytes cannot be verified until the last byte arrives,
cannot be played while it downloads, and forces a client to hold the whole thing
in memory to check it. Per-chunk sealing costs 16 bytes per 256 KiB — about
0.006% — and buys progressive rendering and cheap retries.

**Why the exchange refuses on hash mismatch instead of storing what it was
sent.** A blob that does not match its name is unreferenceable by anything and
would occupy quota until it expired. Checking at `Commit` is one hash over bytes
already on disk.

**Why no transcoding.** An exchange that re-encoded video would have to be able
to read it, which ends the encryption; would have to run media decoders on
attacker-supplied input, which is where a large share of remote code execution
historically lives; and would have to make quality decisions on behalf of people
it cannot ask. Clients encode.

## Compatibility

Purely additive on the wire: seven new routes, no change to any existing format,
and no dependency on a change to SIP-3, SIP-5, SIP-12 or SIP-13.

It is **not** additive on the exchange's request handling. `CHUNK` exceeds the
64 KiB body limit the reference implementation applies uniformly, so an exchange
adding this SIP must raise that limit on the blob routes specifically and keep
it everywhere else. An implementation that leaves the limit uniform can still
conform by choosing a smaller `CHUNK`, at the cost of more requests per blob.
`CHUNK` is a recommended value and a client discovers it with `Limits` rather
than assuming it.

A client without this SIP that receives a message containing an attachment part
ignores that part under SIP-19's rules and displays the rest, so a mixed
population degrades to text rather than breaking.

## Security considerations

**A blob is exactly as protected as the message that references it.** The key is
in the message. Anyone who can read the message can fetch and open the blob, and
membership checks on `Get` are a convenience — they stop casual enumeration and
they bound what a stranger can pull from the exchange. They are not the boundary.
The encryption is.

Read that literally, because it cuts both ways. In a **private** channel the
reference is sealed under SIP-17, so the exchange holds ciphertext and nothing
that opens it — not the key, not the media type, not the dimensions, not the
thumbnail. In a **public** channel the entry is unsealed by design, so the
reference and the key it carries sit in plaintext beside the ciphertext they
open. The blob is encrypted at rest there in the literal sense and that
encryption protects nothing from the exchange, which holds both halves. This
follows from public channels being plaintext and is not a flaw, but
"attachments are encrypted so the exchange cannot see them" is true of private
channels only, and an implementation MUST NOT say it of a public one.

**The exchange sees shape and timing.** Sizes, chunk counts, upload times, which
channel each blob is attached to, and who fetched what and when. A hundred-
megabyte upload followed by a message is not a subtle event, and file size is
often identifying on its own.

**`mime` is a claim by the sender and nothing more.** A receiver MUST NOT
dispatch on it beyond choosing how to display, MUST NOT execute a blob, and MUST
NOT hand one to a handler selected by the sender's string. Treat every blob as
hostile input to a decoder — which is what it is, and image and video decoders
are among the most attacked code any client runs.

**Deduplication on `Commit` is an existence oracle, bounded.** A `Commit` for a
blob already stored succeeds without the bytes needing to be there, so an
uploader who has a candidate file, and its exact key, can learn whether it is
already stored. The key is what bounds this: without it the ciphertext differs
and the name differs, so an attacker must already hold the exact reference —
which means they could have fetched it anyway. An exchange concerned about the
residual MAY require every chunk to be uploaded regardless.

**`Attach` widens an audience deliberately, and there is no way back.** A member
of a private channel can attach any blob they can read to any other channel they
belong to, including a public one, and the blob is then fetchable by anybody.
This is the same exposure as a member forwarding a message, and it is
unpreventable for the same reason: they hold the plaintext. It is worth naming
because the mechanism makes it a single request rather than a re-upload.

**A blob outlives a redaction unless somebody detaches it.** The exchange cannot
tell that a redacted entry referred to a blob, so nothing automatic happens. A
client that redacts and does not detach has removed the words and left the
photograph fetchable by every member for the rest of the retention window, which
is very likely the opposite of what the person asked for. An implementation
SHOULD treat the two as one operation and SHOULD retry a failed detach.

**Pruning is on attachment age, not on reference count.** A blob can outlive
every message that mentioned it — attached to a channel with a long window,
referenced only from one with a short one — and remain fetchable by that
channel's members, who can no longer see the message. It can also be pruned
while a message still points at it, when a client keeps a local copy of the
message past retention. Clients MUST handle `found: 0` from `Head` and `Get` as
an ordinary outcome.

**Upload quota is a denial-of-service surface.** Two gigabytes per channel and
eight concurrent uploads per identity, across however many channels an identity
belongs to, is a great deal of disk an unprivileged member can consume. An
exchange SHOULD apply a per-identity ceiling across all channels as well, which
this SIP does not specify because it is an operator's policy rather than a
matter of interoperation.
