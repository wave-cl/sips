## Abstract

An exchange lists the exchanges it federates with: each peer's key and, where
the operator recorded one, the domain it is reached by. A client that has
reached one exchange can find the others from it, and pins each by SIP-33
before trusting a word of the list.

## Motivation

Reaching an exchange takes a domain, and SIP-33 turns a domain into a pinned
key. What it does not answer is *which* domains: a person who joined one
exchange learns of the next by being told, out of band, by somebody. The
exchanges themselves already know each other -- SIP-35 replicates between
them and SIP-39 bridges calls between them, over a peer list each operator
keeps -- and that list is the one thing here that names other exchanges at
all.

Making it readable turns one exchange into a way to the rest, which is how a
federation stops being a set of servers somebody has to be introduced to.

## Specification

All integers are unsigned big-endian.

### The route

`GET /exchange/peers`, open to any caller, answers:

```
Peers | type: u8 = 0x02 | count: u16 | entry * count |
entry | key[32] | domain_len: u8 | domain |
```

`key` is the peer's SIP-9 exchange key. `domain` is UTF-8, and empty (length
0) when the operator recorded none: a peer may be known by key alone. When
present it MUST be a valid DNS name in lowercase -- the form SIP-33 discovers
-- and an exchange MUST NOT list a label that is not one. `count` is bounded
by the exchange's own peer cap (SIP-39's), which is small.

The list is the exchange's *runtime* peer list -- what it will replicate
from and bridge calls to today -- and nothing else. An exchange MUST NOT list
an exchange it does not peer with, and MUST NOT list itself.

### What a client does with it

A domain from the list is a hint, and the key beside it is what the hint
must resolve to. A client that wants to reach a listed peer resolves the
domain by SIP-33 and MUST refuse the result if the discovered key is not the
listed one. A client MAY reach a listed peer by key alone, through SIP-28
resolution, when no domain was given.

A client MUST NOT connect to a listed peer on the strength of the listing,
and MUST NOT treat a listing as the peer's consent to anything: it says the
*listing* exchange peers with it, which is all the listing exchange knows.

## Rationale

**Why the peer list and not a new list.** Any other list would be a second
thing for the operator to keep, and would drift from the first. The peer
list is already what the exchange acts on; publishing it publishes a fact
rather than an intention.

**Why open to anyone.** The keys are public by construction -- SIP-33
publishes each in DNS, signed -- and the peering is observable: a replicated
channel names its origin (SIP-35), a bridged call names the other exchange
(SIP-39). Withholding the list would hide from a stranger what a member can
already see, at the cost of the one thing the list is for.

**Why a hint and a pin.** SIP-28's boundary, applied here: an exchange is
trusted for availability and never for authenticity. A dishonest exchange can
list a domain that resolves to a key that is not the listed one, and a client
that pins the listed key refuses it. It can omit a peer, which denies and does
not impersonate. It cannot make a client trust a key it did not discover.

**Why the domain is optional.** A peer is added by key (SIP-39's `peer-add`),
with a label an operator may or may not have made a domain. Requiring one
would either refuse to list peers without it -- a partial directory that says
nothing about why -- or invent one. A key alone is still a peer somebody can
reach through SIP-28.

## Compatibility

A new route; an exchange from before it answers 404 with SIP-21's
`NotFound` code, which a client reads as "no directory here". Nothing
existing changes.

## Security considerations

**The list discloses the federation graph.** Which exchanges peer with which
is now a question anyone can ask. It was already answerable by anyone who
could watch a replicated channel or place a cross-exchange call; this makes
it cheaper, and an operator who peers privately -- an exchange kept for one
organisation -- should know that its peers are readable. A future revision
could let an operator mark a peer unlisted; this one does not, because a
directory that might be partial invites a client to assume it is complete.

**A listing is not an endorsement.** Peering says two operators agreed to
carry each other's traffic. A client that presents a listed exchange as
"recommended" is saying something the exchange did not.

**Nothing here is signed** and nothing needs to be: the only claim a client
acts on is "this domain has this key", and SIP-33 signs that.

## Reference implementation

Planned: `sqex-proto::exchange::Peers`; `sqexd` serves the route from the
runtime peer list, listing a peer's label as its domain when the label is a
DNS name; `sqex peers`; sigil's *Add an exchange* dialog offers the current
exchange's peers, each added through the same SIP-33 path as one typed by
hand.
