## Abstract

> **Withdrawn.** This SIP existed to repair a shortfall in one of the two
> mechanisms SIP-2 weighed: the DCID join delivered the caller's X25519 key,
> which is not a name, and the derivation claim below turned it into one.
>
> SIP-2 adopted TLS client authentication instead. The application now receives
> the Ed25519 key directly from the handshake, so there is no shortfall left to
> repair — no claim message, no cache, and no derivation check on the
> connection path.
>
> Nothing here was found to be wrong. The derivation argument in particular
> still holds, and is worth keeping: because the X25519 secret is the Ed25519
> signing scalar, possession of one is possession of the other. Anything that
> needs to prove an Ed25519 key from an observed X25519 key can rely on it.
> What follows is retained for that reasoning and for the record.

The transport authenticates an X25519 key; the ecosystem names identities by
Ed25519 key. A caller states its Ed25519 identity and the exchange verifies the
claim by derivation — no signature, no challenge, no round trip. The result is
cached so later connections resolve with a lookup.

## Motivation

SIP-2 exposes the peer's X25519 key. Everything around it — sqns records,
sqssh authorized_keys, the base58 strings people exchange — names identities by
Ed25519 key. The exchange needs to get from one to the other.

It cannot do so unaided:

- **The reverse map is 2-to-1.** An Ed25519 public key encodes `y` plus a sign
  bit for `x`; the Montgomery form keeps only `u`, which depends on `y` alone.
  Two Ed25519 keys differing in exactly one bit — the top bit of byte 31 —
  produce byte-identical X25519 keys. Reversing gives two candidates and no way
  to choose.
- **Many callers have no Ed25519 key at all.** A sQUIC client configured
  without a persistent identity generates a random X25519 keypair. There is no
  preimage to recover because none ever existed.

So the caller must say who it is. The question this SIP answers is what it takes
to believe them, and the answer is: less than you would expect.

## Specification

### Registration

The caller sends its Ed25519 public key. The exchange accepts the claim if and
only if:

1. the key decompresses to a valid Edwards point;
2. `ed25519_public_to_x25519(claimed)` equals the transport-reported peer key
   from SIP-2, compared in constant time;
3. neither key is of small order (below).

No signature is sent. None is needed — see Rationale.

### Why the derivation check suffices

Both keys share one scalar. The X25519 secret is `clamp(SHA-512(seed)[..32])`,
which is precisely the Ed25519 signing scalar `a`; the public keys are `a·B` in
Edwards form and `a·u` in Montgomery form, and the birational map carries one to
the other.

MAC1 already proved the caller holds the scalar for the observed X25519 key. If
the claimed Ed25519 key maps to that same key, the caller holds its scalar too,
and can therefore sign as it. The connection has already done the work a
signature would repeat.

### Rejecting small-order points

Implementations MUST reject a claimed or observed key that is of small order,
and MUST reject a Diffie-Hellman result of all zeros.

This is not defensive tidiness. Diffie-Hellman against the zero point yields an
all-zero shared secret whatever the other key is — a value the caller knows in
advance without knowing anything about the peer. An implementation that omits
this check will verify a MAC computed by someone who has never seen its public
key. Where a whitelist is enforced the damage is bounded, because the degenerate
key will not be listed; where it is not, the silent-server property is simply
gone.

The same check belongs in the transport, and its absence there is being tracked
separately.

### Caching

On a successful claim the exchange SHOULD cache `x25519 -> ed25519`. Later
connections then resolve by lookup, with no claim message and no curve
arithmetic on the connection path.

The cache is an index, not a security boundary — every entry in it was verified
by derivation when written, and any entry could be recomputed from the claim.
Losing it costs a round trip, not correctness. Implementations MAY bound it by
size or age and MAY discard it entirely on restart.

An exchange MAY instead compute both candidate Ed25519 keys from an observed
X25519 key — flip the top bit of byte 31 — and look each up among identities it
already knows. That avoids the claim message for known callers, at the cost of
two lookups and no answer at all for callers it has not seen.

### Two spellings of one identity

Because two Ed25519 keys map to one X25519 key, an identity has a second
encoding that converts identically. This is not an authentication break — the
scalar is still required — but it means a key compared as base58 and a key
compared after conversion can disagree.

Implementations MUST canonicalise: store and compare the Ed25519 key exactly as
claimed, and never treat the X25519 key as an identity.

### Expiry and rotation

Expiry is exchange policy, not part of the claim: an entry is a cache of a fact
that can be re-derived, so evicting it is free. Implementations SHOULD evict
identities not seen for some period.

An identity that rotates under sqns's delegation model presents a different
Ed25519 key and therefore a different X25519 key, and simply makes a new claim.
The exchange SHOULD retain the predecessor so a consumer asking about the old
identity learns it was superseded rather than that it went quiet. **This SIP
does not verify rotation** — confirming a successor was issued by the same
identity requires consulting sqns, and is left to a future SIP.

### Unregistered callers

A caller that makes no claim is still authenticated as an X25519 key. Services
MAY serve such callers where no name is needed. They MUST NOT be presented as an
Ed25519 identity.

## Rationale

**Why no signature.** An earlier draft of this SIP specified one, over a
domain-separated message binding both keys, with an expiry and replay
protection. All of it was redundant. The signature would have proven possession
of the scalar; MAC1 proved possession of the scalar. The premise of sqex is that
a connection is already an authentication, and putting a signature at the door
would have contradicted it in the first feature.

**Why the caller states its identity rather than the exchange deriving it.**
Because deriving it is ambiguous — two candidates — and because for ephemeral
clients there is nothing to derive. A claim also carries intent: the caller
asked to be known by that name, which no amount of arithmetic recovers.

**Why cache rather than recompute.** One curve operation per connection is not
expensive, but it is unnecessary, and the mapping is stable for the life of the
key. The cache is the obvious optimisation and carries no risk precisely
because it holds nothing that cannot be recomputed.

## Compatibility

New protocol. Requires SIP-2, without which the exchange cannot see the peer
key to compare against.

## Security considerations

**The derivation check is the whole mechanism.** Omit it and any caller can
claim any identity whose public key it can read, which is all of them. There is
no second line of defence.

**Small-order points**, as above. This is the check most likely to be skipped
and the most damaging to skip.

**The X25519 secret is signing-equivalent to the Ed25519 private key.** Both use
the same scalar, and an Ed25519 signature needs only the scalar — the seed is
required for deterministic nonces, not for validity. Anyone obtaining the
derived X25519 secret can forge signatures under the identity. Hashing the seed
protects the seed; it does not protect the identity. The transport holds this
secret for the life of every connection, and it deserves the care given to a
signing key.

**Loss of an identity key is unrecoverable here.** This SIP offers no
revocation. sqns's identity/service split exists for exactly this reason, and an
exchange SHOULD prefer that callers bind service keys rather than identity keys.

**Privacy.** The cache maps long-lived public identities to connection times and
source addresses. SIP-4 turns that into a disclosure; here it is an internal
structure, but it is the same data.
