## Abstract

The transport proves an X25519 key; the ecosystem names identities by Ed25519
key. This SIP defines a one-time registration that binds the two, after which
every subsequent connection from that identity is authenticated by the
transport alone, with no signature and no authentication round trip.

## Motivation

SIP-2 exposes the peer's X25519 key. Every service around it — sqns records,
sqssh authorized_keys, the base58 strings a person copies and pastes — names
identities by their Ed25519 key. `ed25519_public_to_x25519` runs one way only,
so an exchange holding an X25519 key cannot say which Ed25519 identity it
belongs to.

An exchange could convert every identity it knows about and match forward. That
works, and it is what sqsshd's whitelist already does, but it scales with the
number of known identities and answers nothing about a caller it has not been
told of.

Binding the pair once, with a signature the identity can produce while its key
is briefly available, converts an O(n) search into a lookup and lets the
exchange name callers it has never been configured with.

## Specification

### Registration

The client connects and sends a registration containing its Ed25519 public key
and a signature. The exchange knows the X25519 key already, from SIP-2.

The signed message is domain-separated and binds the two keys together:

```
"sqex-binding-v1" ‖ ed25519_pubkey ‖ x25519_pubkey ‖ expires_at
```

| Field | Width | Notes |
|---|---|---|
| context | 15 | ASCII `sqex-binding-v1`, not length-prefixed |
| ed25519_pubkey | 32 | the identity being claimed |
| x25519_pubkey | 32 | MUST equal the key the transport reports |
| expires_at | 8 | big-endian u64, seconds since the Unix epoch |

The exchange MUST reject the registration unless all of:

- the signature verifies under `ed25519_pubkey`;
- `x25519_pubkey` equals the transport-reported peer key for this connection;
- `ed25519_public_to_x25519(ed25519_pubkey)` equals `x25519_pubkey`;
- `expires_at` is in the future and no more than 365 days ahead.

The third check is the substantive one. Without it a caller could bind an
Ed25519 key it controls to an X25519 key it does not, or bind someone else's
identity to its own connection.

### Authentication after registration

Once bound, a connection is authenticated by looking its X25519 key up in the
binding table. No signature is sent, no challenge is issued, no round trip is
spent. This is the point of the mechanism.

An expired binding MUST NOT authenticate. The exchange SHOULD retain it briefly
so it can distinguish "expired, re-register" from "never seen".

### Re-registration and rotation

An identity MAY re-register at any time, replacing its binding and extending
expiry.

Where an identity has rotated under sqns's delegation model, the successor is a
different Ed25519 key and therefore a different X25519 key, and a new
registration is required. The exchange SHOULD record the predecessor so that a
consumer asking about the old identity learns it was superseded rather than
that it went quiet — the same distinction sqns already draws between a retired
key and an absent one.

**This SIP does not verify rotation.** An exchange that wants to confirm the
successor really was issued by the same identity must consult sqns; how it does
so is left to a future SIP rather than guessed at here.

### Unregistered callers

A caller with no binding is still authenticated as an X25519 key. Services MAY
accept such callers for operations that do not need a name. They MUST NOT be
presented as an Ed25519 identity.

## Rationale

**Why sign at all, when the transport authenticates?** Because the transport
authenticates the wrong key. The signature exists once, to cross a gap the
transport cannot: proving that whoever holds this X25519 key also holds a
particular Ed25519 key. After that the transport is sufficient, forever.

**Why include `x25519_pubkey` in the signed message when it is derivable?**
Because deriving it is the exchange's check, not the signer's claim. Signing
over both makes the binding explicit and prevents a signature captured in one
context being replayed to assert a different pairing.

**Why an expiry rather than permanence?** A binding is a claim that a key is
current. Identities are lost and machines are decommissioned, and a table of
permanent assertions is a table nobody can safely prune. A year is long enough to be
unobtrusive and short enough to be meaningful.

**Why not just convert every known identity and match?** It works for a
whitelist of tens, which is sqsshd's case. An exchange is open to callers it
has not been configured with, and cannot enumerate them in advance.

## Compatibility

New protocol; nothing to break. Requires SIP-2, without which the exchange
cannot see the X25519 key to bind.

## Security considerations

**The binding is only as good as the signature check.** Omitting the derivation
check — that the Ed25519 key really does convert to this X25519 key — would let
any caller claim any identity whose public key it can read, which is all of
them. It is the load-bearing line in this SIP.

**Replay.** The signed message contains no nonce, deliberately: it is bound to
a specific X25519 key, so a captured registration can only be replayed by
someone already holding that key's private half, who could simply register
again. `expires_at` bounds how long a captured registration stays useful.

**Binding table poisoning.** Registration requires a signature, so entries
cannot be forged, but an attacker holding many keys can register many
identities. Exchanges SHOULD rate-limit registration per connection and per
source address.

**Loss of an identity key is unrecoverable here.** Anyone obtaining an Ed25519
private key can bind it to a key of their choosing and be authenticated as that
identity thereafter. This SIP offers no revocation; sqns's identity/service
split exists for exactly this reason, and an exchange SHOULD prefer binding
service keys over identity keys.

**Privacy.** The table maps long-lived public identities to X25519 keys, and by
extension to connection times and source addresses. See SIP-4, where that
becomes a disclosure rather than an internal detail.
