## Abstract

SIP-2 exposes the X25519 key MAC1 verified, and an application names the caller
by matching that key against Ed25519 identities it already holds. That works
only for a *closed* set. This SIP lets a client carry its Ed25519 public key in
the same envelope, bound by MAC1 and checked by derivation, so the server can
report the caller's Ed25519 identity at accept **without prior knowledge of the
caller**. It is the piece an open exchange needs to authorise by identity.

Carrying the key is optional per connection. A client with no persistent
identity, or one that prefers not to reveal it, sends none and is reported as
having no identity — exactly as an ephemeral client is under SIP-2.

## Motivation

Every identity in this ecosystem is named by an Ed25519 key. The transport
verifies an X25519 key, and the two are the same scalar in different
coordinates — but the map from X25519 back to Ed25519 is 2-to-1: the Montgomery
u-coordinate depends only on the Edwards y, so the x-sign bit is lost and
reversing yields two candidate keys with no way to choose, and none at all for
an ephemeral caller. SIP-2 confronts this honestly by not reversing: it hands
up the X25519 key and lets an application with a known set convert its keys
*forward* and match.

A server that must name a caller it has never registered has no set to match
against. An open exchange — sqex, and the liveness beacon of SIP-4 — is exactly
that server. Two other ways to close the gap have been considered: a signed claim exchange
(an earlier proposal, since removed) and TLS client authentication. Both work; both cost
more than the problem needs. The claim exchange is an extra round trip after
connecting. TLS client authentication adds a client-certificate flight of
roughly 340 bytes and moves identity into the TLS layer.

The caller already holds the answer the reverse map cannot recover: which of
the two Ed25519 keys is really its own. The cheapest correct thing is to let it
say so, in the packet it is already sending, and have the transport verify the
statement with work it is already doing.

## Specification

> **Amended for envelope version 4.** The two diagrams in this section describe
> the envelope as it stood when this SIP was written, and are kept because the
> change from one to the other is what the SIP is about. **They are no longer the
> wire format** — SIP-6 is normative for that, and version 4 moved the trailer
> from 108 bytes to 69, or 101 with an identity.
>
> One rule below changed and is marked in place: an identity is now signalled by
> a flag in the header byte, not by 32 zero bytes. Everything else this SIP
> specifies — the derivation check, what a server does when it fails, and why
> the field must be authenticated — is unchanged.

### The envelope today

sQUIC appends a fixed 76-byte trailer to each Initial packet
(`squic-rust/src/mac.rs`, `MAC_OVERHEAD`):

```
[ QUIC Initial ][ client X25519 pub (32) ][ ts (4) ][ nonce (8) ][ MAC1 (16) ][ MAC2 (16) ]
```

`MAC1 = HMAC-SHA256(shared_secret, quic_data || ts || nonce)[:16]`, where
`shared_secret = X25519(client_priv, server_pub)`. The X25519 public key is not
in the MAC1 input; it is bound implicitly, because tampering it changes the
shared secret and MAC1 fails.

### The envelope with an identity

This SIP inserts a 32-byte Ed25519 field after the X25519 key:

```
[ QUIC Initial ][ X25519 pub (32) ][ Ed25519 pub (32) ][ ts (4) ][ nonce (8) ][ MAC1 (16) ][ MAC2 (16) ]
```

The trailer is 108 bytes. Field widths and order are fixed; there is no
variable-length form.

**Absence.** A client with no identity to assert MUST omit the Ed25519 field
entirely and clear the identity flag in the header byte (SIP-29); a server MUST
treat a cleared flag as "no identity" and MUST NOT look for the field.

Under version 3 and earlier, absence was 32 zero bytes and a server treated all
zeros as "no identity" before applying the derivation check. The rule below
about all-zeros being a *valid* point rather than an invalid encoding is
retained because it explains why the sentinel needed care — and why a flag needs
none. Consumers see no difference: both encodings map to the same "no identity
asserted", and the peer's X25519 key is recorded either way.

All zeros is *not* an invalid encoding — it decompresses to the order-4 point
`(±i, 0)`, which maps to the Montgomery key `u = 1`. What makes it unambiguous
is that it can never be a genuine identity: a real public key `aB` lies in the
prime-order subgroup, so it is never small-order and never derives to `u = 1`.
The value is therefore reserved rather than naturally invalid, and a server must
match it explicitly rather than expect the derivation to reject it.

### MAC1 covers the identity

```
MAC1 = HMAC-SHA256(shared_secret, quic_data || ed25519_pub || ts || nonce)[:16]
```

The Ed25519 field MUST be part of the MAC1 input. This is not optional and is
the single change that makes the scheme safe (see Security considerations): the
field does not feed the shared secret, so if it were left unauthenticated an
on-path attacker could substitute the sign-conjugate key, which passes the
derivation check, and flip the reported identity.

MAC2 was unchanged in construction by this SIP: it covered the whole trailer up
to but not including MAC1, so it covered the Ed25519 field as a consequence.
Under version 4 there is no MAC2 — the gate tag replaced it, and both tags cover
one contiguous range that includes the identity field when it is present.

### Server verification

After MAC1 verifies, and only then, a server that implements this SIP:

1. If the Ed25519 field is all zeros, the connection has no asserted identity.
   Stop; report absence.
2. Otherwise, reject the connection unless
   `ed25519_public_to_x25519(ed25519_pub)` equals the X25519 key already
   verified, compared in constant time. A mismatch is a malformed claim and
   MUST fail the handshake, not be treated as absence (SIP-2's reasoning: a
   downgrade to anonymous is a downgrade the peer must not get to choose).
3. Reject a claimed Ed25519 key that is not a valid point, **and one that is
   small-order** (equivalently, one for which `[8]P` is the identity). An honest
   key is never small-order, so this costs a legitimate caller nothing. It is
   required rather than advisory so that this check stands on its own: a
   small-order claim would otherwise be caught only indirectly, by the
   non-contributory X25519 check SIP-2 requires happening to run first, and an
   implementation that reordered the two would silently lose the guarantee.
4. Continue to reject small-order X25519 keys as SIP-2 requires.

A server that does not implement this SIP ignores the field entirely — but see
Compatibility: it cannot, because the trailer width changed.

### What the application sees

An implementation exposes the verified Ed25519 identity at accept, joined to
the connection by the same Destination Connection ID mechanism SIP-2 defined:

- Rust: `ServerListener::peer_identity(&Incoming) -> Option<[u8; 32]>`
- Go: `ServerListener.PeerIdentity(*quic.Conn) ([32]byte, bool)`

`None` / `false` means no identity was asserted (the zero field), the DCID was
contested, or the entry expired. This sits beside SIP-2's `peer_key` /
`PeerKey`, which continues to return the X25519 key; an application may want
either or both.

## Rationale

**Why in the envelope and not a later message.** The caller is already sending
an authenticated packet whose MAC the server already checks. Adding one field
and one curve operation reaches the identity with no round trip and no second
protocol. A separate claim message needs the connection to be up first.

**Why derivation and not a signature.** MAC1 already proves possession of the
scalar. The Ed25519 and X25519 public keys are that one scalar's point in two
coordinate systems, so a forward-map equality is sufficient proof that the
stated identity belongs to the proven scalar. A signature would prove the same
thing at the cost of a signature.

**Why the caller must state it rather than the server deriving it.** The server
cannot: reversing X25519 to Ed25519 is 2-to-1, and the discarded bit is exactly
the one the caller must supply. The forward check is unambiguous precisely
because the caller named which of the two it is.

**Why optional.** Ephemeral clients have no Ed25519 key, so a mandatory field
is impossible. Optionality is also useful in its own right: a client that does
not want its identity on the wire (see Security considerations) simply sends
zeros and falls back to SIP-2 forward matching where the server knows it.

**Why this does not replace SIP-2.** SIP-2 is wire-invisible and sufficient for
closed sets; it should stay the default for sqssh, which gains nothing from
paying these bytes. This SIP is for the open-set case SIP-2 cannot serve. The
two coexist: same DCID join, two accessors.

## Compatibility

**This is a breaking wire change.** The trailer goes from 76 to 108 bytes, and
the current envelope carries no version field to negotiate around it: a peer
computes `quic_len = len - MAC_OVERHEAD` with a hardcoded width, so a new
client talking to an old server misparses the packet entirely. There is no
graceful interop between a SIP-3 peer and a pre-SIP-3 peer.

Deployment is therefore a coordinated cutover: both implementations ship the
new trailer together, and all clients and servers of a given deployment move at
once — the same flag-day discipline used for earlier envelope changes. Both
implementations MUST move together per SIP-1, since this SIP touches the wire.

A future envelope revision SHOULD add a version marker so the next change need
not be a flag day; specifying that marker is out of scope here and noted as
follow-up work.

The application API is additive: `peer_identity` / `PeerIdentity` is new, and
`peer_key` / `PeerKey` is unchanged.

## Security considerations

**The identity is proven, not merely asserted.** MAC1 proves the scalar; the
derivation check proves the stated Ed25519 key is that scalar's key. A caller
can only present an identity it controls. In particular it can present its own
key `A` or the sign-conjugate `-A`, and it controls the scalar for both, so
neither is impersonation of a key it does not hold.

**Degenerate points are not identities.** Every 32-byte string that decompresses
is *some* curve point, so the derivation map alone cannot separate an identity
from a degenerate value — the reserved all-zero field is itself a valid
order-4 point. The small-order rejection in Specification step 3 is what draws
that line, and it is normative for the reason given there: without it the
guarantee rests on the ordering of a check in a different part of the handshake.
An attacker gains nothing directly from a small-order claim (it cannot match a
genuine caller's X25519 key), but an identity surfaced to applications should be
one the transport has fully qualified, not one that happens to be unreachable.

**The MAC1 coverage is load-bearing.** If the Ed25519 field were not in the
MAC1 input, an on-path attacker could replace a victim's `A` with `-A` — a
public computation that passes the derivation check — and the server would
report `-A`, a different 32-byte identity, for the victim's connection.
Including the field in MAC1 makes that substitution fail the MAC, because the
attacker cannot recompute it without the shared secret.

**The identity is in plaintext on the wire.** The X25519 key is already
plaintext, so a passive observer can already link a persistent client's
connections. This SIP additionally reveals the caller's *published* Ed25519
name — the one in `authorized_keys` and sqns records — so an observer can
attribute traffic to a known identity, not merely link it. For a public
service such as the liveness beacon this discloses nothing that is not already
public. For a service where who-is-connecting is sensitive it is a regression,
and such a service SHOULD leave the field zero and rely on SIP-2 forward
matching, or use an identity mechanism that keeps the name in the encrypted
handshake. This is the reason optionality is normative rather than a
convenience.

**Absence must fail closed at the application.** As in SIP-2, an application
that authorises by identity and reads `None` must treat it as "not identified",
never as a default identity.

**No new denial-of-service surface.** The added work is one curve operation per
Initial that already passes MAC1 — the same gating that bounds the existing DH.
The Ed25519 field rides inside the Initial's existing padding: 76 to 108 bytes
of trailer on a datagram QUIC already pads to ~1200 stays within one datagram
under a normal MTU, so there is no fragmentation and no amplification change.

## Reference implementation

Shipped in both implementations, released together as the flag-day
Compatibility requires:

- **squic-rust v0.15.0** — the 108-byte envelope with the Ed25519 field in the
  MAC1 input, the derivation check with small-order rejection
  (`crypto::ed25519_identity_to_x25519`), and
  `ServerListener::peer_identity()` exposed via the SIP-2 DCID join.
  Advertising is opt-in through `Config::advertise_identity`.
- **squic-go v0.60.0** — the same wire and checks
  (`Ed25519IdentityToX25519`), with `ServerListener.PeerIdentity()` filled
  through the `ConnContext`/`Tracer` bridge SIP-2 introduced, and
  `Config.AdvertiseIdentity`. (The two repositories are on independent version
  lines; what pairs these releases is the wire, not the number.)
- **Cross-implementation harness** — `scripts/cross_peerkey_test.sh` in
  squic-go runs the Rust×Go server/client matrix twice, advertised and
  anonymous, asserting both that the reported peer key equals the dialing
  client's X25519 key and that the reported identity equals the one the client
  advertised (the anonymous case asserting it reports *none*). It runs in CI in
  both repositories, each testing its revision against the sibling's `main`.

Unit tests in both languages cover the MAC1 coverage of the identity field (a
tampered field fails), the derivation mismatch, and the small-order rejection —
including that the reserved all-zero field is a genuine order-4 point mapping
to `u = 1` rather than an invalid encoding.

This SIP is the naming step SIP-4 requires and records as open; SIP-4 binds its
beacon through the accessor defined here.
