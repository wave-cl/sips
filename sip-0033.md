## Abstract

A domain publishes one DNSSEC-signed `TXT` record at `_sqex.<domain>` naming its
exchange's Ed25519 public key, and ordinary `A` and `AAAA` records give the
address. A client holding nothing but the domain can then reach the exchange.

The key obtained this way is a **bootstrap, not an authority**. It is taken on
first contact, pinned locally, and a later change is refused rather than
followed. DNSSEC decides who answers the first question; the pin decides every
question after it.

## Motivation

Reaching an exchange needs two facts, and SIP-9 supplies neither: an address and
the key to pin. Both arrive out of band — a flag, an environment variable, a
line in a config file, a string pasted into a chat. That is workable between
people who already have a channel to exchange it on, and it is the whole
difficulty for everybody else. A domain is the one identifier people already
publish, already control, and already know how to hand to a stranger.

sqns does not answer this. It resolves **key → endpoint** — the key is the name,
and you look up the key you already hold — which is the opposite direction and
assumes the hard part is done. The question here is the one before it: *I have a
name and nothing else.*

### Why the key belongs in DNS, and what that costs

The stack's position until now has been that DNS carries pointers and never
identity. It is stated plainly in the sqns client:

> What this is not: the thing that makes a connection safe. The server's key is
> in the address and sQUIC pins it, so a forged answer leads to a host that
> cannot complete a handshake. DNSSEC protects the pointer.

Putting a key in DNS changes that. It makes a registrar, a DNS operator, and the
root and TLD key-signing keys into a trust root for *identity* — the
certificate-authority-shaped dependency this stack exists partly to avoid. There
is no way to have name-based discovery without conceding some version of this:
if a name is to mean something, somebody must be authoritative for the name.

What can be bounded is **how long the concession lasts**. Under this SIP a
compromised registrar can lie once, to clients that have never connected before.
It cannot lie to a client that has, because that client refuses a changed key.
The exposure is a first-contact window rather than a standing authority, which
is the same bargain SSH has made since 1995 and the reason `known_hosts` exists.

## Specification

### Location

An exchange publishes at the underscore-prefixed label `_sqex` beneath its
domain, per RFC 8552:

```
_sqex.example.com.  IN  TXT  "v=sqex1; k=2YQYQCzPocTTdjMoU5KmimvyEkVLzS9mkE4C6QeM2F7u; h=exchange.example.com"
exchange.example.com.  IN  A     198.51.100.4
exchange.example.com.  IN  AAAA  2001:db8::5
```

The zone containing the `TXT` record MUST be DNSSEC-signed. The zone containing
the `A`/`AAAA` records need not be; see *What is validated*.

### Grammar

Tag-value pairs in the style of DKIM (RFC 6376 §3.2): a tag name, `=`, a value,
pairs separated by `;`, whitespace around any token insignificant.

```
record   = "v=sqex1" *( ";" WSP* tag )
tag      = name "=" value
name     = ALPHA *(ALPHA / DIGIT)
value    = *(%x21-3A / %x3C-7E)     ; printable, excluding ";"
```

| tag | required | meaning |
|---|---|---|
| `v` | yes | Version. MUST be exactly `sqex1` and MUST be the first tag. |
| `k` | yes | The exchange's Ed25519 public key, base58, 32 bytes decoded. |
| `h` | no | Host whose `A`/`AAAA` give the address. Defaults to the queried domain. |
| `p` | no | Port, decimal, 1–65535. Defaults to `443`. |

A parser MUST ignore any tag it does not recognise. A parser MUST reject a
record whose first tag is not `v=sqex1`, without reporting an error: a `TXT`
record at this name that is not ours is not a malformed record, it is somebody
else's.

A record with a duplicate tag MUST be rejected. A record whose `k` is not
base58, or does not decode to 32 bytes, MUST be rejected.

**The default port is 443/udp**, which is HTTP/3's own and the one port that
survives networks filtering everything else — the same reasoning that put sqssh
on 22 rather than a number of its own. A domain may name any port with `p=`, so
the default decides only for one that does not bother; publishing the port is
always the safer choice.

### Character-strings

`TXT` RDATA is one or more character-strings of at most 255 bytes. The strings
**within a single record** are concatenated with no separator before parsing.
Strings belonging to **different records** are never concatenated. A record
defined here is around 100 bytes and will not normally be split, which is
precisely why an implementation that gets this wrong will not find out.

### Several records mean rotation

More than one conforming record MAY appear in the RRset, and each names a key
that is currently valid. A client MAY use any of them.

The window buys what it can honestly buy, which is less than it first appears.
While both keys are published, clients that already pinned the old one keep
working, and clients with no pin take the new one — so the population migrates as
it turns over. It does **not** migrate clients that have already pinned: when the
old key is finally withdrawn, those clients stop, and a person decides. See
*Rationale* for why the tempting alternative is not taken.

### Resolution

A client resolving a domain `d`:

1. Query `TXT` for `_sqex.d` through a **validating resolver, validating
   locally** against the DNS root trust anchor. The client MUST NOT rely on the
   AD bit of a recursive resolver's answer: that is a claim by the resolver, and
   the path to the resolver is not protected.
2. Discard every record whose DNSSEC proof is not **Secure**. `Insecure` — an
   unsigned zone — is a valid DNSSEC outcome and MUST be treated as a refusal,
   not as an absence of opinion. If no Secure record remains, resolution fails
   and the client MUST say that the zone was unsigned rather than that the
   domain was not found; the two are different problems with different fixes.
3. Parse each surviving record. Ignore records failing the `v=sqex1` test.
   Reject, with an error, records that pass it and are then malformed.
4. Reconcile against the pin store (below). This yields the key to use.
5. Resolve `h` (or `d`) to addresses by ordinary means and connect on `p`,
   pinning the key from step 4 as SIP-9 requires.

### What is validated

- The `TXT` lookup **MUST** be Secure. It carries identity.
- The `A`/`AAAA` lookup **need not** be validated at all.

The asymmetry is deliberate and is the original stance intact. By the time
addresses are resolved the key is already pinned, and SIP-9 has the client
refuse any server that cannot prove possession of it. A forged pointer therefore
leads to a host that cannot complete a handshake — a denial of service, which
DNSSEC could not have prevented anyway, and not an impersonation.

### Reaching it again

A client SHOULD remember where a domain answered and try that first, climbing
three rungs in order:

1. **A remembered address.** No DNS at all, so it works when DNS does not.
2. **The `h=` host it already holds**, resolved now. Finds a server that changed
   address but kept its name, which is the ordinary case.
3. **A fresh lookup.** The only rung that finds a server whose record now names
   somewhere else.

This is safe for the same reason the `A`/`AAAA` records need no signature: an
address is not identity. A remembered address that is stale, or one an attacker
has arranged for the client to hold, costs a failed handshake and nothing more,
because SIP-9 refuses any server that cannot prove the pinned key.

The cost is delay rather than exposure, and that cost is real: a client whose
first rung is wrong pays a connection timeout before trying the second. A client
SHOULD therefore give the cached rungs a **short deadline** and reserve the full
connect budget for the discovered one. An implementation that gives every rung
five seconds turns a moved server into a ten-second wait on every start, for as
long as the cache is wrong.

Only an address that actually answered is remembered. Recording one that was
merely offered would poison the cache with the very addresses that did not work.

### Pinning

A client maintains a store of domain → key. On the first successful resolution
of a domain it records the key and SHOULD tell the user it has done so. The
remembered host and addresses live beside the key but are **cache, not pin**:
they may be replaced freely, and replacing them is not a trust decision.

On every later resolution:

- If a discovered key equals the pinned key, proceed.
- If the RRset contains the pinned key **and** others, a rotation is in progress:
  proceed with the pinned key. Having seen another key beside it grants that key
  nothing; the pin does not move on its own, ever.
- If the pinned key is no longer published, the client MUST refuse, even if the
  key now offered is one it has previously seen alongside the pin.
- If no discovered key matches the pin, the client MUST refuse to connect, MUST
  name both the pinned and the offered key, and MUST NOT proceed on a warning.
  Replacing the pin is an act the operator takes deliberately.

A client MUST NOT silently update a pin. A client that treated a mismatch as a
warning would have the security of no pin at all, while appearing to have one.

## Rationale

**Why `TXT` and not `SVCB`.** RFC 9460 `SVCB` is the right shape for this —
endpoint plus typed parameters, with `ipv4hint`/`ipv6hint` built in — and would
avoid the tag-value grammar entirely. It is not used because a new `SvcParamKey`
needs IANA registration to be interoperable, and because `SVCB` records remain
awkward or impossible to publish in a good number of DNS control panels. `TXT`
is editable everywhere by everyone today. If `SVCB` support becomes universal,
`v=sqex2` is not the migration path; a parallel `SVCB` record is.

**Why an underscore label.** The apex `TXT` set is crowded with SPF, DMARC and
half a dozen vendors' domain-verification tokens. Publishing there would mean
parsing everyone else's records to find ours and would risk another tool
misparsing ours. RFC 8552 exists for this and `_sqex` follows the convention
that `_sqssh` and `_sqns` could later use unchanged.

**Why tag-value.** It is the grammar operators already know from SPF and DKIM,
it survives being retyped by hand, and it extends without a version bump. The
requirement to ignore unknown tags is what makes the last part true, and is why
SPF has added modifiers for twenty years without breaking a parser.

**Why the version tag is mandatory and first.** So that a foreign `TXT` record
at the same name is skipped rather than diagnosed. Without it, a domain that
publishes anything else at `_sqex` produces errors instead of being ignored.

**Why the pin rather than trusting DNS each time.** Because otherwise the
registrar is a standing authority over every connection, and a domain transfer,
a compromised registrar account, or a hostile DNS operator silently redirects
every client forever. With the pin, that same adversary reaches only clients
that have never connected, and every existing client fails loudly. It is the
difference between a window and a door.

**Why the pin never follows a rotation.** It is tempting to let a client note the
keys published beside its pinned one and, when the pinned one is withdrawn, move
to a key it has already witnessed. That would make rotation seamless, and it
would give away the property the pin exists for. An adversary who can write the
zone would publish their key beside the real one, wait for clients to witness the
pair, withdraw the real one, and carry every existing client across — turning "a
zone compromise cannot move a client that has already connected" into "a zone
compromise can move a client in two publishes". A witnessed key is not an
authenticated one; it is only a key that was in the same answer.

**Why a mismatch is a refusal and not a prompt.** A prompt at the point of
connection is answered "yes" by almost everyone almost always; it converts a
security control into a formality. Moving the pin is rare enough to deserve a
separate deliberate act.

## Compatibility

Nothing on the wire changes and no existing deployment is affected. An exchange
that publishes no record is reached exactly as before, by address and key.

Discovery applies only when a client has a domain and no key. An explicitly
configured key always wins: a client MUST NOT let a `TXT` record override a key
given on the command line, in the environment, or in a config file. Discovery
fills a gap; it does not get a vote where an answer already exists.

A client older than this SIP ignores the record, having never looked for it.

## Operational notes

### A newly published record can stay invisible to clients while `dig` shows it

A validating client sets the **CD** (checking-disabled) bit, because it intends
to check signatures itself rather than accept a resolver's verdict. Recursive
resolvers cache CD answers in a slot of their own, separate from the answers
they give ordinary queries.

The consequence bites the first time a record is published. If anything queried
`_sqex.<domain>` *before* the record existed, the resolver holds a signed
proof of non-existence — an NSEC or NSEC3 — in its CD slot, and goes on serving
it for the negative TTL, which is the zone's SOA minimum and is commonly an
hour. During that window:

```
$ dig +short TXT _sqex.example.com          # no CD bit
"v=sqex1; k=…"                              # the record, plainly there

$ dig +dnssec +cdflag TXT _sqex.example.com  # what a validating client sends
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN
```

Same resolver, same name, same instant, opposite answers. An operator debugging
with `dig` concludes the record is fine and the client is broken; both are true,
and neither observation helps.

There is nothing to fix in the zone and nothing a client can usefully do about
it — flushing a resolver it does not control is not available to it. So the
requirement is on the diagnostics instead: a client MUST distinguish a **proven**
absence, where a signed NSEC or NSEC3 came back, from simply finding nothing,
and SHOULD report the remaining negative TTL. "There is no record, publish one"
sends somebody to fix what is already correct.

Publishing the record before announcing the domain avoids the window entirely,
since nothing will have asked yet.

## Security considerations

**The first-contact window is real.** An adversary controlling the domain's DNS
— a compromised registrar account, a hostile or coerced DNS operator, a stolen
zone-signing key — can publish their own key and intercept clients that have
never connected before. Those clients pin the wrong key and will keep using it.
Nothing in this SIP detects that; the pin protects continuity, not origin. Where
first contact must be trustworthy, the key still has to arrive out of band, and
this SIP does not change that.

**DNSSEC is not confidentiality.** The query `_sqex.example.com` is visible to
every resolver on the path and states that the client intends to reach that
exchange. DNS over TLS or HTTPS to a validating resolver helps against
observers, but the recursive resolver still learns it, and validation must
remain local regardless.

**Downgrade is the likely attack, not forgery.** Signatures are hard to forge and
easy to strip. An adversary who can drop DNSSEC records makes a signed zone look
unsigned, and a client that accepts an unsigned answer has no protection at all.
This is why an `Insecure` proof is refused explicitly rather than left to fail on
its own — it does not fail on its own, it succeeds.

**A stale pin outlives a compromise.** If an exchange's key is genuinely stolen,
the operator publishes a new key and withdraws the old, and every pinned client
refuses to connect until a human intervenes. That is the intended behaviour and
it is also an outage. Operators should rotate through the overlap window
described above, and should expect a key compromise to be a manual event for
their users.

**The pin store is a target.** It holds no secrets, but an attacker who can
write to it can install a key of their choosing and will not be detected,
because a matching pin is exactly what this design trusts. It should be
protected like `known_hosts`: user-readable, user-writable, and no more.

**Multiple records widen the accepted set.** During a rotation two keys are
valid, and an adversary who can add a record to the zone can therefore add a key
without removing the operator's. This is inherent in rotation and is bounded the
same way: only clients with no pin, or clients whose pinned key has been
withdrawn, will take the new one.

## Reference implementation

`sqex-discovery` in the sqex workspace: the record grammar and its parser, a
locally-validating `TXT` lookup built on hickory with the root anchor and an
explicit `Proof::Secure` filter, and the pin store. Wired into `sqex-chat`,
`sqex-cli` and `sqex-voice`, which resolve a server and key today from flags,
environment and `~/.sqnr/config`.

`sqex discover <domain>` reports what a domain publishes, whether it validated,
and what the pin store would do about it — without connecting to anything and
without moving a pin. `sqex discover` alone lists what is pinned, and
`sqex discover --forget <domain>` drops a pin, which is the deliberate act a
changed key requires; a client that offered to do it at the moment of connecting
would be offering a prompt, which this SIP declines to do.

The validating-resolver logic follows `sqns-client`'s, which solves the same
problem for `sqns://` addresses.
