## Abstract

A sQUIC client dials an address and an Ed25519 public key, and accepts the
connection only if the server proves possession of that key. The server presents
a self-signed certificate carrying the key; the client compares the certificate's
**SubjectPublicKeyInfo** against the key it pinned, and consults no certificate
authority, no chain, no hostname and no expiry. This SIP specifies that
comparison, states precisely which field it is made against and why no other
will do, and records what pinning buys — which is the strongest property in the
stack and, until now, the least documented.

## Motivation

Every other transport SIP assumes this one. SIP-6 makes a server invisible to
callers who do not hold its public key; SIP-7 derives its cookie-sealing key
from that public key on the grounds that "any legitimate client already knows
it"; SIP-8 whitelists callers by a key the server was configured with. All of
that is about authenticating the *client*. What makes the arrangement worth
anything is the other direction: that the client is talking to the server whose
key it meant to reach, and not to whatever answered at the address.

That direction is what lets the naming layer be untrusted. sqns resolves an
identity key to an endpoint, and a dishonest resolver is a availability problem
rather than a confidentiality one precisely because the client pins the key it
asked for and will not complete a handshake with anything else. The same is true
of DNS, of a hostile network, and of an endpoint that has been reassigned.

Nothing specified how the pin is checked. In squic-go it was checked correctly
and had no test. In squic-rust it was checked by **searching the certificate's
DER for the pinned 32 bytes and accepting on any hit**, which is not the same
thing at all, had no test either, and was bypassable: an attacker holding no
part of the pinned identity could self-sign with a key of their own, paste the
pinned key into an extension, and be accepted — because the search hits, and the
handshake signature is then verified against the certificate's own key, which
the attacker holds. The pin did not constrain who completed the handshake.

That is the case for writing this down. The defect survived two rewrites of the
same function, each of which looked like an improvement on the last, because
there was no statement anywhere of what the check was supposed to establish.

## Specification

### The server's certificate

A server presents a **self-signed X.509 certificate whose subject public key is
its Ed25519 identity key** — the same key SIP-6 derives the transport X25519
secret from. TLS 1.3 or later MUST be used, and the ALPN protocol list defaults
to the single protocol `squic`.

The certificate is a container for a key. A client MUST NOT attach meaning to
any other field, and a server MAY set them to anything a conforming X.509
encoder will emit. The reference implementations use the common name `squic`, a
serial of 1, and validity periods that differ from each other by a decade; none
of it is checked and none of it can be.

A server MUST NOT present a chain. A client MUST ignore any certificate after
the first.

### What the client checks

Given a pinned 32-byte Ed25519 public key, a client MUST:

1. Reject the handshake if no certificate was presented.
2. Parse the end-entity certificate. Reject if it does not parse.
3. Read the **SubjectPublicKeyInfo**. Reject if its algorithm is not
   id-Ed25519 (OID 1.3.101.112), or if the subject public key is not exactly 32
   bytes.
4. Compare those 32 bytes against the pinned key **in constant time**. Reject on
   any difference.

A client MUST NOT accept on any weaker test. In particular, **searching the
certificate's encoding for the pinned bytes does not satisfy this requirement**,
and neither does locating the key by scanning for the Ed25519 object identifier:
the OID appears in a self-signed certificate twice, once in the
SubjectPublicKeyInfo and once in the signature algorithm.

The reason is worth stating rather than leaving to inference. Every byte of the
certificate except the SubjectPublicKeyInfo is chosen freely by whoever presented
it, and an attacker can place any 32 bytes anywhere — in an extension, a subject
attribute, a serial number. The SubjectPublicKeyInfo is the only field the peer
must hold a private key for, because it is the key that signs CertificateVerify.
A check that passes on bytes found elsewhere lets an attacker present their own
key for the signature and the victim's key as decoration, and both the pin and
the signature then verify. The certificate is attacker-controlled data; only one
field in it is a claim the attacker has to back.

### What the client does not check

A client MUST NOT consult, and MUST NOT fail on:

- certificate chains or any certificate authority;
- `notBefore` and `notAfter`;
- the subject, the common name, or any subject alternative name;
- revocation, in any form;
- the hostname or address it dialled.

Pinning replaces all of it. A reader arriving from web PKI should take this as
the deliberate design it is: there is no issuer to trust, so there is nothing to
validate a path against, and an expiry date signed by the same key it would
constrain is decoration. This is also why both implementations disable their TLS
stack's default verification outright — `InsecureSkipVerify` in Go, the
`dangerous` builder in Rust — which is alarming to read and correct to do,
because the default verifier answers a question that has no meaning here.

### Key rotation

There is none. A server's identity is its key; changing the key produces a
different identity, and every client learns the new one by the same out-of-band
route it learned the old one. A deployment that needs continuity across a key
change needs both keys reachable during the transition, which is a naming-layer
problem rather than a transport one.

## Rationale

**Why pinning rather than a certificate authority.** There is no namespace to
authorise. An identity here *is* a key, so a CA would be attesting that a key is
itself. Every property a CA provides in the web model — name binding, revocation,
delegation — is either meaningless in this model or belongs to a layer that can
express it.

**Why a certificate at all, given none of it is checked.** Because TLS 1.3
requires the server to authenticate with one, and reusing the mechanism costs
nothing: the certificate carries the key to a place the TLS stack will already
verify a signature against. Raw public keys (RFC 7250) would express this more
honestly and are not universally supported by the TLS libraries in use.

**Why the SubjectPublicKeyInfo rather than verifying the handshake signature
against the pinned key directly.** Verifying CertificateVerify under the pinned
key would also be sound, and arguably more direct. Comparing the SPKI is chosen
because it is what a TLS stack's verification callback is positioned to do, it
leaves the signature check where the TLS library already does it correctly, and
it is a single comparison a second implementer can get right. The two are
equivalent given a correct TLS stack: once the SPKI is the pinned key, the
signature the library checks is a signature by the pinned key.

**Why constant-time comparison.** The value being compared is public, so there is
no secret to leak, and the requirement is cheap insurance rather than a
countermeasure to a known attack. It also keeps the rule uniform with every other
comparison in the transport, where some of the values are not public.

**Why not fall back to hostname verification when no key is pinned.** There is no
such mode. A sQUIC client cannot dial without a key — the key is what MAC1 is
computed against — so the case does not arise.

## Compatibility

No wire change, and nothing here is new behaviour for a conforming peer: a
server that was presenting an Ed25519 self-signed certificate continues to, and
a client that was comparing the SubjectPublicKeyInfo continues to.

It **is** a behavioural tightening for squic-rust, which previously accepted any
certificate whose encoding contained the pinned bytes. The connections that
newly fail are exactly the impersonations described in the motivation; an honest
server presents its key in the SubjectPublicKeyInfo and is unaffected. No
deployment needs to change anything, and old and new clients interoperate with
old and new servers in all four combinations.

Per SIP-1, a proposal that does not touch the wire does not require both
implementations to move together. Both have moved regardless, because the rule
is only worth stating if both are known to keep it.

## Security considerations

**This is the strongest authentication property in the stack.** A client
completing a handshake has proof that the peer holds the private key it pinned.
Not that the peer is at a particular address, has a particular name, or was
vouched for by anyone — those are weaker claims and none of them are made.

**It makes the naming layer untrusted, which is the point.** A dishonest sqns
record, a poisoned DNS answer, a hijacked route or a reassigned address can all
send a client to the wrong host. None of them can make the client talk to it.
The residual power of an attacker who controls resolution is denial of service:
they can stop a client reaching the server, and they cannot become it.

**There is no revocation, and a compromised server key is compromised until
every client is told otherwise.** There is no expiry that helps, no CRL, no
OCSP, and no signal a client can act on. A deployment's recovery procedure is
distributing a new key by whatever channel distributed the first one, and that
channel's properties are the real bound on recovery time. This is the sharpest
cost of the design and it has no mitigation inside this SIP.

**The pin does not authenticate the client.** A server accepts any caller that
passes MAC1, subject to SIP-8. The two directions are independent and a reader
should not assume that pinning the server authenticates the connection as a
whole.

**A certificate is attacker-controlled data.** Only the SubjectPublicKeyInfo is a
claim backed by a private key; a client MUST NOT read or act on any other field,
including for logging or diagnostics that might later be trusted.

**Everything the certificate carries is visible to a passive observer**, but in
TLS 1.3 the server's Certificate message is encrypted under the handshake keys,
so the server's identity is not on the wire in the clear — unlike the client's
X25519 key, which is (SIP-6). An observer therefore learns which client is
connecting more readily than which server it reached.

## Reference implementation

- squic v0.16.0 — `src/tls.rs`: `self_signed_cert` builds the server's
  certificate, `PinnedKeyVerifier` performs the check above, parsing the
  certificate and comparing the SubjectPublicKeyInfo. Five unit tests cover the
  pinned key accepted, a different key rejected, an unparseable certificate
  rejected, a non-Ed25519 key rejected, and a certificate that merely contains
  the pinned key rejected.

  Before v0.16.0 this implementation scanned the certificate's DER for the
  pinned bytes and accepted on any hit — the defect described in the motivation.
  The last of those five tests fails against v0.15.0 and passes against v0.16.0.

- squic-go v0.61.0 — `tls.go`: `selfSignedCert` and the `VerifyPeerCertificate`
  closure in `ClientTLSConfig`, which parses the certificate and compares
  `cert.PublicKey`. This implementation was always correct and was never tested;
  six tests now cover it, including the same smuggled-key case.

The cross-implementation matrix described in SIP-2
(`scripts/cross_peerkey_test.sh` in squic-go) dials every server/client pairing
by raw key, so it exercises the ordinary accepting path across both
implementations on every run.
