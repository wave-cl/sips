## Abstract

Two identities, neither reachable by the other, exchange data *through* an
exchange both can already reach. The exchange matches them only when each has
asked for the other, relays one ephemeral public key in each direction, and
thereafter carries opaque frames between them. A three-term Diffie–Hellman makes
the session key derivable only by the two peers, so the exchange cannot read
what it carries and cannot stand in the middle of the agreement it is relaying.

## Motivation

SIP-6 proposes introducing two peers so they can connect *directly*, by
exchanging observed addresses and hole punching. That is the better outcome when
it works, but it does not always work and it does not work here yet:

- **Symmetric NAT defeats it.** SIP-6 says so itself; endpoint-independent
  mapping is the usual requirement.
- **sQUIC cannot currently do it.** `dial` binds a fresh ephemeral local port,
  and there is no way to dial from — or listen on — the port the exchange
  observed. That port reuse *is* the mechanism; without it the NAT creates a
  different mapping for peer traffic and the punch cannot land.

Meanwhile both peers demonstrably hold a working connection to the exchange —
that is how they are asking for each other at all. Carrying the session over
those two existing connections needs no new reachability, no new port, no new
key pinning, and no transport change. It works behind symmetric NAT and behind a
firewall that permits only outbound connections.

SIP-6 anticipated this, listing relaying among its open questions and judging it
"a much larger commitment and probably a separate SIP". This is that SIP. SIP-6
remains the direct-connection design and is not superseded: a future
implementation may punch first and fall back to a relayed session.

## Specification

All integers are unsigned big-endian. Every operation is bound to the caller's
transport identity (SIP-3). A connection carrying no identity has no session and
MUST be refused.

### Consent

A session exists only when **both** identities have an outstanding request
naming the other. Until then the requester learns nothing: not the peer's
ephemeral key, not whether the peer has ever connected, not whether the peer
exists. `Waiting` is returned for a peer who has not asked, for a peer who has
never been seen, and for a peer who does not exist — the three MUST be
indistinguishable, so that asking cannot be used to probe for an identity.

### Key agreement

Each peer contributes a fresh ephemeral X25519 public key with its request. The
exchange relays each to the other once both have asked. Both then derive:

```
first, second = the two identities, in lexicographic order of their key bytes
DH1 = X25519(eph_first,    static_second)
DH2 = X25519(static_first, eph_second)
DH3 = X25519(eph_first,    eph_second)
key = SHA-512(SESSION_CONTEXT || first || second || eph_first || eph_second
              || DH1 || DH2 || DH3)[0..32]
```

`SESSION_CONTEXT` is the ASCII string `sqex-session-v1`. `static_x` is the
forward derivation of that identity's Ed25519 key. Ordering by key bytes means
both ends derive the same key without negotiating who began. Implementations
MUST reject a non-contributory (small-order) result from any term.

**Why three terms.** DH1 and DH2 each require a *static* private key, which only
the peers hold: the exchange, relaying both ephemerals, still cannot complete
either, so substituting its own ephemerals gains it nothing and there is no man
in this middle. Those same two terms authenticate both peers — deriving the key
at all proves possession of the identity key each is named by — so no signature
is needed, keeping this in line with SIP-4 and SIP-5 where the connection and
the keys do the work. DH3 supplies forward secrecy: if both long-term identity
keys leak afterwards, DH3 still requires an ephemeral secret, and those are
discarded when the session ends.

The ephemerals are bound into the transcript so that a relayed substitution
changes the key rather than passing unnoticed.

### Framing

```
nonce = direction(1) || seq(8) || 0(3)
frame = ChaCha20-Poly1305(key, nonce, plaintext)
```

`direction` is 0 for frames from `first` and 1 for frames from `second`, so the
two streams can never collide on a nonce and a reflected frame does not decrypt.
`seq` counts frames in that direction from zero and MUST NOT repeat.

**Frames carry opaque bytes.** Nothing in this SIP inspects a payload; it is
whatever the two peers agree it is.

### Messages

```
Open      | type=0x01 | peer[32] | ephemeral[32] |
OpenAck   | state: u8 | session_id: u64 | peer_ephemeral[32] | now: u64 |
Send      | type=0x02 | session_id: u64 | seq: u64 | ciphertext |
Recv      | type=0x03 | session_id: u64 |
Frames    | open: u8  | count: u32 | count × { seq: u64 | len: u32 | ciphertext } |
Close     | type=0x04 | session_id: u64 |
```

`state` is 0 waiting, 1 established. `open` is false once the session is closed
or expired, which is how the other end learns.

A `Recv` drains what is waiting. Either peer may `Close`; the other learns on its
next `Recv`. An `Open` for an already-established session MUST answer
idempotently, so a retry or a lost acknowledgement resumes rather than starting
again.

### Quotas

| Limit | Value |
|---|---|
| Plaintext per frame | 32 KiB |
| Frames queued per direction | 256 |
| Bytes queued per direction | 1 MiB |
| Session and unmatched-request TTL | 1 hour |

A send that would exceed a direction's queue MUST be refused, distinguishably
from a malformed request. **It MUST NOT be dropped silently:** a peer that is not
collecting must not look like one that is.

## Rationale

**Why relay rather than introduce.** See Motivation: introduction needs a
transport capability that does not exist and a NAT type that cannot be assumed,
while relaying needs only the connections both peers already have.

**Why the exchange must not be able to read.** It carries every byte, which is
precisely why the design cannot rest on its restraint. The three-term agreement
makes non-readability structural rather than promised.

**Why no signatures.** They were the obvious way to authenticate the relayed
ephemerals, and they are not needed: the two static terms already prove
possession of both identity keys. Adding a signature would have put one on every
session for no gain and broken the pattern SIP-4 and SIP-5 set.

**Why strictly mutual consent.** An exchange that answered "that identity has
not asked for you" would answer differently for an identity that exists, and
become a presence oracle. One answer for all three cases is the only version
that discloses nothing.

**Why backpressure rather than dropping.** A relay that silently discards is
indistinguishable from one that delivers, and the sender has no way to find out.
Refusing is the only honest signal available.

## Compatibility

New protocol; nothing to break. Requires SIP-2 and SIP-3 — the latter is what
lets the exchange name two peers it has never registered.

Does not supersede SIP-6. The two are complementary: SIP-6 gets peers connected
directly where the network and transport allow, this carries them where they do
not.

## Security considerations

**The exchange cannot read the session, and this is structural.** DH1 and DH2
each need a static private key it does not hold. That is a stronger statement
than SIP-5's, where the exchange also cannot read but the sender chose the
recipient's key independently; here the exchange is relaying the key material
itself, and still cannot.

**Both peers are mutually authenticated** by the same two terms. Unlike SIP-5,
where the sealed payload does not prove who sent it, a frame that opens here
proves the peer holds the identity key it is named by.

**Forward secrecy is complete for the session.** Compromising both identity keys
afterwards does not open recorded traffic, because DH3 requires an ephemeral
secret that no longer exists. Peers MUST discard ephemeral secrets when a
session ends; an implementation that keeps them forfeits this.

**The exchange learns the metadata, and more of it than SIP-5's.** Who asked for
whom — including requests that never matched — when, how often, how many bytes
each way, and for how long. That is a social graph with timing and volume, and a
traffic-analysis surface even though the content is opaque. **This is not
anonymous communication and must not be described as such.**

**Unmatched requests are retained** for the TTL, so the exchange knows who tried
to reach whom even when no session ever formed.

**The exchange can deny, delay and reorder.** It cannot forge a frame — the AEAD
prevents that — but it can drop frames, hold them, or deliver them out of order,
and peers see only silence. Sequence numbers let a peer detect gaps and
reordering; nothing detects a session simply being starved. A peer that needs
liveness assurance must build it above this.

**Relaying is a resource commitment.** The exchange spends bandwidth and memory
on traffic between two parties, on behalf of anyone who can connect. The quotas
bound a single session; they do not bound how many sessions one identity opens,
and an exchange facing abuse needs its own policy above this SIP.

## Real-time media

Frames are opaque, so voice or video *fit* the protocol: an Opus frame is bytes
like any other. The obstacle is carriage, not design, and it is worth stating
plainly so nobody builds a phone on the reference implementation as it stands.

The reference implementation polls for incoming frames and issues one
request-response per frame. That adds a poll interval of latency in each
direction and a request per 20 ms of audio, and it delivers reliably and in
order — which is the wrong guarantee for media, where a late packet is worth
less than a lost one.

None of that is in this SIP. A real-time carriage would keep the key agreement,
consent rules, framing and quotas exactly as specified and change only how frames
move: a held-open stream, or QUIC datagrams (which sQUIC already supports via
`enable_datagrams`) for unreliable delivery. Latency would then be the two relay
hops, which is inherent to relaying and is the price of working where a direct
connection cannot. Specifying that carriage is future work.

## Reference implementation

Shipped in [sqex](https://github.com/wave-cl/sqex) v0.5.0, on squic v0.15.0
(SIP-3):

- `sqex-proto::session` holds the layouts, the three-term agreement and the
  framing. `sqexd` links it but derives no key: it has no static private key to
  derive one with.
- `sqexd::session` matches consenting pairs, relays the ephemerals, and moves
  frames between two per-direction queues with backpressure and expiry.
- Routes: `POST /session/{open,send,recv,close}`, each refusing a connection
  with no advertised identity.
- `sqex session talk <peer>` opens a session, waits for the peer to open one in
  return, then pumps stdin to them and their frames to stdout.

Integration tests cover two unregistered, mutually unreachable identities
exchanging data both ways; the relayed frames being opaque, with an impostor
holding both ephemerals unable to open one; asking after an identity that never
asks disclosing nothing; a third identity being unable to inject, read, or close
someone else's session; either peer closing and the other learning; and
anonymous connections having no session at all.

**Known limitation: state is in memory.** Here that is close to honest — a
session is live coordination between two connected peers, so a restart ending
them is better than silently resuming half of one — but unmatched open requests
are lost too, which merely costs a retry.
