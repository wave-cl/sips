## Abstract

The Initial envelope of SIP-6 has no version field, so every change to it has
been a flag day: a peer computes `quic_len = len - 108` with a hardcoded width,
a peer using a different width misparses the packet entirely, and because the
failure is a silent drop there is no diagnostic on either side. This SIP adds a
one-byte version marker as the **last** byte of the envelope, where a receiver
can find it without first knowing the envelope's length, and binds it into MAC1.

The marker lets one server accept several envelope versions at once, which is
what actually removes the flag day: servers upgrade first and support both,
clients then move whenever they like. Adding it costs a supporting server about
one extra Diffie-Hellman in every two hundred and fifty-six packets during the
transition, and nothing at all afterwards — so unlike every previous envelope
change, this one does not need a flag day of its own.

## Motivation

SIP-6 records the defect and declines to fix it:

> This should be fixed, and fixing it is out of scope here: a version marker has
> to be introduced by a flag day of its own, and designing it [...] is a SIP in
> its own right.

That assessment was pessimistic, and the cost of leaving it unfixed has now been
paid twice. SIP-3 grew the trailer from 76 to 108 bytes and every deployment cut
over at once. Then squic v0.16.0 fixed a defect in SIP-9's pinned-key check —
an attacker could self-sign a certificate carrying the pinned key in an
extension and be accepted as the server — and because that fix sat on the far
side of the SIP-3 envelope change, taking it meant crossing a wire break. sqssh
and sqns each had to move a client and a server in a coordinated deployment,
in the correct order, to pick up a security fix that had nothing to do with the
wire.

**A security fix that can only be had by breaking the wire is an argument for
being able to change the wire without breaking it.** That is this SIP.

The problem is not that nobody thought of a version field. It is that adding one
to a trailer looks impossible: a version at the *front* of the trailer cannot be
found, because finding the front of the trailer requires knowing its length,
which is what the version was supposed to tell you. That circularity is what
made the marker look like it needed a flag day. It does not — the marker simply
has to go at the other end.

## Specification

All integers are unsigned big-endian.

### Where the marker goes

The version marker is a single byte, and it is the **last byte of the
datagram**:

```
[ QUIC datagram ][ X25519 (32) ][ Ed25519 (32) ][ ts (4) ][ nonce (8) ][ MAC1 (16) ][ MAC2 (16) ][ ver (1) ]
```

A receiver reads `datagram[len - 1]` before parsing anything else. That byte
names the envelope version, which fixes the width of everything before it, which
is what lets the rest be parsed. The trailer for version 2 is therefore 109
bytes.

The marker MUST be the final byte and MUST be one byte wide. Both properties are
what make it findable by a receiver that knows nothing else about the packet.

### The version registry

| Version | Envelope | Defined by |
|---|---|---|
| 0 | Reserved, never emitted | this SIP |
| 1 | 108-byte trailer, no marker byte | SIP-6 |
| 2 | 109-byte trailer, marker byte last | this SIP |

Version 1 is assigned retroactively to the envelope SIP-6 specifies. It carries
no marker on the wire and never will; it is named here so that a receiver
supporting both has something to call the unmarked form.

A future SIP that changes the envelope assigns itself the next version and says
what changes. Version 0 is reserved and MUST NOT be emitted, so that a receiver
which reads a zero byte knows it is not looking at a marker.

### MAC1 binds the version

For version 2, the version byte is **prefixed** to the MAC1 input:

```
MAC1 = HMAC-SHA256(shared, ver || quic_datagram || ed25519 || ts || nonce)[0..16]
```

Version 1's construction is unchanged and has no such prefix (SIP-6).

The prefix is normative and is doing two jobs. It authenticates the marker, so a
tampered version cannot be made to stand. And because it is a prefix, MAC1
values computed under different versions are unrelated even when the remaining
input coincides — so a packet valid under one version can never verify under
another, whatever an attacker chooses for the rest of the envelope. Appending
the version instead would authenticate it but would not give that separation as
cleanly.

### Receiving

A receiver that supports a set of versions, of which version 1 may be one:

1. Read `datagram[len - 1]`.
2. If that byte names a supported version other than 1, parse under that
   version's layout and verify. If verification succeeds, accept.
3. Otherwise — the byte named nothing supported, or verification failed — and
   if version 1 is supported, parse under version 1's layout and verify.
4. If nothing verified, drop in silence, as SIP-6 requires for every other
   failure.

Step 3 is the whole transition mechanism. A version 1 packet's last byte is the
last byte of MAC2, which is uniformly random, so it names version 2 about once
in every 256 packets; in that case the receiver does one wasted parse and
Diffie-Hellman before falling back and succeeding. Every other version 1 packet
is recognised as not-version-2 immediately and costs nothing extra. The expected
overhead of supporting both is therefore about 1.004 Diffie-Hellman operations
per Initial, and it disappears entirely once version 1 is retired.

A receiver MUST NOT let this fallback grow without bound. It applies to version
1 alone, because version 1 is the only unmarked version there will ever be;
every marked version is identified by its marker and needs no guessing. An
implementation supporting versions 1, 2 and 5 tries at most two layouts, never
three.

### Sending

A client sends exactly one version per Initial: the one it is configured to
send. It MUST NOT try several versions on one connection attempt.

**The default MUST be the older version, not the newest one the client
implements.** This is the servers-first rule expressed where it can actually be
enforced. A release that introduces version N ships clients that still send
N-1 by default and offer N as an opt-in; once servers have had time to deploy,
a later release flips the default. A client that defaulted to the newest version
it understood would break every deployment that upgraded a client before a
server — which is precisely the failure this SIP exists to remove, reintroduced
by its own implementation.

A client MUST send the same version on every Initial of a connection, including
retransmissions, for SIP-6's reason: an Initial that fails MAC1 is dropped in
silence, so a client that varied its version mid-handshake would be
indistinguishable from an attacker and would stall.

### Retiring a version

A server MAY refuse any version, and SHOULD refuse versions it no longer wishes
to support. Retirement is a server-side policy decision and needs no wire
mechanism: the server stops parsing that layout, and clients still sending it
are dropped in silence exactly as they are today.

A server MUST be able to refuse version 1 specifically. Without that, the oldest
envelope ever defined becomes a permanent floor, and any weakness in it stays
reachable for the life of the protocol.

## Rationale

**Why the last byte and not the first.** The trailer is appended, so its front is
at an offset the receiver does not know until it knows the version. Its back is
at an offset every receiver knows: the end of the datagram. The marker has to go
where it can be read with no prior knowledge, and there is exactly one such
place.

**Why one byte.** 255 versions is more than this protocol will use. A wider
marker, or a magic number alongside the version, would cut the one-in-256
false match on version 1 packets — but a false match costs one wasted parse and
is corrected by the fallback, so there is nothing to buy. Bytes on an Initial are
not free: the envelope already pushes the packet past the segment size (SIP-6).

**Why a version and not a length.** A length would let a receiver find the QUIC
boundary without knowing the format, which sounds more general and is not
useful: the receiver cannot verify MAC1 without knowing where the fields are,
and it must verify MAC1 before doing anything at all. A version names a
specification; a length names only a number.

**Why this does not need a flag day, when every previous envelope change did.**
Because a server can support two versions at once for the price of a rounding
error, and the previous changes had no way to tell the two apart. Servers
upgrade first and accept both; clients move at their own pace afterwards. That
is the ordinary way protocols evolve, and the envelope has simply never been
able to do it.

**Why clients do not fall back.** A client could try version 2, time out, and
retry with version 1. It should not. The server is silent by design, so a
timeout is indistinguishable from an unreachable host, a firewall, or a key that
is not whitelisted — and the client would pay a full connect timeout to learn
nothing reliable. Servers-first deployment costs nothing and is unambiguous.

**Why not negotiate.** Negotiation needs a round trip with a server that has
decided to answer, and the entire point of the envelope is that the server has
not decided anything yet. Marking is what is possible before authentication;
negotiation is not.

## Compatibility

**A version 2 client cannot talk to a version 1 server.** The server computes
`len - 108`, is one byte out, fails MAC1 and drops in silence. This is the one
direction that does not interoperate, and it is why deployment is
**servers first**: upgrade every server to support both versions, confirm it,
then move clients whenever convenient.

**A version 1 client can talk to a version 2 server** that still supports
version 1, which is the property this SIP exists to provide.

Both implementations must move together per SIP-1, since this is wire. But
"together" here means only that both must be able to *receive* version 2 before
either starts *sending* it — which is a far weaker requirement than the
simultaneous cutover every previous envelope change needed, and is what the
default-to-the-older-version rule above guarantees.

Existing deployments are unaffected until they choose to move. Nothing about
version 1 changes, no key material changes, and no configuration changes.

## Security considerations

**The marker is read before it is authenticated, and that is safe.** A receiver
must read the version to know how to parse, and can only verify MAC1 afterwards.
An attacker who flips the byte changes how the receiver parses, so MAC1 is
computed over a different layout and fails. The outcome of tampering is a
dropped packet — never an accepted one — because there is no version whose
layout makes an unmodified MAC1 verify over the wrong fields.

**There is no downgrade attack, because there is nothing to downgrade.** A
version names a wire layout, not a cipher suite or a security level, and every
version verifies the same MAC1 over its own layout. An attacker cannot rewrite a
version 2 packet into a valid version 1 packet: it does not hold the key, and
the version prefix in MAC1 means the two constructions produce unrelated tags
even if it could arrange identical remaining inputs.

**A version that is weak must be retired, and retiring it is the deployment's
job.** This SIP gives servers the ability to refuse a version and requires that
they can refuse version 1. If a future version fixes something the previous one
got wrong, continuing to accept the previous one keeps the flaw reachable — the
marker makes the transition possible, and does not make it happen.

**The marker tells a passive observer which implementation vintage a peer is
running.** This is a small addition to what the envelope already discloses: its
width is observable, and its width has always identified the version. A client's
X25519 key is a far stronger identifier and is already in the clear (SIP-6).

**Under load, the version is checked against MAC2 before MAC1 has authenticated
it.** MAC2's input is unchanged by this SIP and does not cover the version byte,
which sits after it. A flipped version therefore makes the receiver compute MAC2
over the wrong range, MAC2 fails, and the caller is challenged with a cookie it
did not need. That costs one spurious challenge and nothing else; MAC1 remains
the authority on the envelope's integrity.

## Reference implementation

- squic v0.17.0 — `src/mac.rs` (`ENVELOPE_V1`/`ENVELOPE_V2`, `trailer_len`, the
  version-prefixed MAC1), `src/conn.rs` (`validate_and_strip`'s dispatch,
  `try_version`, and the marker in `build_initial`), `Config::envelope_version`
  and `Config::accepted_envelope_versions`.
- squic-go v0.62.0 — `mac.go` and `conn.go`, with the same names, plus
  `Config.EnvelopeVersion` and `Config.AcceptedEnvelopeVersions`.

Nine tests in each cover the round trip at version 2, one server serving both
versions at once, a server retiring version 1, a version 1 server refusing
version 2, a flipped marker being dropped, and MAC1 being bound to the version
in both directions. The one-in-256 fallback is forced rather than left to
chance: a version 1 envelope has its last byte overwritten with a version 2
marker and must still be rescued by the fallback.

The cross-implementation harness described in SIP-2 gained a version dimension
and runs 16 pairings — every server/client combination at version 1 and at
version 2, advertised and anonymous. The version 1 rows are the transition case
this SIP exists for: an old client reaching a new server across the
implementation boundary. It was checked against a deliberate divergence: moving
the MAC1 version from a prefix to a suffix in one implementation leaves both
same-language pairings passing and fails all four mixed version 2 rows, which is
exactly the class of defect the prefix rule guards against.

Compatibility was verified against a real earlier build rather than argued. A
squic v0.17.0 client emitting version 1 completes a handshake with a v0.16.0
server; the same client emitting version 2 does not. That is the one direction
this SIP says will not interoperate, and it is why servers upgrade first.

Neither implementation has moved its client default to version 2, which is the
rule in Sending working as intended: the default follows the deployed servers,
not the newest specification.
