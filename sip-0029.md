## Abstract

The Initial envelope of SIP-6 originally had no version field, so every change
to it was a flag day: a peer computed `quic_len = len - 108` with a hardcoded
width, a peer using a different width misparsed the packet entirely, and because
the failure is a silent drop there was no diagnostic on either side. This SIP
adds a one-byte marker as the **last** byte of the envelope, where a receiver can
find it without first knowing the envelope's length, and binds it into the tags
computed over that envelope.

The marker lets one server accept several envelope versions at once, which is
what removes the flag day: servers upgrade first and support both, clients then
move whenever they like.

**Amended for envelope version 4.** The byte now carries version *and flags* —
high nibble and low nibble — because version 4 made the trailer's width depend
on whether an Ed25519 identity is present, and the width has to be derivable
from the one byte a receiver can find. The version-1 fallback this SIP
originally defined is gone with the version it existed for. Versions 1 to 3 are
retired; version 4 is the only layout defined.

## Motivation

SIP-6 records the defect and declines to fix it:

> This should be fixed, and fixing it is out of scope here: a version marker has
> to be introduced by a flag day of its own, and designing it [...] is a SIP in
> its own right.

That assessment was pessimistic, and the cost of leaving it unfixed has now been
paid twice. SIP-3 grew the trailer from 76 to 108 bytes and every deployment cut
over at once. Then squic v0.16.0 fixed a defect in SIP-9's pinned-key check —
an attacker could self-sign a certificate carrying the pinned key in an
extension and be accepted as the server — and because that fix sat on the far
side of the SIP-3 envelope change, taking it meant crossing a wire break. sqssh
and sqns each had to move a client and a server in a coordinated deployment,
in the correct order, to pick up a security fix that had nothing to do with the
wire.

**A security fix that can only be had by breaking the wire is an argument for
being able to change the wire without breaking it.** That is this SIP.

The problem is not that nobody thought of a version field. It is that adding one
to a trailer looks impossible: a version at the *front* of the trailer cannot be
found, because finding the front of the trailer requires knowing its length,
which is what the version was supposed to tell you. That circularity is what
made the marker look like it needed a flag day. It does not — the marker simply
has to go at the other end.

## Specification

All integers are unsigned big-endian.

### Where the marker goes

The version marker is a single byte, and it is the **last byte of the
datagram**:

```
[ QUIC datagram ][ ... version-specific fields ... ][ hdr (1) ]
```

For the current envelope, version 4, that is:

```
[ QUIC datagram ][ X25519 (32) ][ Ed25519 (32, if flagged) ][ ts (4) ][ gate (16) ][ MAC1 (16) ][ hdr (1) ]
```

A receiver reads `datagram[len - 1]` before parsing anything else. That byte
names the envelope version *and the flags*, which together fix the width of
everything before it, which is what lets the rest be parsed. For version 4 the
trailer is 69 bytes, or 101 with an identity.

The marker MUST be the final byte and MUST be one byte wide. Both properties are
what make it findable by a receiver that knows nothing else about the packet.

### The version registry

| Version | Envelope | Status | Defined by |
|---|---|---|---|
| 0 | Reserved, never emitted | — | this SIP |
| 1 | 108-byte trailer, no marker byte | Retired | SIP-6, originally |
| 2 | 109-byte trailer, marker byte last | Retired | this SIP |
| 3 | 125-byte trailer, MAC0 added | Retired | SIP-37 |
| 4 | 69/101-byte trailer, one gate tag, flagged identity | **Current** | SIP-6 |

Version 1 was assigned retroactively to the original unmarked envelope. Versions
1 to 3 are **retired**: an implementation MUST NOT emit them and MUST NOT accept
them. That is stronger than deprecation and deliberately so — versions 1 and 2
carried no gate at all, so a server accepting them performed a Diffie-Hellman
for any caller who sent a plausible Initial, and a version that must be narrowed
*away from* in order to be safe will be left wide somewhere.

A future SIP that changes the envelope assigns itself the next version and says
what changes. Version 0 is reserved and MUST NOT be emitted, so that a receiver
which reads a zero byte knows it is not looking at a marker.

### The header byte

The marker is one byte with two fields:

```
  7   6   5   4   3   2   1   0
+---+---+---+---+---+---+---+---+
|    version    |     flags     |
+---+---+---+---+---+---+---+---+
```

The high nibble is the envelope version, so versions 0 to 15 are expressible.
The low nibble is flags, whose meaning is defined per version. For version 4,
bit 0 set means an Ed25519 identity field is present; bits 1 to 3 are reserved
and MUST be sent as zero. Receivers do not currently check them, which SIP-6
records along with what it costs: a bit nobody rejects is a bit that cannot
later be given meaning.

Flags share the byte with the version rather than taking one of their own
because the marker's whole value is that it sits where a receiver can reach it
without knowing the trailer's width. A second byte at the same end would work
and would cost a byte on every Initial for one bit of information; a nibble
costs nothing and four flags is more than version 4 needs.

### The tags bind the header

The header byte is **prefixed** to the input of every tag computed over the
envelope. For version 4 that is both of them — the gate and MAC1 — and SIP-6
gives the constructions:

```
tag = HMAC-SHA256(key, hdr || covered)[0..16]
```

The prefix is normative and is doing two jobs. It authenticates the marker, so a
tampered version cannot be made to stand. And because it is a prefix, MAC1
values computed under different versions are unrelated even when the remaining
input coincides — so a packet valid under one version can never verify under
another, whatever an attacker chooses for the rest of the envelope. Appending
the version instead would authenticate it but would not give that separation as
cleanly.

### Receiving

1. Read `datagram[len - 1]`.
2. Drop if its high nibble names a version this receiver does not accept.
3. Derive the trailer width from the version and flags. Drop if the datagram is
   not longer than that width.
4. Parse under that layout and verify, per SIP-6.
5. If anything fails, drop in silence, as SIP-6 requires for every other
   failure.

**A receiver MUST NOT try a second layout for one datagram.** This SIP
originally defined a fallback: if the marker named nothing supported, parse
again as unmarked version 1. That was the transition mechanism for the one
unmarked version that will ever exist, and it is gone with it.

It is worth recording *why* it is now forbidden rather than merely unnecessary.
A version 1 packet's last byte was the last byte of MAC2, uniformly random, so
it named version 2 about once in every 256 packets and the receiver did one
wasted parse before falling back — the modest cost this SIP originally
advertised. What that framing missed is that a *deliberate* caller could pick
the byte. One datagram parsed under two layouts is one datagram buying two
Diffie-Hellman operations from a server that accepted both versions, and an
attacker chooses the byte rather than drawing it at random. With one layout per
marker there is nothing to guess and nothing to double.

### Sending

A client sends exactly one version per Initial: the one it is configured to
send. It MUST NOT try several versions on one connection attempt.

**The default MUST be the older version, not the newest one the client
implements**, whenever more than one is defined. This is the servers-first rule
expressed where it can actually be enforced. A release that introduces version N
ships clients that still send N-1 by default and offer N as an opt-in; once
servers have had time to deploy, a later release flips the default. A client
that defaulted to the newest version it understood would break every deployment
that upgraded a client before a server — which is precisely the failure this SIP
exists to remove, reintroduced by its own implementation.

The move to version 4 did not follow this rule, and the exception should be
recorded rather than hidden: versions 1 to 3 were retired in the same release
that introduced 4, so there was no older version to default to. That made it a
coordinated cut with a real outage window in which every failure was silent, and
it was chosen deliberately over serving `[3, 4]` for one release. The rule stands
for the next transition; this one bought the removal of three unsafe layouts by
paying a window, knowingly.

**A client MUST refuse to dial on a version it cannot emit.** The symptom
otherwise is a handshake timeout with no diagnostic, since the server drops the
envelope in silence — so a misconfiguration and an unreachable host look
identical.

A client MUST send the same version on every Initial of a connection, including
retransmissions, for SIP-6's reason: an Initial that fails MAC1 is dropped in
silence, so a client that varied its version mid-handshake would be
indistinguishable from an attacker and would stall.

### Retiring a version

A server MAY refuse any version, and SHOULD refuse versions it no longer wishes
to support. Retirement is a server-side policy decision and needs no wire
mechanism: the server stops parsing that layout, and clients still sending it
are dropped in silence exactly as they are today.

A server MUST be able to refuse version 1 specifically. Without that, the oldest
envelope ever defined becomes a permanent floor, and any weakness in it stays
reachable for the life of the protocol.

**A server MUST refuse to start when its configured accept set names a version
it cannot parse, and MUST refuse an empty set.** Retirement is a server-side
policy decision, but the configuration expressing it is the sharpest edge in
this SIP: a server told to accept only versions its build does not implement
binds successfully, reports itself healthy, and then drops every Initial in
silence — because that silence is what SIP-6 requires of anything that fails
validation. There is no error, no log line and no reply, so the operator sees a
live process and a dead port.

Every named version must be implemented, not merely one of them. A set naming
one implemented version and one retired one is the quieter form of the same
fault: callers on the implemented version connect, callers on the retired one
are dropped without a word, and the operator believes both are served.

This is the mirror of the rule for senders, where an implementation already
refuses to dial on a version it cannot emit. The receiving side matters more:
a misconfigured client fails alone, and a misconfigured server takes down
everyone who depends on it.

It follows that a config naming a version ahead of the binary is refused. That
is correct — the accept set is read at start, and a version arrives with the
code that parses it.

## Rationale

**Why the last byte and not the first.** The trailer is appended, so its front is
at an offset the receiver does not know until it knows the version. Its back is
at an offset every receiver knows: the end of the datagram. The marker has to go
where it can be read with no prior knowledge, and there is exactly one such
place.

**Why one byte.** 255 versions is more than this protocol will use. A wider
marker, or a magic number alongside the version, would cut the one-in-256
false match on version 1 packets — but a false match costs one wasted parse and
is corrected by the fallback, so there is nothing to buy. Bytes on an Initial are
not free: the envelope already pushes the packet past the segment size (SIP-6).

**Why a version and not a length.** A length would let a receiver find the QUIC
boundary without knowing the format, which sounds more general and is not
useful: the receiver cannot verify MAC1 without knowing where the fields are,
and it must verify MAC1 before doing anything at all. A version names a
specification; a length names only a number.

**Why this does not need a flag day, when every previous envelope change did.**
Because a server can support two versions at once for the price of a rounding
error, and the previous changes had no way to tell the two apart. Servers
upgrade first and accept both; clients move at their own pace afterwards. That
is the ordinary way protocols evolve, and the envelope has simply never been
able to do it.

**Why clients do not fall back.** A client could try version 2, time out, and
retry with version 1. It should not. The server is silent by design, so a
timeout is indistinguishable from an unreachable host, a firewall, or a key that
is not whitelisted — and the client would pay a full connect timeout to learn
nothing reliable. Servers-first deployment costs nothing and is unambiguous.

**Why not negotiate.** Negotiation needs a round trip with a server that has
decided to answer, and the entire point of the envelope is that the server has
not decided anything yet. Marking is what is possible before authentication;
negotiation is not.

## Compatibility

**A client cannot talk to a server that does not accept its version**, in
either direction, and the failure is silent at both ends: the server drops the
envelope without a reply, so the client sees a timeout indistinguishable from an
unreachable host. This is why deployment is **servers first** whenever more than
one version is defined — upgrade every server to accept both, confirm it, then
move clients whenever convenient.

**A server MUST refuse to start when its configured accept set names a version
it cannot parse, and MUST refuse an empty set.** Without this the same silence
becomes an outage that looks like health: the server binds, reports itself up,
and drops every Initial. Every named version must be implemented, not merely
one of them — a set naming one implemented version and one retired one serves
callers on the first and silently drops callers on the second while the operator
believes both are served.

Both implementations must move together per SIP-1, since this is wire. But
"together" here means only that both must be able to *receive* version 2 before
either starts *sending* it — which is a far weaker requirement than the
simultaneous cutover every previous envelope change needed, and is what the
default-to-the-older-version rule above guarantees.

Existing deployments are unaffected until they choose to move. Nothing about
version 1 changes, no key material changes, and no configuration changes.

## Security considerations

**The marker is read before it is authenticated, and that is safe.** A receiver
must read the version to know how to parse, and can only verify MAC1 afterwards.
An attacker who flips the byte changes how the receiver parses, so MAC1 is
computed over a different layout and fails. The outcome of tampering is a
dropped packet — never an accepted one — because there is no version whose
layout makes an unmodified MAC1 verify over the wrong fields.

**There is no downgrade attack, because there is nothing to downgrade.** A
version names a wire layout, not a cipher suite or a security level, and every
version verifies the same MAC1 over its own layout. An attacker cannot rewrite a
version 2 packet into a valid version 1 packet: it does not hold the key, and
the version prefix in MAC1 means the two constructions produce unrelated tags
even if it could arrange identical remaining inputs.

**A version that is weak must be retired, and retiring it is the deployment's
job.** This SIP gives servers the ability to refuse a version and requires that
they can refuse version 1. If a future version fixes something the previous one
got wrong, continuing to accept the previous one keeps the flaw reachable — the
marker makes the transition possible, and does not make it happen.

**The marker tells a passive observer which implementation vintage a peer is
running.** This is a small addition to what the envelope already discloses: its
width is observable, and its width has always identified the version. A client's
X25519 key is a far stronger identifier and is already in the clear (SIP-6).

**The header is read before anything has authenticated it**, which is
unavoidable: it is what tells the receiver how to parse the rest. It is safe
because every tag over the envelope prefixes it, so a flipped header produces a
tag over a different layout and cannot verify. Under version 3 a flipped marker
could still cost the caller one spurious cookie challenge, because MAC2 did not
cover the marker; under version 4 the gate covers it like MAC1 does, so a
tampered header can only cost a drop and never an accept or a reply.

## Reference implementation

- squic v0.25.0 — `src/mac.rs` (`ENVELOPE_V4`, `hdr`, `hdr_version`,
  `hdr_has_identity`, `trailer_len`, and the header-prefixed gate and MAC1),
  `src/conn.rs` (`validate_and_strip`, `validate_envelope`, and the header in
  `build_initial`), `Config::envelope_version` and
  `Config::accepted_envelope_versions`, with the accept-set guard in `listen`
  and the emit guard in `dial`.
- squic-go v0.70.0 — `mac.go` and `conn.go`, with the same names, plus
  `Config.EnvelopeVersion` and `Config.AcceptedEnvelopeVersions` and the same
  two guards.

Both refuse the misconfiguration this SIP's Compatibility section names, and
both are tested against the accept set `[3]` specifically — the value the
`ex.squic.org` exchange was running up to the version 4 cut, where a binary
installed without editing that line would have bound successfully and served
nobody.

Nine tests in each cover the round trip at version 2, one server serving both
versions at once, a server retiring version 1, a version 1 server refusing
version 2, a flipped marker being dropped, and MAC1 being bound to the version
in both directions. The one-in-256 fallback is forced rather than left to
chance: a version 1 envelope has its last byte overwritten with a version 2
marker and must still be rescued by the fallback.

The cross-implementation harness described in SIP-2 gained a version dimension
and runs 16 pairings — every server/client combination at version 1 and at
version 2, advertised and anonymous. The version 1 rows are the transition case
this SIP exists for: an old client reaching a new server across the
implementation boundary. It was checked against a deliberate divergence: moving
the MAC1 version from a prefix to a suffix in one implementation leaves both
same-language pairings passing and fails all four mixed version 2 rows, which is
exactly the class of defect the prefix rule guards against.

Compatibility was verified against a real earlier build rather than argued. A
squic v0.17.0 client emitting version 1 completes a handshake with a v0.16.0
server; the same client emitting version 2 does not. That is the one direction
this SIP says will not interoperate, and it is why servers upgrade first.

Neither implementation has moved its client default to version 2, which is the
rule in Sending working as intended: the default follows the deployed servers,
not the newest specification.
