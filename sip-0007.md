## Abstract

MAC1 makes a server invisible but not cheap: verifying it costs a
Diffie-Hellman, and anyone holding the server's public key can make the server
pay that cost by sending Initials from a forged address. This SIP specifies the
second gate. When the Diffie-Hellman rate crosses a threshold the server stops
doing key agreement for callers it has not heard from, and instead returns an
encrypted cookie bound to the caller's IP address. A caller that echoes the
cookie back as MAC2 — a MAC the server can check with a hash and no curve
operation — is admitted; one that does not is challenged again. The cost of the
first packet moves from the server to the client, and only while the server is
under load.

## Motivation

SIP-6's validation order puts every cheap check before the Diffie-Hellman, so
rubbish costs a server almost nothing. What it cannot make cheap is a *valid*
Initial, because deciding whether MAC1 is valid is what the Diffie-Hellman is
for. An attacker who holds the server's public key — which for many deployments
is simply the published address of a service — can send well-formed Initials
from spoofed source addresses as fast as it likes, and the server does one curve
operation per packet.

This is WireGuard's problem and this is WireGuard's answer, adapted. The
insight is that the expensive check can be deferred behind a cheap one that
proves the caller can receive at the address it claims: send it a value, and
require the value back. A spoofing attacker never sees the reply, so it can
never produce the second packet, and a legitimate client pays one extra round
trip during an attack and nothing at all otherwise.

Nothing about this has been written down. The mechanism is on the wire — a
packet type of its own, a MAC construction, a key derivation both ends must
agree on — and lives in two implementations that have never been tested against
each other on this path.

## Specification

All integers are unsigned big-endian.

### When the defence engages

A server counts the Diffie-Hellman operations it performs (SIP-6 step 5) and
compares the count against a threshold once per second, then resets it. The
server is **under load** for the following second when the count exceeded the
threshold.

The default threshold is **1000 operations per second**. A deployment MAY change
it, and MAY disable the defence entirely, in which case the server never
demands MAC2 and never issues a cookie.

Under load, SIP-6 step 3 becomes: verify MAC2, and if it does not verify, send a
cookie reply and drop the packet. Not under load, step 3 is skipped and the MAC2
field is ignored entirely — including when it is nonsense.

The threshold is on the DH rate rather than the packet rate deliberately: it
measures the resource actually being consumed, and it falls back to zero on its
own when the attack stops, so the server leaves under-load mode without
intervention.

### The cookie

A cookie is 16 bytes, deterministic for a given secret and client address:

```
cookie = HMAC-SHA256(secret, ip)[0..16]
```

`secret` is 32 random bytes known only to the server. `ip` is the client's
address as **16 bytes**: an IPv6 address verbatim, and an IPv4 address in its
IPv4-mapped form, `::ffff:a.b.c.d` — that is, ten zero bytes, then `0xff 0xff`,
then the four address bytes. An implementation MUST normalise to 16 bytes, so
that the same client reaching a dual-stack socket is not issued two different
cookies depending on how the address was presented to it.

The cookie is deterministic so the server can recompute it to verify MAC2
without storing anything per client. That is the point: a defence that allocated
state per challenged address would be a memory-exhaustion attack with extra
steps.

**Secret rotation.** The server MUST replace its secret periodically —
**every 120 seconds** — and MUST retain the previous secret for one further
period. On verification it tries the current secret first and the previous one
second. Without the grace period, a client challenged a moment before a rotation
would answer with a cookie the server no longer recognises, be challenged
again, and in a pathological case never converge.

### MAC2

```
MAC2 = HMAC-SHA256(cookie, envelope_before_mac1 || mac1)[0..16]
```

`envelope_before_mac1` is the datagram from byte 0 up to but **not including**
MAC1 — that is, the QUIC datagram, the X25519 field, the Ed25519 field, the
timestamp and the nonce. MAC1 is then fed in as a separate second input.

The boundary is the rule an implementation is most likely to get wrong, and it
is worth being explicit about why it is drawn there. Hashing the buffer whole,
up to and including MAC1, and then appending MAC1 again folds MAC1 into the
input twice; the two sides disagree and the MAC never verifies. Because a
failing MAC2 is indistinguishable from a client that has no cookie, the symptom
is not an error but a handshake that takes an extra round trip forever.

**The all-zero sentinel.** A client with no cookie MUST set MAC2 to all zeros,
and a server MUST treat all zeros as "no cookie" without attempting
verification. A genuine MAC2 is all zeros with probability 2⁻¹²⁸; in that case
the client is challenged once more and computes a different tag over a fresh
timestamp and nonce. Nothing else is affected.

### The cookie reply

A challenged client receives a single datagram:

```
[ 0x01 ][ nonce (24) ][ XChaCha20-Poly1305(cookie) (32) ]
```

57 bytes: a one-byte type, a 24-byte nonce, and the 16-byte cookie sealed under
XChaCha20-Poly1305 with its 16-byte tag. There is no associated data.

`0x01` cannot be confused with a QUIC packet. A QUIC long header has the high
bit set, so its first byte is at least `0x80`; a short header has the high bit
clear but the fixed bit set, so its first byte is at least `0x40`. No valid QUIC
first byte is below `0x40`, and the values below it are free.

The sealing key is derived from the server's transport public key:

```
cookie_key = SHA-256("squic-cookie-v1" || server_x25519_pub)
```

where `server_x25519_pub` is the 32-byte X25519 public key derived from the
server's identity seed (SIP-6), and the label is the 15 ASCII bytes with no
terminator.

Both ends can compute this without any key agreement: the server holds the seed,
and any legitimate client already knows the server's public key — that is the
premise of a silent server, and the premise SIP-9 makes good. Keying the reply
off the Diffie-Hellman shared secret instead would defeat the entire mechanism,
since the cookie exists precisely so the server need not perform a DH for an
unverified caller.

Encrypting the reply at all keeps a cookie from being harvested by an observer
who does not hold the server's public key. An attacker who does hold it could
already make the server do DH work, so the encryption gives nothing away that
was being protected.

### Client behaviour

A client MUST scan incoming datagrams for the `0x01` type byte during the
handshake, remove them from what it passes to the QUIC layer, and open them with
`cookie_key`. A reply that does not open, or that does not contain exactly 16
bytes, MUST be discarded, and any cookie already held MUST be kept — a reply
that will not open did not come from a server holding the key the client pinned.

On storing a new cookie, a client SHOULD **immediately** rebuild and resend its
most recent Initial carrying MAC2, rather than waiting for the QUIC layer's
retransmission timer. The QUIC layer never saw the cookie reply and has no
reason to retransmit early; waiting costs the caller a full probe timeout for
every challenge, which is roughly a second the mechanism does not need to spend.

Resending is sound. The server dropped the original at the MAC2 gate before the
QUIC layer ever saw it, so this is the first time that packet number reaches the
peer; in the race where the original did get through — under-load cleared in
between — the QUIC layer discards the duplicate. Only the sQUIC envelope is
rebuilt, with a fresh timestamp, nonce and MAC1. The QUIC packet inside it MUST
NOT be regenerated: it is the same packet number carrying the same frames, and
producing a different one would be a genuine protocol violation rather than a
harmless retransmission.

A client MUST continue to send MAC2 on subsequent Initials once it holds a
cookie. There is no signal that the server has left under-load mode, and a
cookie costs nothing to carry.

**A client MUST keep watching for cookie replies until its handshake
completes**, not merely until the first packet that is not one. A server can
cross its load threshold at any moment, including after it has already answered
the client's first Initial, and the challenge it then raises is against an
Initial the client is still retransmitting. A client that stopped watching
earlier ignores that challenge, retransmits an Initial that is dropped again,
and stalls until the handshake times out — recovering only on a fresh attempt,
which sees the challenge first and succeeds. The safe point to stop is the
client's first short-header packet: a short header means 1-RTT keys, so the
handshake is finished and no Initial remains to be challenged.

Both reference implementations had this wrong until the audit for this SIP; see
Reference implementation.

### QUIC Retry MUST NOT be enabled

QUIC has its own address-validation mechanism, and it MUST NOT be used. This SIP
is its replacement, sitting below QUIC where it can refuse a packet without
answering it — Retry, by definition, answers. Beyond the redundancy, enabling
Retry silently breaks SIP-2: the accepting application looks a connection up by
its original destination connection ID, and a retried Initial carries a
different DCID on the wire than the accept path reports, so the join misses and
every connection is reported as having no verified peer.

## Rationale

**Why an IP-bound cookie rather than a random challenge.** A random challenge
must be remembered, and remembering is what the attacker wants the server to do.
Deriving the cookie from the address makes verification a hash over data already
in the packet.

**Why the address and not the full four-tuple.** A cookie bound to the source
port would be invalidated by a NAT rebinding mid-handshake, which is a normal
event, and the port adds nothing: an attacker able to receive at an address can
receive on any of its ports.

**Why the defence is rate-triggered rather than always on.** Always challenging
would cost every first connection an extra round trip, forever, to defend
against an attack that is usually not happening. The threshold buys the ordinary
case a single round trip and accepts that the first packets of an attack get
through before the counter turns over.

**Why the previous secret is kept but not two.** One period of grace covers the
rotation boundary, which is the only case that needs covering. Keeping more
would widen the window in which a harvested cookie stays valid for no benefit.

**Why the cookie is 16 bytes.** It is a MAC key, not a secret to be guessed
offline; the attacker's task is to receive a datagram at an address, and no
amount of cookie length changes that.

**Why not just require MAC2 always.** Considered and rejected: it makes the
common case worse to make the rare case better, and the rare case is already
survivable because a server under load that drops everything is no worse off
than a server that never had the mechanism.

## Compatibility

**Not a wire change to the envelope.** MAC2 is a field SIP-6 already reserves,
and a client that never receives a cookie sends zeros in it forever. A server
with the defence disabled never inspects it. The two ends therefore interoperate
in all four combinations of "implements this SIP" without negotiation.

**Both implementations must move together** for any change to the cookie
construction, the reply format or the key derivation, per SIP-1.

**How the two implementations spell "disabled" differs, and this is an API
difference rather than a wire one.** squic-rust's threshold is an
`Option<u64>`: `None` selects the default, `Some(0)` disables the defence.
squic-go cannot distinguish a struct field left out of a literal from one
explicitly set to zero, so zero selects the default and a negative value
disables. Both express the same two states and neither is visible to a peer.

## Security considerations

**This defends the server's CPU, and nothing else.** A caller that answers a
challenge has proved it can receive datagrams at the address it claims. It has
not proved who it is, and MAC1 still has to verify afterwards.

**Address validation is not address authentication.** An attacker on the path,
or one that has compromised any host on the route, receives the reply and
answers the challenge. The mechanism raises the cost of spoofed-source flooding
specifically, which is the attack it was built for.

**The cookie leaks that the server is under load** to anyone who can reach it
with a valid MAC1 — which requires the server's public key. An attacker can
therefore measure whether its own attack is working. This is unavoidable in any
challenge-based scheme: the challenge is the signal.

**The reply is a response, and the server is meant to be silent.** Under load, a
server answers packets it would otherwise have dropped, so a caller that holds
the server's public key can confirm the server exists more cheaply than before.
It could already confirm this by completing a handshake, so nothing is disclosed
to anyone who was not already able to learn it. A caller *without* the public
key still gets nothing: it cannot produce a valid MAC1, and step 3 comes before
the DH but after the length and timestamp checks — a packet that is not a
plausible Initial is dropped in silence as always.

**A harvested cookie is usable for up to two rotation periods**, by anyone who
can send from the address it was minted for. It admits them to the MAC1 check,
which they must then pass on their own.

**Under-load mode is a degraded mode and should be observable.** An operator who
cannot tell that every new client is paying an extra round trip cannot tell an
attack from a slow service. Both implementations expose a counter of challenges
issued and Initials admitted on a valid MAC2.

## Reference implementation

- squic v0.16.0 — `src/mac.rs` (`cookie_value`, `cookie_key`, `encrypt_cookie`,
  `compute_mac2`), `src/conn.rs` (the under-load branch in
  `ServerSocket::validate_and_strip`, `send_cookie_reply`, the rotation and load
  tasks in `spawn_maintenance`, and the client's `store_cookie` and
  `answer_challenge`).
- squic-go v0.61.0 — `mac.go` and `conn.go`, with the same names.

Both expose the under-load state and its counters (`load_stats` / `LoadStats`),
and hidden setters so a test need not win a race with the one-second load
monitor or wait out the 120-second rotation timer.

**Both implementations stopped watching for cookie replies too early**, arming
the fast path at the first received packet that was not a cookie — which is the
server's very first packet back. The stall described under Client behaviour was
the consequence, and it is fixed in the versions above by arming on the first
short-header packet *sent* instead. Neither implementation's tests could have
caught it: the case needs a server that crosses its threshold mid-handshake, and
every test started the server under load before the first packet arrived.

The cookie path is held to the same wire behaviour across implementations by
`scripts/cross_cookie_test.sh` in squic-go, which runs the Rust and Go probes in
all four server/client pairings with the server under load, and asserts both
that the handshake completed and that the server issued a challenge and verified
a MAC2 — so a run that quietly skipped the cookie path fails. It was checked
against a deliberate divergence: changing one character of the cookie-key label
in one implementation leaves both same-language pairings passing and fails both
mixed ones. Before this existed, all four of this SIP's constructions had only
ever been checked against themselves.
