## Abstract

An identity publishes what it offers — ALPN, service type, version — and others
query it.

**This SIP may not survive review, and the reason is recorded below.** Most of
what it proposes belongs in sqns, not the exchange.

## Motivation

Knowing where a service is and knowing what it speaks are different questions.
sqns answers the first. Nothing answers the second: a caller must already know
that a key on port 22 speaks `sqssh/1`, and a rolling upgrade is invisible.

## The boundary problem

The intended split was that sqns says *where* and the exchange says *what*.
Examined against sqns as it actually exists, that split mostly does not hold.

An sqns `Record` carries `key`, `delegation`, `serial`, `issued_at`, `ttl` and
a body, and a `Live` body carries endpoints. Crucially, a `Live` record is
signed by **the service key, not the identity key** — `expected_signer()`
returns `self.key` for `Live`, reserving the offline identity key for
retirement. The service key is online by definition; it is what the service
uses to answer.

So the argument that produced SIP-4 does not apply here. A beacon cannot live
in sqns because heartbeats cannot be signed by an offline key. Capability
**can** be signed, by a key that is already online, and put in a record that is
signed, replicated, cached with a TTL, and — decisively — still readable when
the service is down.

An exchange answer has none of those properties. It is transport-authenticated
rather than self-authenticating, held by one operator, and meaningless when the
subject is offline. For static facts about a service, that is worse in every
dimension.

### What would remain

Only state that changes faster than it is worth re-signing and republishing,
and that is meaningless when the service is offline. Plausibly: current load,
readiness during a rolling restart, a version that changes between record
publications.

That residue is thin, and it overlaps SIP-4 — a beacon already proves the
service is up, and `flags` could carry readiness without a new mechanism.

## Recommendation

Do not implement this as written. Take one of:

1. **Extend the sqns record body** with optional ALPN, service type and
   version. Static capability, signed, replicated, available offline. Requires
   a `RecordBody` change and therefore a record-format revision — the format is
   already on its fourth — but puts the data where its properties are best.
2. **Narrow this SIP to dynamic state only**, and justify each field against
   the question "why can this not be signed and published to sqns". Fields that
   cannot answer it do not belong here.
3. **Withdraw**, folding readiness into SIP-4's flags.

Option 1 is preferred. It is a different SIP against a different layer, and
this one should be marked Replaced when it is written.

## Rationale

Recorded rather than deleted because the reasoning is the useful part. The
temptation to put service metadata in an exchange — where it is easy, needs no
signature and no format revision — is real, and the cost is losing every
property that makes sqns records worth having. A future proposal will meet the
same temptation.

## Compatibility

None as written.

## Security considerations

Advertising capability advertises attack surface: a version string tells an
attacker which vulnerabilities apply. That is true wherever the data lives, but
an exchange makes it queryable for every identity at once, which a distributed
set of signed records does not.

## Reference implementation

None, and none intended while the recommendation above stands.
