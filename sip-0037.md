> **Replaced by SIP-6.** MAC0 no longer exists as a separate construction. The
> property this SIP established — that a caller who does not hold the server's
> public key is turned away for one HMAC, in silence, whether or not the server
> is under load — is unchanged and now carried by the **gate tag** specified in
> SIP-6, which merged MAC0 with SIP-7's MAC2 in envelope version 4.
>
> The merge was possible because the two were two states of one proof. A cookie
> is delivered encrypted under a key derived from the server's public key, so a
> valid MAC2 already demonstrated the knowledge MAC0 existed to prove; the two
> fields were never both load-bearing on the same packet. Version 3 spent 32
> bytes on them, version 4 spends 16 on one tag with two possible keys.
>
> **Nothing here was withdrawn or found wrong.** This document is retained
> because its Motivation is the clearest statement of why the gate exists at
> all, and because the three-outcome rule it introduced — accept on a
> cookie-keyed tag, challenge on a key-keyed one, silence otherwise — is
> reproduced verbatim in SIP-6 and is the part an implementer is most likely to
> get subtly wrong. Read this for the reasoning; implement SIP-6.

## Abstract

SIP-6 promises that a caller who does not hold the server's public key gets no
response and no evidence the server exists. SIP-7 forfeits that promise whenever
it engages: under load the server issues an encrypted cookie to *anyone* whose
datagram is Initial-shaped and carries a plausible timestamp, because it has no
way to tell a caller who knows its key from one who does not without paying for
a Diffie-Hellman — which is the cost the cookie exists to defer.

This SIP adds **MAC0**, a 16-byte tag keyed on a hash of the server's X25519
public key, carried in a new envelope version 3 and verified before the cookie
decision and before the key agreement. It is WireGuard's MAC1 construction,
added alongside sQUIC's rather than replacing it. A caller who does not hold the
server's public key is then turned away for the price of one HMAC, in silence,
whether or not the server is under load.

## Motivation

The silent server is the premise of the whole system, and SIP-7's own
specification quietly suspends it:

> Under load, SIP-6 step 3 becomes: verify MAC2, and if it does not verify, send
> a cookie reply and drop the packet.

Nothing has been proved at that point. SIP-6's validation order puts MAC2 at
step 3, ahead of the whitelist at step 4 and the Diffie-Hellman at step 5, so a
server under load replies to a datagram whose only credentials are a first byte
in `0xC0`–`0xCF`, a length over 108, and four timestamp bytes inside a
240-second span. One packet, no key, and the server has announced itself.

The property inverts exactly when it is most wanted, and it is reachable on
demand rather than by luck. A deployment with no whitelist — the documented
default — counts every caller's Diffie-Hellman toward the load threshold, so an
attacker raises the server into under-load mode with traffic it will then be
answered by.

**Why SIP-7 cannot fix this alone.** The gap is not a slip in SIP-7; it is a
consequence of SIP-6's choice of MAC1. WireGuard's first MAC is

```
mac1 = MAC(HASH(LABEL_MAC1 || Spub_r), msg)
```

keyed on a hash of the responder's *static public key*, so a responder verifies
it with one hash and one MAC and can therefore issue a cookie only to callers
who have already proved they know the key. sQUIC's MAC1 is instead keyed on a
Diffie-Hellman shared secret. That buys something WireGuard's does not — MAC1
proves possession of the caller's private key, which is what SIP-2 surfaces as
the peer key and SIP-3 binds an identity to — and it costs the one thing the
cookie stage needs: a check cheap enough to run first.

So the fix is not to reorder SIP-6's steps. There is nothing cheap to move to
the front. One has to be added.

## Specification

All integers are unsigned big-endian.

### Envelope version 3

Version 3 is version 2 (SIP-29) plus a 16-byte MAC0 field, placed after the
nonce and before MAC1. The trailer is **125 bytes**:

```
[ QUIC datagram ][ X25519 (32) ][ Ed25519 (32) ][ ts (4) ][ nonce (8) ][ MAC0 (16) ][ MAC1 (16) ][ MAC2 (16) ][ ver = 3 (1) ]
```

| Field | Width | Meaning |
|---|---|---|
| X25519 | 32 | The caller's transport public key |
| Ed25519 | 32 | The caller's asserted identity, or all zeros (SIP-3) |
| ts | 4 | Epoch seconds, for the replay window |
| nonce | 8 | Random, from a CSPRNG |
| MAC0 | 16 | Proof the caller knows the server's public key, checkable without a curve operation |
| MAC1 | 16 | Proof the caller holds the private key for the X25519 field |
| MAC2 | 16 | Cookie proof, or all zeros (SIP-7) |
| ver | 1 | The version marker of SIP-29; `3` |

A server computes `quic_len = datagram_len - 125` and MUST drop any version 3
Initial whose length is not greater than 125.

### The MAC0 key

```
K0 = SHA-256("squic-mac0-v1" || server_x25519_pub)
```

`server_x25519_pub` is the 32-byte X25519 public key derived from the server's
Ed25519 identity per SIP-6. Both ends compute `K0` with one hash and no key
agreement: the server holds the matching private key, and any legitimate caller
already knows the server's public key, which is the premise of a silent server.

An implementation SHOULD derive `K0` once, when the endpoint is created, rather
than per packet.

`K0` MUST NOT be the cookie-reply key of SIP-7. Both are derived from the same
public key and are separated only by their labels; an implementation that reused
one label for both would key two unrelated constructions identically.

### MAC0

```
MAC0 = HMAC-SHA256(K0, version || quic_datagram || x25519 || ed25519 || ts || nonce)[0..16]
```

The covered range is contiguous: it is every byte of the datagram and the
envelope from offset 0 up to, but not including, MAC0 itself.

The version byte is prefixed, for the reason SIP-29 gives for MAC1. It
authenticates the marker, which a receiver must read before it can verify
anything, and because it comes first, tags computed under different versions are
unrelated even when the remaining input coincides.

Unlike MAC1, MAC0 covers the X25519 field **explicitly**. MAC1 does not need to
— that field is what its shared secret is derived from, so altering it changes
the key and MAC1 fails — but `K0` does not depend on it, so leaving it
uncovered would let it be substituted freely.

MAC0 MUST be compared in constant time.

### Server validation, in order

This section replaces SIP-6's *Server validation, in order*. Steps 3 and 4 are
new; the remainder is SIP-6's, renumbered.

1. **Length.** Drop if the datagram is not longer than the trailer for its version.
2. **Replay window.** Drop if `|now - ts| > 120` seconds.
3. **MAC0.** For an envelope version carrying the field, drop if MAC0 does not
   verify. Versions without the field skip this step.
4. **MAC2.** If the server is under load, require a valid MAC2 or answer with a
   cookie and drop (SIP-7).
5. **Whitelist.** Drop if a whitelist is enabled and the X25519 field is not in
   it (SIP-8).
6. **Diffie-Hellman.** Compute `shared`. Drop if the exchange is non-contributory.
7. **MAC1.** Drop if MAC1 does not verify, compared in constant time.
8. **Identity.** Apply SIP-3's derivation check to the Ed25519 field.

The order is normative, and two adjacencies carry the weight of this SIP. Step 3
precedes step 4, which is what makes the cookie stage silent: a cookie is issued
only to a caller that has already demonstrated knowledge of the server's public
key. Step 3 precedes step 6, which is what makes rubbish cheap: an unauthorised
caller costs one HMAC rather than a curve operation, so the load threshold is no
longer the only thing standing between a stranger and the server's CPU.

A server MUST NOT respond to a packet it drops at any of these steps.

## Rationale

**Why a new field rather than reordering.** Moving SIP-7's MAC2 check behind the
whitelist would silence non-whitelisted callers, and does nothing at all for a
deployment without a whitelist — which is the default and the majority. There is
no ordering of the existing checks that separates "knows the key" from "does
not" without a Diffie-Hellman, because MAC1 is the only thing that makes that
distinction and MAC1 is the expensive step.

**Why keyed on a public value.** MAC0 is forgeable by anyone holding the
server's public key, and that is not a weakness but the design. Its job is to
separate callers who hold the key from callers who do not, at negligible cost;
proving *possession* of the caller's own key is MAC1's job, and MAC1 still runs
afterwards. An implementation MUST NOT treat MAC0 as authentication, and MUST
NOT short-circuit MAC1 for a packet whose MAC0 verified.

**Why not replace MAC1 with WireGuard's construction outright.** Because MAC1
earns its cost. It proves possession of the private key for the X25519 field,
which is what SIP-2's peer key means and what SIP-3's identity binding rests on.
A hash-keyed MAC proves only knowledge of a published value. The two do
different jobs and this SIP keeps both.

**Why before MAC2 rather than after.** After MAC2 the cookie has already been
sent, which is the disclosure being prevented.

**Why 16 bytes.** It matches MAC1 and MAC2, and the tag is not protecting a
secret: forging it requires the server's public key, which an attacker who has
it can use to compute the tag honestly. Truncation to 128 bits is ample against
blind guessing.

**Rejected: making the cookie reply itself prove knowledge of the key.** It
already does — SIP-7 encrypts it under a key derived from the server's public
key, so a caller without the key cannot open it. That protects the cookie's
*contents* and not the server's existence: the reply is a packet arriving from a
port that was supposed to be silent, and its unreadability does not conceal it.

## Compatibility

Version 3 is a new envelope version under SIP-29, which is what makes this
deployable without a flag day. A server MAY accept versions 1, 2 and 3
simultaneously, and the default SHOULD be all three. Following SIP-29's
discipline, the release that introduces version 3 ships clients still emitting
version 2; a later release moves the client default once servers have deployed.

**This SIP does not close the hole on its own, and implementers must not read it
as though it does.** Versions 1 and 2 carry no MAC0 and skip step 3, so while a
server still accepts them, a caller on those versions is challenged under load
exactly as before — an attacker simply sends a version 1 envelope. The property
this SIP specifies is achieved when, and only when, a deployment retires
versions 1 and 2 and accepts version 3 alone. Both implementations expose that
as configuration.

The trailer widths are now 108 (v1), 109 (v2) and 125 (v3). A version 3 Initial
is 17 bytes larger than a version 2 one, which keeps it well inside the
oversized-Initial send path SIP-6 already requires.

## Security considerations

**What it gains.** A caller who does not hold the server's public key is turned
away in silence for one HMAC, at every load level. The cookie stage of SIP-7 no
longer discloses the server's existence. The Diffie-Hellman flood of SIP-7's
motivation now requires the server's public key, which also removes the cheapest
way to fill the peer table of SIP-2.

**What it does not protect against.** Nothing MAC0 does is authentication. An
attacker holding the server's public key — which is published, being the tail of
the connection string — computes MAC0 as easily as any client, and for that
attacker every SIP-7 property is exactly as it was. This SIP raises the floor
from *anyone at all* to *anyone who has the key*; it does not raise it further,
and SIP-8's whitelist remains the control for deployments that need the
distinction.

**Timing.** MAC0 MUST be compared in constant time. It guards a value derived
from public data, so a timing oracle on the comparison discloses little, but the
comparison is on the path of every Initial and the discipline is free.

**Replay.** MAC0 does not change SIP-6's replay window, and is itself replayable
inside it along with the rest of the envelope. See SIP-6, *The replay window,
and what the nonce is not*.

**Downgrade.** An on-path attacker can strip a version 3 envelope's marker, but
not usefully: MAC0 and MAC1 both prefix the version to their input, so an
envelope altered to claim another version verifies under neither. What an
attacker *can* do is send version 1 or 2 traffic of their own while a server
still accepts it, which is the Compatibility section's point restated — the
downgrade is not against a particular connection but against the deployment's
configuration.

## Reference implementation

- squic-rust: `src/mac.rs` (`ENVELOPE_V3`, `mac0_key`, `compute_mac0`,
  `verify_mac0`), `src/conn.rs` (step 3 in `try_version`, emission in
  `build_initial`).
- squic-go: `mac.go` (`EnvelopeV3`, `MAC0Key`, `ComputeMAC0`, `VerifyMAC0`),
  `conn.go` (step 3 in `tryVersion`, emission in `buildInitial`).

Shipped in squic-rust v0.20.0 and squic-go v0.65.0; current as of
squic-rust v0.22.0 and squic-go v0.67.0. Verified across implementations in
both directions on all three envelope versions — 20 of 20, re-run at
promotion.

Deployed on the public exchange `ex.squic.org` since sqexd 0.24.1, which
accepts **version 3 only**. That last part is what turns this document from a
mechanism into the property it claims: MAC0 exists only in version 3, so a
server still accepting 1 or 2 keeps answering callers on those versions with a
cookie under load, whatever they know. The silence arrives on retirement, not
on implementation.
