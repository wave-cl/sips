## Abstract

A SIP-12 session joins two identities that are both connected to the same
exchange. This SIP joins two identities connected to *different* exchanges:
`alice@squic.org` calls `bob@indra.org` while each stays connected only to their
own home exchange, and the two exchanges relay the call between themselves over
an authenticated, allowlisted link. It is the federated form of SIP-12 and
nothing more — the same reciprocal-consent open, the same end-to-end key
agreement neither exchange can complete, with one extra relay hop in the middle.
The caller's home exchange does the cross-domain work (SIP-33 discovery, SIP-38
resolution) on the caller's behalf; the callee's home exchange rings the callee
across its own devices. Neither exchange can read the call, and an exchange
bridges only to peers its operator has named.

## Motivation

Everything the stack needs to *find* a party on another domain already exists.
SIP-33 turns a domain into an exchange, SIP-38 turns a name into an account, and
SIP-28 turns an account into endpoints. So `alice` can already resolve
`bob@indra.org` to a key. What she cannot do is *talk* to it: SIP-12, the
mechanism that carries a call when two parties cannot reach each other directly,
requires both of them to be connected to the one exchange doing the relaying
(its module says so outright — "both already hold a working connection to the
exchange"). The moment Bob is on a different exchange, he is invisible to Alice's
`open`, and Alice is invisible to his.

The two ways to close that gap are to move a party or to join the exchanges.
Moving a party — having Alice also connect to Bob's exchange — throws away the
home-exchange model this stack is built on: an identity has one exchange it is
known at, reachable by its domain, holding its names and its mailbox. Requiring
a caller to hold a connection to every domain they might call is the federation
model email spent thirty years escaping. So the exchanges join instead: Alice's
exchange and Bob's exchange peer, and the call is relayed between them exactly as
SIP-12 relays between two connections today, with the peer link standing in for
the second connection.

This is deliberately the same shape as SIP-35. That SIP gave one exchange a way
to pull a signed log from another, authenticated by SIP-9 and gated by an
operator allowlist. This one gives two exchanges a way to relay a *live* session,
authenticated and gated the same way. SIP-35 is asynchronous and one-directional
and carries signed history; this is real-time and bidirectional and carries
opaque media. They are two uses of one idea — exchanges that know each other's
keys doing work for each other's users — and this SIP reuses SIP-35's trust
machinery wholesale.

## Specification

All integers are unsigned big-endian. Two exchanges take part: **X**, the
caller's home exchange, and **Y**, the callee's. Each party is bound to its home
exchange by its transport identity (SIP-3) as everywhere else; a connection
carrying no identity is refused. The caller is **A**, a device identity connected
to X. The callee is addressed as an **account B**, resolved on Y; the session
binds to whichever of B's devices answers.

### The relay link

X and Y communicate over one long-lived sQUIC connection, the **relay link**,
dialled by the exchange that is placing a call and reused for the life of the
peering. It is brought up exactly as SIP-35 brings up a replica's connection to
an origin:

- The dialling exchange dials with `advertise_identity` set, so the accepting
  exchange reads a MAC1-verified SIP-3 identity — which, for an exchange, is its
  SIP-9 key.
- The dialling exchange pins the peer's SIP-9 key. It obtains the peer's address
  by SIP-33 discovery of the peer's domain (a DNSSEC-Secure `_sqex` record), and
  pins the key the discovery returns; the key is then checked against the
  allowlist below before the link carries anything. **A key is never taken from
  the link itself**, only from discovery cross-checked against configuration,
  which is SIP-35's rule restated.

Unlike a replica link, the relay link is bidirectional and long-lived: once up,
either exchange may originate a call over it, and it carries live media. Control
messages travel as length-prefixed, type-tagged frames on a bidirectional QUIC
stream that either end may write to at any time — the held-open, server-may-write
model SIP-30 established for events, rather than request/response, because a ring
is answered seconds later and by the far side. Media travels as QUIC datagrams
on the same connection.

### Allowlisting

An exchange bridges a call to or from another exchange only if that exchange's
SIP-9 key is in its **`relay_peers`** list — operator configuration that mirrors
SIP-35's `replication_peers` in every respect:

- It is a list of base58 Ed25519 keys, empty by default. An empty list means the
  exchange federates with nobody, and its relay routes **refuse every caller
  identically**, the uniform non-oracle refusal SIP-35 and SIP-24 use so that a
  refused stranger learns nothing.
- It is capped at load, as `replication_peers` is, and a peer being on it is the
  *operational* half of the gate only: it admits the peer's exchange to the link,
  it does not admit any particular caller to any particular callee. Per-call
  consent is the callee's, below.

Being on the list is symmetric in effect but stated on each side: X will accept a
bridged call to a squic.org user only from an exchange in X's list, and Y will
ring an indra.org user only for an invite from an exchange in Y's list. Two
operators federate by each naming the other's key.

Resolution is **not** gated this way. X resolving `bob` at Y uses Y's ordinary
SIP-38 `/name/resolve`, which is public to any authenticated caller; X need not
be an allowlisted peer of Y to *look up* a name, only to ring one.

### Placing a call

The client → exchange step gains one message, because the existing SIP-12 `Open`
names its peer by a bare 32-byte key with no domain and cannot express "an
account on another domain". Alice's client sends X:

```
CallOpen | type: u8 = 0x05 | eph: [32] | tgt_len: u8 | target |
```

`target` is a UTF-8 string, either `name@domain` (SIP-38) or `key@domain` (a
base58 key qualified by its home domain). `eph` is Alice's per-call X25519
ephemeral public key, exactly as SIP-12's `Open` carries. A bare local peer — no
`@domain` — is not this message; that is SIP-12's `Open`, unchanged.

On receiving `CallOpen`, X:

1. Splits `target` into its label/key and its domain, and **discovers the domain**
   (SIP-33) to get Y's address and key. If the domain is X's own, this is a local
   SIP-12 session and the cross-exchange path is not used.
2. Checks Y's key against `relay_peers`; if absent, X answers Alice's call as
   refused (it will not federate with an exchange its operator has not named).
3. Brings up or reuses the relay link to Y, and if `target` was a name, resolves
   it at Y (SIP-38 `/name/resolve`) to the account **B**. A `key@domain` target
   is B directly.
4. Records a pending bridged open keyed by `(A, bridge)` and sends Y an `Invite`.

`bridge` is a 16-byte identifier X chooses at random, unique on the link, by
which both exchanges refer to this bridged session.

### The bridge, and the reciprocal open across it

The control messages on the relay link:

```
Invite   | 0x01 | bridge: [16] | caller: [32] | caller_eph: [32]
                | account: [32] | dom_len: u8 | caller_domain |
Ringing  | 0x02 | bridge: [16] |
Reject   | 0x03 | bridge: [16] | reason: u8 |
Accept   | 0x04 | bridge: [16] | callee: [32] | callee_eph: [32] |
Close    | 0x05 | bridge: [16] | reason: u8 |
```

`caller` is A, `caller_eph` is Alice's ephemeral, `account` is the resolved B,
and `caller_domain` is X's domain — carried so Y and Bob can display who is
calling and so a client has the qualified caller for its own records; routing
uses the link the message arrived on, never the string.

On `Invite`, Y records a **bridge**: `bridge → (caller A reached via this link,
target account B)`. Y then rings B (below). One of two things follows.

- **Bob's device answers.** SIP-12 requires the callee to open toward the caller;
  Bob's client, told the caller's identity by the ring, sends Y an ordinary
  `Open { peer: A, ephemeral: eB }`. A is not connected to Y, so there is no
  local pending open to match — instead Y matches the open against the bridge
  whose `caller == A` and whose `account` is Bob's account (SIP-22). On a match Y
  allocates a local `session_id`, records a session one of whose ends is remote
  (A, via the link and `bridge`), returns Bob the normal SIP-12 `OpenAck`
  carrying `peer_ephemeral = caller_eph`, and sends X an `Accept` naming the
  answering device `callee` and its ephemeral `callee_eph = eB`.
- **Bob declines, is offline, or has no such account.** Y sends X a `Reject` with
  a `reason` (0 no such account, 1 no reachable device, 2 declined, 3 busy, 4
  refused), and X answers Alice's call as failed. `Reject` is the only thing Y
  discloses about B to an allowlisted peer, and it does not distinguish "no such
  account" from "declined" any more finely than the reasons above — a peer that
  may ring B's phone is trusted more than a stranger but is still not owed B's
  presence.

On `Accept`, X matches `bridge` to Alice's pending open, allocates its own local
`session_id`, records the mirror session (Alice local, `callee` remote via the
link), and returns Alice a `CallAck`:

```
CallAck | state: u8 | reason: u8 | session_id: u64 | peer: [32] | peer_eph: [32] | now: u64 |
```

`state` is `ringing` (0), `established` (1) or `rejected` (2); `reason` is a
`Reject` reason and is meaningful only when `state` is `rejected`. `CallAck` is
polled the way an `OpenAck` is — `ringing` means ask again — because the far
side answers seconds later; `established` carries the live session and
`rejected` says the call did not connect and why, so the caller is never left
polling a call that will not come.

`CallAck` differs from SIP-12's `OpenAck` in two things: the explicit
`rejected` state above, and that it carries `peer`, the answering device's
identity. It carries `peer` because Alice addressed an *account* (or a name) and
could not have known which device would answer — this is the account → device
binding that a same-exchange caller never needs, since there the caller names the
device in `Open`. With `peer` and `peer_eph` Alice completes the identical SIP-12
key agreement (`Session::derive` over the two identities and the two ephemerals).
Bob completed his half already, from A and `caller_eph`.

**The end-to-end key is unchanged and neither exchange holds it.** `Session::derive`
mixes the two parties' static identity keys and their two ephemerals; each of the
two static-key Diffie-Hellmans needs a private key only its party holds. X and Y
each see one static *public* key and both ephemeral *public* keys, which is what
a SIP-12 relay already sees and is not enough to derive. A two-exchange path is a
longer courier chain; the couriers are still excluded.

### Ringing the callee

Y rings B the way SIP-36 rings within a channel, minus the channel: a
cross-exchange call has no shared SIP-16 channel to hang a ring on, so the ring is
its own SIP-30 event, delivered **per device** to every device of account B —
the per-device delivery SIP-36 established, because a call that rings one of
Bob's devices and not the others is broken.

```
Event CrossCall | KIND_CROSSCALL | bridge: [16] | caller: [32] |
```

The event is a fixed-size SIP-30 hint and deliberately carries **no caller
domain**: a SIP-30 event is a hint the client acts on, not a payload, and the
action here is to open toward the caller's *key*, which is all the callee needs.
The caller's domain is display only, so it rides the exchange-to-exchange
`Invite` — where the callee's exchange can log who called — rather than the
per-device event, keeping the event the fixed-width hint the rest of SIP-30 is.

A device that accepts opens toward `caller` as above; a device elsewhere in the
account that sees the call accepted or declined stops ringing, by the same
per-device signal fan-out SIP-36 uses (the accepting device is excluded from the
cancellation because it already knows). The ring names the caller and the caller's
domain and nothing Y invented; Y is relaying X's `Invite`, and cannot embellish
it.

### Media relay

Once established, media is SIP-12 datagrams, relayed a hop further. A datagram on
the relay link is:

```
RelayData (QUIC datagram) | bridge: [16] | seq: u64 | ciphertext |
```

When Alice sends a `DatagramFrame { session_id_X, seq, ciphertext }`, X's
datagram forwarder finds the counterpart is remote, looks up `bridge` from
`session_id_X`, and emits `RelayData { bridge, seq, ciphertext }` on the link. Y
looks up `bridge`, finds the local session and the answering device, and emits an
ordinary `DatagramFrame { session_id_Y, seq, ciphertext }` toward that device's
connections. The reverse is symmetric.

**Only `session_id` is rewritten, and only because it is local routing.** SIP-12's
frame nonce is `direction || seq`; it does not include `session_id`, so remapping
the id between the two exchanges' local session numbers changes nothing the
parties authenticate. `seq` and `ciphertext` — everything the parties sealed and
will open — cross both exchanges untouched.

### Teardown

Either party's `/session/close` closes its local session and prompts its exchange
to send the other a `Close`; the receiving exchange closes its local session and
drops the bridge. SIP-36's call states ride the same `Close.reason` and the
control messages above (`Reject` for decline/busy before answer, `Close` for a
hang-up after), so Alice's client can distinguish "declined" from "ended". A
relay link with no live bridges may be kept open or dropped at the operator's
discretion; a dropped link tears down nothing that was not already closed.

### Limits

| Limit | Value |
|---|---|
| `relay_peers` | list of base58 keys, empty default, capped at load as `replication_peers` is |
| `bridge` | 16 random bytes, unique per link |
| Concurrent bridged calls | operator-bounded per link and per exchange; a relay a peer can drive needs a ceiling SIP-12 does not have locally |
| Link connections | `max_connections` applies to the link as to any connection |
| `Reject.reason` | 0 no account · 1 unreachable · 2 declined · 3 busy · 4 refused |

## Rationale

**Always relay; no direct-connect attempt first.** SIP-25 introduces two peers so
they connect directly, the exchange out of the path, and would remove the media
from both exchanges entirely. It was not chosen as a first step here for the
reason it is still Draft: it needs a NAT type that cannot be assumed and a
transport capability whose success across two real home networks nobody has yet
demonstrated. A call that works only behind cooperative NATs is not a call that
works. Relaying through both exchanges works behind any NAT, at the cost of two
exchanges carrying opaque traffic — the same trade SIP-12 makes against SIP-25
within one exchange, made again across two. A future revision may try a
cross-exchange SIP-25 rendezvous first and fall back to this relay; that is
additive and is left to when SIP-25 has left Draft.

**An allowlist, not open federation.** The useful-sounding version is the email
one: any exchange may ring any user. It was rejected on the grounds the whole
corpus rejects unbounded reachability (SIP-24's door, SIP-4's withheld beacon,
SIP-12's single answer): a user's exchange ringing their phone because an
arbitrary domain asked is an abuse surface — spam calls, reflection, presence
probing — with no operator in the loop. Requiring both operators to name each
other's key makes federation a decision somebody made, which is the same
principle SIP-35 applies to replication and SIP-24 to admission. It is more
closed than email and deliberately so; a deployment that wants openness can grow
its list, and a future consent-gated open mode (a callee opting in to
cross-domain reachability) is the named way to widen it without discarding the
operator's veto.

**The caller's exchange resolves, not the caller.** Alice could discover Y and
resolve `bob` herself, then hand X a bare key — the CLI already resolves names
against a foreign domain this way. Having X do it instead was chosen so the
client speaks to exactly one exchange (its own) for a call, so there is one
authenticated resolution path rather than the client holding transient
connections to arbitrary domains, and so the name → account step and the ring
happen at the same place. It concedes that X makes the outbound discovery and is
trusted to make it honestly — which it is trusted for regardless, since it is
about to carry the call.

**Why the initiator learns the device on answer.** A same-exchange SIP-12 caller
names the callee's device in `Open` and the exchange matches it. A cross-exchange
caller cannot: the callee is an account with several devices, any of which may
answer, and which one is not known until one does. So the caller addresses the
account and the exchange returns the answering device in `CallAck`. This is not a
weakening of SIP-12's identity model — the session still binds two device
identities and the key agreement is still over those two — it is the account →
device resolution made explicit for the one caller who could not do it in advance.

**Why it reuses SIP-35's link and not a new trust scheme.** The hard parts of an
exchange-to-exchange link — mutual SIP-9 authentication, an operator allowlist,
the discipline of never trusting a wire-supplied key, the uniform refusal — are
exactly the parts SIP-35 already built and audited. Inventing a second scheme for
the same job would be a second thing to get wrong, which is the mistake SIP-1
exists to prevent. What is new here is live media over the link and the bridge
bookkeeping, not the trust.

## Compatibility

New client message (`CallOpen`/`CallAck` in the session namespace, type `0x05`
which was unused there), a new relay-link protocol with its own control messages
and datagram framing, a new SIP-30 event kind (`CrossCall`), and a new
`relay_peers` configuration key. No existing wire format changes: an exchange
without this SIP has an empty `relay_peers`, brings up no relay links, refuses the
relay routes identically, and never emits a `CrossCall` — it simply cannot place
or receive a cross-exchange call, and a same-exchange SIP-12 call is untouched. A
client without it never sends `CallOpen`. There is no flag day, and the two
implementations need not move together.

Requires SIP-3 for the authenticated identities at both ends and on the link;
SIP-9 for the exchanges authenticating each other; SIP-12 for the session and its
key agreement, of which this is the federated form; SIP-22 to resolve an account
to the devices Y rings; SIP-30 for the per-device ring event; SIP-33 to discover
the far exchange; and SIP-38 for the `name@domain` the caller hands its own
exchange. It composes SIP-35's peering pattern without depending on replication
itself. It reads none of `sqns`.

## Security considerations

**Neither exchange can read the call, and adding one did not change that.** The
property is SIP-12's and rests on `Session::derive` needing a private key from
each party; X and Y are each a relay that sees public keys and ciphertext. The
new exposure is not confidentiality but the two facts a relay learns by relaying:
that A called B, and the traffic pattern of the call. X already learns this for
its own user; Y learns it for its own user; the link discloses to X that its user
reached an account on Y and to Y that an account on X reached its user — the
communication graph across the two domains, which is inherent in relaying between
them and is why federation is an operator decision rather than a user one.

**The name binding is trusted exactly as far as SIP-38 says.** X resolves `bob`
at Y, and Y asserts which account `bob` means; a dishonest Y can substitute an
account, and X cannot check it, precisely the man-in-the-middle-on-the-binding
SIP-38 documents. This SIP adds no new trust there — it is the same resolution
SIP-38 already specified, performed by X rather than by Alice's client — and the
same mitigations apply: out-of-band verification, or SIP-38's named upgrade to an
account-signed claim. What this SIP must add is that X is now trusting Y's key
*binding* and about to send its user into a call on the strength of it, so an
operator federating with Y is vouching for Y's honesty about its own namespace to
its own users.

**The allowlist is the abuse boundary and must fail closed.** An empty or
unmatched `relay_peers` refuses identically and rings nobody; this is the only
thing standing between a user's devices and an arbitrary exchange ringing them, so
the refusal must be uniform (no oracle for who is or is not a peer) and the
default must be empty. A compromised allowlisted peer can ring an operator's users
and consume relay capacity up to the per-exchange ceiling; the ceiling bounds the
resource abuse, and the callee's own decline bounds the nuisance, but an operator
who lists a key is trusting the exchange behind it not to abuse the reachability
that listing grants. Listing is revocable — removing a key stops new bridges to
and from it at once — but does not tear down calls already up, which end
normally.

**Per-call consent stays with the callee.** Being an allowlisted peer lets X ask Y
to ring B; it does not admit X to B. B's devices ring, B accepts or declines, and
a decline is a `Reject` that tells X only that the call did not connect. An
exchange must not let an allowlisted peer distinguish "declined" from "no such
account" or "offline" beyond the coarse reasons, or the link becomes the presence
oracle the door in SIP-24 refused to be.

**Resource exhaustion on the link.** A bridged call ties up capacity on both
exchanges and a datagram path between them. Without a ceiling a peer — or a flood
of calls through an honest peer — could exhaust it, the shape SIP-12 has locally
and never bounded because a local session is bounded by `max_connections`
already. Here the bridge count is its own quantity and MUST be capped per link and
per exchange, so a busy or hostile peer cannot convert the link into an
open-ended allocation.

## Reference implementation

`sqex`. Written *after* this document rather than alongside it — the first SIP
in the set to be specified ahead of its code — and the implementation composes
existing seams as promised: the `H3Client` dial with `advertise_identity` and the
`Peer.identity`/allowlist check that SIP-35's replica and peering routes use, for
the link and its gate; `Sessions`/`counterpart` and the datagram forwarder, for
the local half of each bridged session and the point at which a remote
counterpart diverts a frame onto the link; `Session::derive`, unchanged, for the
key; and the SIP-30 per-device event streams, for the ring.

- `sqex-proto::relay` — the `Control` messages, `RelayData`, the `sqex-relay`
  ALPN and the `Reject`/`Close` reasons; `session::{CallOpen, CallAck}`;
  `events::Event::CrossCall`.
- `sqexd::relay` — the relay link (raw `quinn` bidi stream for control,
  datagrams for media), the bridge bookkeeping (a high-bit session-id space
  disjoint from local sessions), `place_call`, `try_answer`, `close_bridge`, and
  the divert/inject datagram paths. Wired into the accept loop (ALPN dispatch),
  `forward_datagrams`, and the `/session/{open,call,close}` routes. `relay_peers`
  and `max_bridges` are operator configuration.
- `sqex-voice` — `call name@domain` places one, `answer` picks the next one up.

An end-to-end test bridges two `sqexd` instances and confirms media crosses both
and each end decrypts what the other sealed, alongside a negative control that an
unfederated call is refused.

**Three things building it settled, and this document now reflects.** The
`CrossCall` event is a fixed-size hint carrying no caller domain, because a
SIP-30 event is a hint and not a payload — the domain rides the `Invite`
instead. `CallAck` carries an explicit `rejected` state and reason, because a
polling caller needs to be told a call will not connect rather than poll
forever. And **relay peers are configured, not discovered**: a peer is a
`{ domain, key, addr }` in configuration, the same static, pin-from-config
peering SIP-35 uses, rather than the `sqex_discovery::discover` this document's
body describes. Configuration is what makes the link testable across two local
exchanges and keeps the key out of the wire; SIP-33 discovery of the peer by
domain is the production refinement, and the point at which `sqexd` would call
`sqex_discovery` for the first time.

**Active** on the strength of that implementation and its deployment. The bar for
an exchange↔exchange wire here is the one **SIP-35** set — it went Active on a
single implementation with both ends the same `sqexd`, because there is one
exchange and a replica link has no independent second party — and this meets it
and then some: `sqex-proto` unit tests, an end-to-end suite bridging two `sqexd`
instances with a negative control, deployment to `ex` (squic.org) and
`ex.indra.org`, and a live `alice@squic.org` ↔ `bob@indra.org` call carrying Opus
both ways across the two exchanges. An earlier draft of this section held out for
a second implementation before promotion; that was the *transport*-SIP bar
(Rust and Go, for the shared sQUIC wire) applied to an exchange-layer proposal it
does not govern, and it is corrected here.

The one honest residual, stated the way SIP-35 stated its own: **both ends of the
relay wire are the same code.** A second, independent implementation of the link
would check the specification against something other than the source it was
written from, and none exists yet. That is a weaker check than the
cross-implementation harness a transport SIP earns, and it is the first thing a
Go exchange, if one is ever built, should exercise.
