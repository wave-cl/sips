## Abstract

An application holding an accepted sQUIC connection should be able to ask who
is calling, and get back the caller's Ed25519 public key, without running an
authentication exchange of its own.

This SIP specifies that the client presents its identity as a self-signed
Ed25519 certificate in the TLS handshake, and the server reads it from the
established connection. Neither implementation needs a new API to do this. A
second design was considered and is recorded in the rationale.

## Motivation

A sQUIC client stamps its X25519 public key into every Initial packet and
proves possession of the matching private key by MAC1, computed over a
Diffie-Hellman shared secret. The server verifies this before quinn sees the
packet: an Initial that fails is dropped in silence. By the time an application
accepts a connection, a key has been proven.

No application uses this. sqsshd, holding a connection whose peer is already
proven, runs a second Ed25519 signature challenge at the application layer to
learn who is calling. The work is done twice and only the second result is ever
read.

Two things stand in the way, and they are separate problems that have been
easy to conflate:

- **The proven key never leaves the transport.** It is validated inside
  `validate_and_strip`, in the UDP receive path, before the QUIC state machine
  has produced a connection object. `ServerListener` offers no accessor and
  quinn's connection types carry nothing of ours.
- **The proven key is the wrong key.** Every identity in this ecosystem — sqns
  records, sqssh `authorized_keys`, the base58 strings people paste — is named
  by an Ed25519 public key. The transport only ever observes X25519, and the
  reverse map is 2-to-1 rather than one-way, so an observed X25519 key cannot be
  turned back into the name anyone uses.

A mechanism that solves only the first leaves the application holding a key it
cannot name. That is the fault line this SIP is built around, and it is why the
answer is not simply to surface what MAC1 already verified.

## Requirements

These are stated ahead of the specification so that any competing proposal can
be judged against the same bar, and so that the reason for the design is
legible without reading it.

**R1 — The identity delivered is the Ed25519 public key, or nothing.** An
implementation MUST NOT present an X25519 key as though it were an identity.
Where only an X25519 key is available, the mechanism is incomplete and MUST say
so rather than substitute.

**R2 — The identity is proven, not asserted.** Delivering a key the caller
merely claimed, without the transport or the handshake having established
possession of the corresponding private key, does not satisfy this SIP.

**R3 — Absence is representable.** A caller with no persistent identity is
legitimate. The mechanism MUST be able to report that there is no identity,
distinctly from reporting a zero or placeholder key.

**R4 — Identity is not authorisation.** The mechanism answers who is calling.
Whether they may do what they are asking is the application's decision, and the
API SHOULD NOT invite the two to be conflated.

**R5 — Degenerate keys are rejected.** A small-order peer key makes the
Diffie-Hellman non-contributory: the shared secret is all zeros whatever the
server's key is, so a caller who has never seen the server's public key can
compute it in advance and forge a MAC1. Any mechanism that reports identity
while accepting such a key would report an identity that authenticated nothing.

**R6 — Both implementations can support it through supported APIs.** SIP-1
requires a Standards Track SIP touching the wire to have both a Rust and a Go
implementation before it reaches Active. A mechanism reachable in one language
only, or reachable in the other only by depending on unexported internals or
repurposed hooks, does not clear this bar.

## Specification

### The certificate

A client with a persistent identity MUST present a self-signed X.509
certificate whose SubjectPublicKeyInfo carries its Ed25519 public key, signed
by the corresponding private key.

A client with no persistent identity MUST NOT present a certificate.

The certificate is an envelope for a key, not a credential in its own right. It
carries no meaningful issuer, and its validity window is not consulted.
squic's existing `self_signed_cert()` already produces exactly this shape for
the server; the same routine serves the client.

### Server verification

The server MUST request a client certificate and MUST accept the connection
whether or not one is presented.

For a presented certificate, the server MUST verify:

1. the certificate parses and its SubjectPublicKeyInfo holds an Ed25519 key;
2. the key decompresses to a valid Edwards point;
3. the handshake's CertificateVerify is valid over the transcript, under that
   key.

The server MUST NOT require a chain to a certificate authority, an unexpired
validity window, a matching subject name, or any extension. The key is the
identity; nothing else in the certificate is consulted.

If any check fails the server MUST fail the handshake rather than treat the
peer as anonymous. A malformed claim is not the same as no claim.

### What the application sees

The identity of an accepted connection is the Ed25519 public key from the
verified certificate, or absent where no certificate was presented. Absent
MUST be distinguishable from any key value, satisfying R3.

Both implementations expose this already, and `ServerListener::accept()` does
not change:

- **Rust** — `quinn::Connection::peer_identity()` returns the peer certificate
  chain (`quinn-0.11.9/src/connection.rs:569`).
- **Go** — `Conn.ConnectionState().TLS.PeerCertificates[0]`.

Implementations SHOULD offer an accessor returning the 32-byte key directly,
so that every caller does not re-implement the extraction.

### Relationship to the transport key

The Ed25519 identity and the X25519 key verified by MAC1 are **separate
credentials, separately proven, and this SIP does not require them to match.**

Each answers a different question. MAC1 and the whitelist decide whether the
server is willing to spend a handshake on this caller at all; they run in the
UDP path, before any state is allocated, and that is what makes the silent
server work. The certificate decides who the caller is, and it is checked
inside a handshake the server has already agreed to perform.

Two consequences follow, and both are intended:

- A deployment using a whitelist necessarily requires clients to use persistent
  transport keys, because that is what the whitelist gates on.
- A deployment without one MAY let clients use **ephemeral** transport keys
  while still presenting a persistent identity. Such a client shows no stable
  identifier in plaintext on the wire, because its identity travels in the
  encrypted handshake flight. This is a strictly better privacy position than
  the transport can offer on its own, and requiring the two keys to match would
  destroy it.

Where a deployment does gate on a whitelist, it SHOULD derive the whitelisted
X25519 keys from the Ed25519 identities it authorises, so the two lists cannot
silently disagree. This is operational hygiene, not a security requirement:
neither credential can be presented without its private key, whatever the other
one says.

### Degenerate keys

The server MUST reject a client X25519 key of small order, and MUST reject an
all-zero Diffie-Hellman result, before MAC1 is considered verified (R5). This
belongs in the transport and is independent of the certificate check.

## Rationale

**Why state requirements before the mechanism.** The first draft of this SIP
specified a mechanism and treated it as the definition of the goal. That made
an X25519 key look like an answer, and pushed the actual question — how does an
application learn a name it can act on — into a second document, where it read
as a follow-on rather than as the unfinished half.

**Why a certificate rather than a signed statement of our own.** sqsshd's
Ed25519 challenge is a hand-rolled TLS client authentication: a nonce, a
signature, and a transcript binding that TLS already specifies and both stacks
already implement. Replacing it with the standard one removes code from the
place where divergence between two implementations is most expensive.

**Why the validity window is ignored.** These certificates are envelopes
generated on demand from a key that is the real credential. An expiry would
express nothing about the key, and honouring one would introduce a clock
dependency into a handshake that has none.

**Why not report a converted key.** Converting an observed X25519 key into a
plausible Ed25519 key would be lying about what was proven: the map admits two
preimages, and for an ephemeral caller it admits none. R1 forbids it for that
reason and not for tidiness.

### Alternative considered: the DCID join

The rejected design carried the MAC1-verified X25519 key from the receive path
to the accept path, joined to the connection by the Destination Connection ID
present in the same Initial. The application would then learn the caller's
Ed25519 name by a separate claim exchange, in which the caller states its
identity and the server checks that `ed25519_public_to_x25519(claimed)` equals
the observed key — the mechanism specified in SIP-3.

Its one real advantage is that it changes no wire bytes, and either
implementation could ship it alone.

It was rejected on three grounds.

**It does not satisfy R1 by itself.** It delivers an X25519 key, which is not a
name. Reaching a name requires SIP-3 on top: a claim message, a derivation
check, and a cache, specified at the Exchange layer — so a plain sQUIC server
would not get an identity from it at all without implementing the claim itself.
Two documents and a round trip arrive where one document and no round trip
also arrive.

**It does not satisfy R6.** quic-go v0.59.0 does not expose the original
destination connection ID: `origDestConnID` is unexported
(`connection.go:130`), `ConnectionState` carries no connection ID field, and
`Transport.ConnContext` receives only `RemoteAddr` and `AddrVerified`
(`interface.go:183`) — not the CID, and the address is unusable as a join key
because migration changes it. Correlating by read order is impossible by
construction: received packets pass through a buffered channel and Initials are
handled on a separate goroutine (`server.go:65,285,394`). The one route that
exists — injecting a holder via `ConnContext` and filling it from
`config.Tracer`, which does receive `origDestConnID` (`server.go:804-810`) —
uses the qlog tracer as an identity channel, and R6 excludes it for that
reason. The remaining path is upstreaming an accessor to quic-go, which is a
reasonable thing to propose but not a thing to depend on.

**It carries security-relevant state that this design does not have.** The join
table is reachable by any peer that can pass MAC1, so entries must expire on a
timer or the table grows without bound. Worse, two Initials bearing the same
DCID and different keys cannot be resolved safely by any rule — last-write lets
an on-path attacker overwrite a victim's entry, first-write lets it pre-empt
one — so a contested DCID has to be poisoned and the lookup failed. Correct,
but it is a class of hazard that arises only from moving the key across the
layer boundary by hand.

### Comparison as it stood

|                                    | Adopted — TLS client auth           | Rejected — DCID join (+ SIP-3)           |
| ---------------------------------- | ----------------------------------- | ---------------------------------------- |
| Satisfies R1 alone                 | yes                                 | no — needs SIP-3                         |
| Key delivered                      | Ed25519                             | X25519, named later by claim             |
| Wire change                        | ~340 bytes, no extra RTT            | none                                     |
| Implementations must move together | yes                                 | no                                       |
| Rust public API                    | none — `peer_identity()` exists     | new accessor                             |
| Go public API (R6)                 | standard                            | unavailable; needs upstreaming or a fork |
| Per-handshake server state         | none                                | table entry, expiry and poisoning rules  |
| Identity visible to a passive observer | no — encrypted handshake flight | yes — X25519 key is plaintext in Initial |
| Documents needed                   | this one                            | this one and SIP-3                       |
| Callers with no identity           | reported absent                     | X25519 key with no name                  |

The wire change was the one point on which the rejected design was clearly
ahead. It was judged affordable here: squic is pre-1.0, both implementations
are ours, the deployed surface is one server and a handful of clients, and the
two implementations have already been changed in lockstep twice this month.

## Compatibility

**This changes the wire.** The client's Certificate and CertificateVerify are
added to the handshake. They ride in the same flight as Finished, so there is
no additional round trip, but the flight grows by roughly 340 bytes — squic's
Ed25519 self-signed certificate measures 250 bytes, plus signature and framing.
That flight is not subject to the amplification limit.

Old and new peers do not interoperate in the direction that matters. A server
that requires a certificate will fail handshakes from clients that do not send
one, so **both implementations and the deployed clients must move together.**
Per SIP-1 this SIP cannot reach Active until both exist.

Servers MUST request but MUST NOT require a certificate, so a server that has
adopted this SIP continues to accept clients that have not — they are simply
reported as having no identity. That makes a staged rollout possible: deploy
servers first, then clients, then move applications from their own
authentication to this one.

No embedder API breaks. `ServerListener::accept()` is unchanged, and the
identity accessor is additive.

## Security considerations

**This does not make the transport more trustworthy.** It makes an
authentication that was already happening — twice, in sqsshd's case — happen
once, in the standard place. MAC1 verification is unchanged, and a caller that
could not previously reach the handshake still cannot.

**Identity is not authorisation** (R4). An application must still decide
whether the named identity may do what it is asking. Delivering a name makes
the two easier to conflate, and implementations should document the
distinction.

**CertificateVerify is what proves possession, not the certificate.** A
self-signed certificate is a reusable artifact with no audience binding;
anyone who has seen one can replay it. CertificateVerify is bound to the
handshake transcript and cannot be. Implementations MUST NOT accept an identity
on the strength of a presented certificate alone.

**A malformed certificate must fail the handshake, not degrade to anonymous.**
Treating a failed check as absence would let an attacker present a broken
claim and be admitted as an anonymous caller, which on a server that permits
anonymous callers is a downgrade the peer chooses.

**Identity is not disclosed to observers.** The client's Certificate and
CertificateVerify travel in the encrypted handshake flight, so a passive
observer does not learn who is connecting. This is an improvement on the
status quo rather than parity: squic's X25519 client key is appended to the
Initial in plaintext and read straight from the datagram, so a persistent
client already presents a stable identifier to anyone watching the wire. A
deployment that does not use a whitelist can now remove that identifier
entirely by using an ephemeral transport key, and keep its identity.

**Branching on identity introduces timing.** A server with a whitelist already
responds differently to known and unknown keys, which is the intent. A service
that now varies its behaviour by identity may introduce differences that were
not there before.

**The X25519 secret is signing-equivalent to an Ed25519 private key.** Both
derive from one scalar, and an Ed25519 signature needs only the scalar. This
SIP exposes *public* keys and so adds no risk itself, but the corresponding
secret — which the transport holds for the life of every connection — is as
sensitive as a signing key, not merely a session key.

**Small-order keys must be rejected** (R5).

## Reference implementation

None yet. Required in both Rust and Go before this SIP can reach Active, per
SIP-1.

SIP-3 specified the claim exchange that the rejected design needed to reach an
Ed25519 name. It has no purpose under this specification and is withdrawn.
