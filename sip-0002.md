## Abstract

sQUIC proves the caller's identity while validating the Initial packet and then
discards it. This SIP makes the authenticated peer key available to the
accepting application, so that services need not re-authenticate a peer the
transport has already proven.

Two designs would do this. The specification below joins the validated key to
the connection by Destination Connection ID; the section *Alternative: TLS
client authentication* sets out the other. They are not equivalent — they
differ in what key they deliver, whether they touch the wire, and whether Go
can implement them at all — and this SIP does not yet choose.

## Motivation

A sQUIC client stamps its X25519 public key into every Initial packet and
proves possession of the matching private key by MAC1, computed over a
Diffie-Hellman shared secret. The server verifies this before quinn sees the
packet: an Initial that fails is dropped in silence. By the time an application
accepts a connection, the peer's identity is already established
cryptographically.

No application uses this. sqsshd, holding a connection whose peer is already
proven, runs a second Ed25519 signature challenge at the application layer to
learn who is calling. The work has been done twice and the second time is the
only one anybody reads.

Worse, it cannot be avoided today: the key is validated inside
`validate_and_strip` and then dropped on the floor. `ServerListener` offers no
accessor and quinn's connection types carry nothing of ours. An application
that wants to trust the transport's answer has no way to ask for it.

## Specification

### What is exposed

The peer's **X25519 public key**, 32 bytes, as verified by MAC1.

This is the only key material the transport possesses. The client transmits an
X25519 key, and the reverse of the Ed25519 → X25519 map is **2-to-1, not
one-way**: `u` depends only on the Edwards `y`, so the sign bit for `x` is
discarded, and two Ed25519 keys differing in the top bit of byte 31 produce
byte-identical X25519 keys. Reversing therefore yields two candidates and no way
to choose between them — and for a client using an ephemeral key there is no
Ed25519 preimage at all.

Callers that name identities by Ed25519 key — which is every service in this
ecosystem — must convert their candidates forward and match, or use the binding
described in SIP-3.

Implementations MUST NOT present the X25519 key as though it were an Ed25519
identity.

### Joining the key to the connection

The key is learned during Initial validation, before the QUIC state machine has
produced a connection. Implementations MUST associate the two using the
**Destination Connection ID** carried in that same Initial packet.

The DCID is at a fixed offset in the long header:

```
byte  0        first byte (0xC0..0xCF for Initial)
bytes 1..5     version
byte  5        DCID length (0..20)
bytes 6..6+n   DCID
```

On a MAC1 verification that succeeds, the server records `DCID -> peer key`.
The accepting application looks the connection up by the DCID the QUIC layer
reports as the connection's original destination CID.

Implementations MUST NOT join on the peer's source address. QUIC connection
migration changes it, and a NAT rebinding mid-handshake would silently attach a
connection to the wrong identity — a misidentification, not merely a lookup
failure.

### Lifetime of the table

Entries MUST be removed once the connection is accepted, and MUST expire on a
timer regardless.

The timer is not optional. Under the cookie defence of SIP-2's sibling
mechanism, and whenever an Initial is dropped for any reason, a validated key
may be recorded for a connection that never completes. Without expiry the table
grows for as long as the process runs, and is trivially filled by any peer that
can pass MAC1.

A second Initial bearing a DCID already in the table MUST be handled by
comparing the keys:

- **Same key.** An ordinary retransmission. The entry is unchanged; recording
  it again is idempotent.
- **Different key.** The DCID is ambiguous, and the server has no sound way to
  decide which claimant owns it. The entry MUST be poisoned: lookups for that
  DCID MUST fail for as long as it remains in the table, and MUST NOT return
  either key.

Poisoning rather than resolving is deliberate; see the security considerations.
The cost is one failed handshake, and the alternative is a wrong answer.

### API shape

`ServerListener::accept()` currently yields `quinn::Incoming`. It MUST yield
the peer key alongside. This is a breaking change to a public API and requires
a minor version bump in both implementations.

In Rust, `quinn::Incoming::orig_dst_cid()` supplies the join key at accept
time. Go implementations must obtain the equivalent from quic-go.

## Rationale

**Why the DCID and not the source address.** The address is available and
tempting, and it is wrong: it is not stable across migration, and the failure
mode is attributing a connection to the wrong peer rather than failing to find
one. The DCID is chosen by the client, is present in the very packet being
validated, and is exposed by the QUIC layer at accept — it is the only
identifier common to both ends of the join.

**Why not expose an Ed25519 identity.** Because the transport does not have
one and cannot derive one. A convenience that converted or guessed would be
lying about what was proven. SIP-3 addresses the mapping honestly, at a layer
that can afford a signature.

**Why not keep the application-layer challenge.** It is not harmful, only
redundant, and redundancy in authentication code is where divergence hides. A
service that trusts the transport has less code to get wrong.

## Alternative: TLS client authentication

The specification above is one of two designs that satisfy the motivation. This
section records the other in enough detail to choose between them. Neither is
yet adopted.

### The mechanism

The server enables TLS client authentication with a verifier that accepts a
self-signed Ed25519 certificate and records its key. The client presents a
certificate built from its Ed25519 identity key. The server reads the identity
once the handshake completes.

Both languages already expose this:

- **Rust** — `quinn::Connection::peer_identity()` returns the peer certificate
  chain (`quinn-0.11.9/src/connection.rs:569`). `ServerListener::accept()` does
  not change at all.
- **Go** — `Conn.ConnectionState().TLS.PeerCertificates[0]`.

The pieces exist in squic already, in the wrong direction: `self_signed_cert()`
builds precisely this certificate for the *server*, and `PinnedKeyVerifier` is
the mirror image of the verifier the server would need. The substantive change
is `server_tls_config()`'s `with_no_client_auth()`.

Normatively:

- A client configured with a persistent identity MUST present a self-signed
  certificate whose SubjectPublicKeyInfo carries its Ed25519 public key.
- A client without one MUST NOT present a certificate. The server MUST report
  such a peer as having no identity — absent, not zero.
- The server MUST accept the certificate on a valid CertificateVerify alone. It
  MUST NOT require a chain to a CA, an unexpired validity window, or a matching
  name. The key is the identity; the certificate is only its envelope.
- Possession of the identity is still not authorisation.

### What it costs

**It is a wire change.** The client's Certificate and CertificateVerify ride in
the same flight as Finished, so no extra round trip — but the bytes are real:
squic's Ed25519 self-signed certificate measures 250 bytes, so with the
signature and framing the flight grows by roughly 340 bytes. That flight is not
subject to the amplification limit.

**Both implementations must move together.** This is the DCID design's clearest
advantage, and it is not a small one: the DCID join is a purely local change
that either implementation could ship alone.

**Identity arrives after the handshake, not at accept.** Nothing is lost by
this. MAC1 and the whitelist already refuse unwanted callers strictly earlier
than accept, so the connections that reach this point are ones the server was
willing to have.

**Ephemeral callers get no identity at all**, where the DCID design would at
least hand over an X25519 key. Whether that key is worth anything is doubtful —
SIP-3 already notes there is no Ed25519 preimage to recover, because none ever
existed.

### What it buys

**No join table**, and so no expiry requirement, no attacker-reachable state,
no DCID parsing, and no exposure to the Retry hazard.

**Stock public APIs in both languages.** See below; this is the decisive point.

**Ed25519 directly**, which is what every consumer in this ecosystem names
identities by. It subsumes most of SIP-3 for callers that have an identity at
all.

**It actually retires the application-layer challenge.** sqsshd's Ed25519
challenge is a hand-rolled TLS client authentication, and this replaces it with
the standard one. The DCID design cannot retire it: it delivers an X25519 key
that sqsshd cannot act on until SIP-3 ships behind it.

### The Go problem

This has to be stated plainly, because SIP-1 requires both implementations
before a Standards Track SIP that touches the wire can reach Active.

**quic-go v0.59.0 does not expose the original destination connection ID.**

- `origDestConnID` is unexported (`connection.go:130`), and `ConnectionState`
  carries no connection ID field.
- `Transport.ConnContext` — the only hook that runs while the Initial is being
  handled — receives a `*ClientInfo` carrying `RemoteAddr` and `AddrVerified`
  and nothing else (`interface.go:183`). Not the CID, and the address is the
  join key this SIP forbids.
- Correlating by read order is impossible by construction: received packets
  pass through a buffered channel and Initials are handled on a separate
  goroutine (`server.go:65,285,394`), so the code that validates a packet and
  the code that accepts the connection are deliberately decoupled.

One route does exist. `config.Tracer` is invoked with the post-`ConnContext`
context and with `connID` set to `origDestConnID` (`server.go:804-810`), so a
mutable holder injected in `ConnContext`, filled by the tracer, and retrieved
through `Conn.Context()` would carry the key across. That uses the qlog tracer
as an identity channel and would be at the mercy of every quic-go release.

The DCID design therefore reaches Active only by forking quic-go, upstreaming
an accessor, or accepting that hack. Client authentication needs none of the
three.

### Comparison

|                                    | DCID join (specified above)              | TLS client auth                     |
| ---------------------------------- | ---------------------------------------- | ----------------------------------- |
| Wire change                        | none                                     | ~340 bytes, no extra RTT            |
| Implementations must move together | no                                       | yes                                 |
| Rust public API                    | new accessor, or a break                 | none — `peer_identity()` exists     |
| Go public API                      | unavailable; fork, upstream, or the hack | standard                            |
| Key type delivered                 | X25519                                   | Ed25519                             |
| Requires SIP-3                     | yes                                      | no, for callers that have identity  |
| Per-handshake server state         | table entry, expiry mandatory            | none                                |
| Identity available                 | at accept                                | after handshake                     |
| Ephemeral callers                  | X25519 key with no preimage              | no identity                         |

### What is undecided

**Whether the wire change is acceptable.** The usual answer is no, and the
usual answer is calibrated for protocols with strangers on them. This one has
neither: squic is pre-1.0, both implementations are ours, the deployed surface
is one server and a handful of clients, and the two implementations have
already been changed in lockstep twice this month. Against that, the DCID
design could ship in Rust alone within a week, and client authentication cannot
ship until Go moves too.

**Whether to require that the certificate key derive to the MAC1 key.** It is
tempting, and it would need the very join table this alternative exists to
delete — the TLS verifier runs inside the crypto stack with no access to the
MAC1 key. It is also unnecessary for authentication: the certificate proves
possession of the Ed25519 key by itself, so a caller cannot claim an identity
it does not hold, whatever key it used for MAC1. Leaving it unchecked does
decouple the whitelist (X25519, a denial-of-service gate) from identity
(Ed25519, an authorisation input). That is a housekeeping wart rather than a
vulnerability, but this SIP should choose between them out loud rather than
leave the reader to infer it.

## Compatibility

No wire change: the key is already transmitted and already verified. This
exposes existing information.

The API change is breaking for embedders. Both implementations should move
together so that services can be written against one behaviour, though nothing
on the wire prevents a mixed deployment.

This paragraph describes the DCID design only. Under TLS client authentication
the answers invert: there is a wire change, both implementations must move
together, and no embedder API breaks. The comparison table in that section
carries the full accounting.

## Security considerations

**This does not make the transport more trustworthy — it makes what it already
proves legible.** MAC1 verification is unchanged; a caller that could not
previously authenticate still cannot.

**The key proves possession, not authorisation.** An application must still
decide whether that identity may do what it is asking. Exposing the key makes
it easier to conflate the two, and implementations should document that the
answer to "who is this" is not an answer to "may they".

**Whitelisting already leaks a little.** A server with a whitelist responds
differently to known and unknown keys — the unknown are dropped in silence,
which is the intent. This SIP does not change that, but a service that now
branches on peer identity may introduce timing differences that were not there
before.

**The join table is attacker-reachable.** Any peer that can pass MAC1 can add
an entry. The expiry requirement above is a security requirement, not
housekeeping.

**A contested DCID must not be resolved, only refused.** An attacker who can
observe a victim's Initial learns its DCID, and can send its own Initial
carrying the same DCID and its own key. If the table resolves the collision by
any rule — first write wins, last write wins — then one of the two connections
is attributed to the wrong identity, and which one depends on packet arrival
order the attacker partly controls. Neither rule is safe: last-write lets the
attacker overwrite the victim, and first-write lets the attacker pre-empt a
victim whose Initial it can anticipate or delay.

This is why the specification poisons the entry instead. A failed lookup is a
denial of service against a single handshake, which an attacker positioned to
see the DCID could accomplish anyway by dropping packets. A successful lookup
returning the wrong key is a misidentification the application has no way to
detect, and it is the one outcome the transport must never produce.

Two limits are worth stating, so the severity is not overread. The attacker
must pass MAC1 in its own right, so it must hold a key the server accepts —
under a whitelist, this is an escalation available to an already-authorised
peer, not to a stranger. And it must learn the DCID, which for a first Initial
is at least eight random bytes, so in practice it must be on-path. Accidental
collision between honest clients is negligible at that width, and costs those
clients a handshake rather than their identity.

**The exposed key is signing-equivalent to an Ed25519 private key.** Both derive
from one scalar, and an Ed25519 signature requires only the scalar. This SIP
exposes a *public* key and so adds no risk itself, but implementers should know
that the corresponding secret — which the transport holds for the life of every
connection — is as sensitive as a signing key, not merely a session key.

**Small-order keys must be rejected.** A peer key of small order makes the
Diffie-Hellman output all zeros regardless of the server's key, which lets a
caller who has never seen the server's public key compute a valid MAC1. A
transport that surfaces peer identity while accepting such keys would report an
authenticated identity that authenticated nothing.
