## Abstract

sQUIC proves possession of the caller's X25519 key while validating the Initial
packet, then discarded it. This SIP exposes that verified key to the accepting
application, so a service can identify a caller the transport has already
authenticated instead of trusting a key the caller merely asserts afterward.

The key delivered is X25519 — the only key the transport sees. An application
that names identities by Ed25519 key recovers the identity by matching the
verified key against the identities it already knows, converting them forward.
This is enough for a service with a known set of authorised keys, which is the
case that shipped. It is *not* enough for a service that must identify callers
it has never heard of; that gap and its remedy are recorded in the rationale.

## Motivation

A sQUIC client stamps its X25519 public key into every Initial packet and
proves possession of the matching private key by MAC1, computed over a
Diffie-Hellman shared secret. The server verifies this before quinn sees the
packet: an Initial that fails is dropped in silence. By the time an application
accepts a connection, a key has been proven.

Nothing surfaced it, and the cost of that was not merely duplicated work — it
was a vulnerability. sqsshd authenticates a user by reading an Ed25519 key from
an application-layer auth message and looking it up in `authorized_keys`. That
key is asserted by the client, not proven: MAC1 proves the *transport* key, and
the two were never tied together. Any caller who passed MAC1 with one
authorised key could therefore claim another user's key and username and be
granted that account. With two users each authorising only their own key, one
obtained the other's shell — demonstrated end to end, in both of sqsshd's
identifying auth modes.

Closing that hole needs one thing the transport was throwing away: the key it
actually verified, delivered to the layer that makes the authorisation
decision.

## Requirements

Stated ahead of the specification so a competing design can be judged against
the same bar.

**R1 — What is delivered is the verified transport key, labelled as what it
is.** The transport possesses an X25519 key and no other. An implementation
MUST expose that key as an X25519 key and MUST NOT present it as an Ed25519
identity, because the Ed25519 → X25519 map does not run backwards and any
"conversion" would be a guess. Naming the caller in Ed25519 terms is the
application's job (see R2).

**R2 — Ed25519 naming is by forward match, and only closed sets can rely on
it.** An application that authorises by Ed25519 key converts each key it knows
to X25519 and compares. This resolves the identity exactly when the caller is
already in a known set. A caller outside every known set cannot be named this
way, and an implementation MUST NOT pretend otherwise.

**R3 — The key is proven, not asserted.** The delivered key MUST be one MAC1
verified. A key the caller stated in an application message, with no transport
proof of possession, does not satisfy this SIP — that is the defect being
fixed.

**R4 — Absence is representable.** A connection may have no verified key to
report — none was recorded, the record expired, or the join was contested. The
API MUST report absence distinctly from any key value, and a consumer making an
authorisation decision MUST treat absence as "not identified", never as a
default.

**R5 — Identity is not authorisation.** The key answers who is calling. Whether
they may do what they ask is the application's decision, and the API SHOULD NOT
invite the two to be conflated.

**R6 — Degenerate keys are rejected.** A small-order peer key makes the
Diffie-Hellman non-contributory: the shared secret is all zeros whatever the
server's key is, so a caller who has never seen the server's public key can
forge a MAC1. A transport that surfaced such a key would report an identity
that authenticated nothing.

## Specification

### What is exposed

The peer's **X25519 public key**, 32 bytes, as verified by MAC1 on the Initial
that opened the connection. This is a transport primitive; it is not an
Ed25519 identity and MUST NOT be presented as one (R1).

### Joining the key to the connection

The key is learned during Initial validation, in the UDP receive path, before
the QUIC state machine has produced a connection. Implementations MUST associate
the two using the **Destination Connection ID** carried in that same Initial.

The DCID is at a fixed offset in the long header:

```
byte    0        first byte (0xC0..0xCF for Initial)
bytes   1-4      version
byte    5        DCID length, n (0..20; at least 8 in a client's
                 first Initial, per RFC 9000 section 7.2)
bytes   6..6+n   DCID (n bytes)
```

On a MAC1 verification that succeeds, the server records `DCID -> peer key`.
The accepting application looks the connection up by the DCID the QUIC layer
reports as the connection's original destination CID — in Rust,
`quinn::Incoming::orig_dst_cid()`.

Implementations MUST NOT join on the peer's source address. QUIC connection
migration changes it, and a NAT rebinding mid-handshake would silently attach a
connection to the wrong identity — a misidentification, not merely a lookup
failure.

**Retry invalidates the join.** `orig_dst_cid()` resolves to the *pre-Retry*
DCID, recovered from the retry token. sQUIC does not enable quinn's Retry, so
the reported CID is the one on the validated Initial. An implementation that
enables Retry MUST revisit this join, because the retried Initial carries a
different DCID on the wire than the accept path reports and the lookup will
silently miss.

### The join table

Entries MUST expire on a timer. Under sQUIC's cookie defence, and whenever an
Initial is dropped for any reason, a validated key may be recorded for a
connection that never completes; without expiry the table grows for as long as
the process runs, and any peer that can pass MAC1 can fill it. The reference
implementation expires entries after 30 seconds — the window need only span the
gap between the first Initial and accept, which is sub-second in practice — and
prunes expired entries opportunistically once the table exceeds a fixed size,
so no background task is required.

A second Initial bearing a DCID already in the table MUST be handled by
comparing the keys:

- **Same key.** An ordinary retransmission. The entry is unchanged; recording
  it again is idempotent.
- **Different key.** The DCID is ambiguous, and the server has no sound way to
  decide which claimant owns it. The entry MUST be poisoned: lookups for that
  DCID MUST fail for as long as it remains in the table, and MUST NOT return
  either key. See the security considerations.

A lookup MUST remove the entry it returns, so the table drains as connections
are accepted. A consumer therefore reads the key once; a second read of the
same connection reports absence (R4).

### API shape

The lookup is a separate accessor and MUST NOT change the shape of the accept
call, so existing embedders keep compiling and the SIP need not define what
`accept` returns on a poisoned, expired, or missing entry. In the reference
implementation:

```rust
pub fn peer_key(&self, incoming: &quinn::Incoming) -> Option<[u8; 32]>
```

`None` covers every form of absence in R4.

### Naming the caller

An application that authorises by Ed25519 key holds a set of known identities.
To name the verified X25519 key, it converts each known Ed25519 key forward with
`ed25519_public_to_x25519` and compares. A match names the caller; no match
means the caller is not in the known set (R2).

This is exactly what sqsshd already had: it builds its transport whitelist by
converting `authorized_keys` forward, so the forward map is in hand. The fix
binds the asserted auth key to the verified one — `ed25519_public_to_x25519(claimed)`
must equal `peer_key` — before consulting `authorized_keys`, and fails closed
when no verified key is present (R4). Honest clients derive their transport key
from the same Ed25519 identity, so they are unaffected.

### Degenerate keys

The server MUST reject a client X25519 key of small order, and MUST reject an
all-zero Diffie-Hellman result, before MAC1 is considered verified (R6). This
belongs in the transport and is independent of this SIP's accessor.

## Rationale

**Why the DCID and not the source address.** The address is available and
tempting, and it is wrong: it is not stable across migration, and the failure
mode is attributing a connection to the wrong peer rather than failing to find
one. The DCID is chosen by the client, is present in the very packet being
validated, and is exposed by the QUIC layer at accept.

**Why deliver X25519 and not "resolve" Ed25519 in the transport.** The
transport cannot. The Ed25519 → X25519 map is 2-to-1, so reversing yields two
candidates, and an ephemeral client has no Ed25519 preimage at all. Any
transport-level conversion would be a guess dressed as a fact. Forward matching
at the application is exact and admits no such guess, which is why R1 pushes the
naming up a layer rather than faking it down here.

**Why this is enough for sqssh and not for an open exchange.** Forward matching
resolves an identity precisely when it is already in a known set. sqsshd has
one — `authorized_keys`. A service that must identify callers it has never
registered — an open exchange such as sqex — has no set to match against, and
for it this SIP delivers an X25519 key it cannot name. That case is real but
was not what shipped, and it wants a mechanism that carries the Ed25519 key
itself.

**The alternative for the open-set case: TLS client authentication.** A client
can present its Ed25519 identity as a self-signed certificate in the handshake,
which both quinn (`peer_identity`) and quic-go (`ConnectionState`) already
surface, and which — unlike this SIP — delivers Ed25519 directly and needs no
prior knowledge of the caller. It was not adopted here because it changes the
wire (a client-certificate flight, roughly 340 bytes) and requires both
implementations to move together, and sqssh's closed set made the cheaper,
wire-invisible accessor sufficient. When an open-set consumer arrives, TLS
client authentication is the expected mechanism, and it would be specified in
its own SIP rather than by widening this one.

**Why an accessor and not a change to `accept`.** A tuple return would force the
SIP to define what `accept` yields on a miss, and would break every embedder.
The accessor is additive and leaves the miss semantics to `Option`.

## Compatibility

No wire change: the X25519 key is already transmitted and already verified, and
this exposes existing information. Because nothing on the wire changes, SIP-1's
requirement that a wire-touching Standards Track SIP ship in both Rust and Go
does not gate this one; a single implementation is a complete implementation of
the transport behaviour.

The squic API gains an accessor rather than losing or changing one, so embedders
compile unchanged. The sqsshd binding is a behavioural tightening: it rejects
connections whose asserted key is not the verified transport key. Honest clients
already satisfy it; the connections it newly rejects are exactly the
impersonations the motivation describes.

squic-go exposes the equivalent accessor as of v0.59.7. quic-go does not surface
the original destination CID on an accepted connection, so the join is bridged
through the one hook that does receive it: `Config.Tracer` is called with the
CID and with the context `Transport.ConnContext` returned, which is also the
context `Conn.Context()` reports. ConnContext installs a holder, the Tracer
fills it from the peer table, and the accessor reads it back — public API
throughout, no wire change, and any pre-existing Tracer is chained rather than
displaced. Should quic-go later expose the CID directly, the accessor can move
onto it without changing its own signature.

## Security considerations

**This does not make the transport more trustworthy — it closes an application
that was trusting an unproven key.** MAC1 verification is unchanged; a caller
that could not previously pass it still cannot. What changes is that sqsshd now
authorises on a key the transport proved rather than one the client asserted.

**Identity is not authorisation** (R5). A named caller must still be checked
against what they are allowed to do.

**Absence must fail closed.** A consumer that reads `None` and proceeds as
though some default identity were present reintroduces the very hole this SIP
closes. The reference consumer rejects when no verified key is available.

**A contested DCID must not be resolved, only refused.** An attacker who can
observe a victim's Initial learns its DCID and can send its own Initial with the
same DCID and a different key. Resolving the collision by any rule — first write
wins, last write wins — attributes one of the two connections to the wrong
identity, with the outcome depending on arrival order the attacker partly
controls. Poisoning the entry instead downgrades a silent misidentification,
which the application cannot detect, to a single failed handshake, which an
attacker positioned to see the DCID could force anyway by dropping packets. Two
limits bound the severity: the attacker must pass MAC1 in its own right (under a
whitelist, an already-authorised peer, not a stranger), and must learn a DCID of
at least eight random bytes, so in practice must be on-path. Accidental
collision between honest clients is negligible at that width and costs a
handshake, not an identity.

**The join table is attacker-reachable.** Any peer that can pass MAC1 can add an
entry, so the expiry requirement is a security requirement, not housekeeping.

**The X25519 secret is signing-equivalent to an Ed25519 private key.** Both
derive from one scalar, and an Ed25519 signature needs only the scalar. This SIP
exposes a *public* key and so adds no risk itself, but the corresponding secret
— which the transport holds for the life of every connection — is as sensitive
as a signing key, not merely a session key.

**The verified key is visible on the wire.** Because the X25519 key is appended
to the Initial in plaintext, a persistent client already presents a stable
identifier to a passive observer. This SIP neither adds to that exposure nor
removes it. A deployment that wants to remove it would need the identity to
travel in the encrypted handshake instead — another reason the TLS-client-auth
alternative is attractive for a future open-set consumer.

**Small-order keys must be rejected** (R6).

## Reference implementation

- squic v0.14.0 — `ServerListener::peer_key(&Incoming)`, the DCID join table
  with the poisoning and expiry rules above, and unit and integration tests
  covering the match, the drain, poisoning, and expiry.
- sqssh v0.2.10 — sqsshd binds the asserted auth key to the verified transport
  key before consulting `authorized_keys`, failing closed on absence. Verified
  end to end against the two-user impersonation that previously succeeded: it is
  now rejected in both identifying auth modes while both legitimate logins
  continue to work.

- squic-go v0.59.7 — `ServerListener.PeerKey(*quic.Conn)`, the same DCID peer
  table with the poisoning and expiry rules, bridged to accept through
  `ConnContext`/`Tracer` as described under Compatibility. Tests cover the
  match, idempotent retransmit, poisoning, drain, expiry, and DCID parsing.
