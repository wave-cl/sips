## Abstract

An application holding an accepted sQUIC connection should be able to ask who
is calling, and get back the caller's Ed25519 public key, without running an
authentication exchange of its own. sQUIC already proves possession of a key
before quinn sees the first packet; nothing carries the result upward.

This SIP states what any answer must satisfy, and specifies two mechanisms that
could provide it. They are not variations on one design — they differ in which
key they deliver, whether they touch the wire, and whether both implementations
can support them. **This SIP does not yet choose between them.**

## Motivation

A sQUIC client stamps its X25519 public key into every Initial packet and
proves possession of the matching private key by MAC1, computed over a
Diffie-Hellman shared secret. The server verifies this before quinn sees the
packet: an Initial that fails is dropped in silence. By the time an application
accepts a connection, a key has been proven.

No application uses this. sqsshd, holding a connection whose peer is already
proven, runs a second Ed25519 signature challenge at the application layer to
learn who is calling. The work is done twice and only the second result is ever
read.

Two things stand in the way, and they are separate problems that have been
easy to conflate:

- **The proven key never leaves the transport.** It is validated inside
  `validate_and_strip`, in the UDP receive path, before the QUIC state machine
  has produced a connection object. `ServerListener` offers no accessor and
  quinn's connection types carry nothing of ours.
- **The proven key is the wrong key.** Every identity in this ecosystem — sqns
  records, sqssh `authorized_keys`, the base58 strings people paste — is named
  by an Ed25519 public key. The transport only ever observes X25519, and the
  reverse map is 2-to-1 rather than one-way, so an observed X25519 key cannot be
  turned back into the name anyone uses.

A mechanism that solves only the first leaves the application holding a key it
cannot name. That is worth stating plainly, because it is the fault line
between the two candidates below.

## Requirements

Any mechanism claiming to satisfy this SIP MUST meet all of the following.
They are stated ahead of the mechanisms so that a third proposal can be judged
against the same bar.

**R1 — The identity delivered is the Ed25519 public key, or nothing.** An
implementation MUST NOT present an X25519 key as though it were an identity.
Where only an X25519 key is available, the mechanism is incomplete and MUST say
so rather than substitute.

**R2 — The identity is proven, not asserted.** Delivering a key the caller
merely claimed, without the transport or the handshake having established
possession of the corresponding private key, does not satisfy this SIP.

**R3 — Absence is representable.** A caller with no persistent identity is
legitimate. The mechanism MUST be able to report that there is no identity,
distinctly from reporting a zero or placeholder key.

**R4 — Identity is not authorisation.** The mechanism answers who is calling.
Whether they may do what they are asking is the application's decision, and the
API SHOULD NOT invite the two to be conflated.

**R5 — Degenerate keys are rejected.** A small-order peer key makes the
Diffie-Hellman non-contributory: the shared secret is all zeros whatever the
server's key is, so a caller who has never seen the server's public key can
compute it in advance and forge a MAC1. Any mechanism that reports identity
while accepting such a key would report an identity that authenticated nothing.

**R6 — Both implementations can support it through supported APIs.** SIP-1
requires a Standards Track SIP touching the wire to have both a Rust and a Go
implementation before it reaches Active. A mechanism reachable in one language
only, or reachable in the other only by depending on unexported internals or
repurposed hooks, does not clear this bar.

## Mechanism A: TLS client authentication

The server enables TLS client authentication with a verifier that accepts a
self-signed Ed25519 certificate and records its key. The client presents a
certificate built from its Ed25519 identity key. The server reads the identity
once the handshake completes.

Both languages already expose the result:

- **Rust** — `quinn::Connection::peer_identity()` returns the peer certificate
  chain (`quinn-0.11.9/src/connection.rs:569`). `ServerListener::accept()` does
  not change.
- **Go** — `Conn.ConnectionState().TLS.PeerCertificates[0]`.

The pieces exist in squic already, pointing the other way: `self_signed_cert()`
builds precisely this certificate for the *server*, and `PinnedKeyVerifier` is
the mirror image of the verifier the server would need. The substantive change
is `server_tls_config()`'s `with_no_client_auth()`.

Normatively:

- A client configured with a persistent identity MUST present a self-signed
  certificate whose SubjectPublicKeyInfo carries its Ed25519 public key.
- A client without one MUST NOT present a certificate, and the server MUST
  report that peer as having no identity — satisfying R3.
- The server MUST accept the certificate on a valid CertificateVerify alone. It
  MUST NOT require a chain to a CA, an unexpired validity window, or a matching
  name. The key is the identity; the certificate is only its envelope.
- The server MUST reject a certificate whose key is not a valid Ed25519 point,
  and MUST apply R5 to the transport key independently.

**Against the requirements.** R1 and R2 are satisfied directly: the certificate
carries the Ed25519 key and CertificateVerify proves possession of it. R3 is
satisfied by presenting no certificate. R6 is satisfied by stock APIs in both
languages.

**What it costs.** It is a wire change. The client's Certificate and
CertificateVerify ride in the same flight as Finished, so there is no extra
round trip, but the bytes are real: squic's Ed25519 self-signed certificate
measures 250 bytes, so with the signature and framing the flight grows by
roughly 340 bytes. That flight is not subject to the amplification limit. Both
implementations must move together, and the identity arrives after the
handshake rather than at accept.

## Mechanism B: DCID join, with identity binding

This mechanism has two halves, and **the first alone does not satisfy R1.**

### B1 — carrying the transport key to the application

The key is learned during Initial validation, before the QUIC state machine has
produced a connection. Implementations MUST associate the two using the
**Destination Connection ID** carried in that same Initial packet.

The DCID is at a fixed offset in the long header:

```
byte    0        first byte (0xC0..0xCF for Initial)
bytes   1-4      version
byte    5        DCID length, n (0..20; at least 8 in a client's
                 first Initial, per RFC 9000 section 7.2)
bytes   6..6+n   DCID (n bytes)
```

On a MAC1 verification that succeeds, the server records `DCID -> peer key`.
The accepting application looks the connection up by the DCID the QUIC layer
reports as the connection's original destination CID.

Implementations MUST NOT join on the peer's source address. QUIC connection
migration changes it, and a NAT rebinding mid-handshake would silently attach a
connection to the wrong identity — a misidentification, not merely a lookup
failure.

**Retry invalidates the join.** In Rust, `quinn::Incoming::orig_dst_cid()`
resolves to the *pre-Retry* DCID, recovered from the retry token
(`quinn-proto-0.11.17/src/endpoint.rs:1208`). squic does not enable quinn's
Retry today, so the reported CID is the one on the validated Initial. An
implementation that enables Retry MUST revisit this join, because the retried
Initial carries a different DCID on the wire than the accept path reports, and
the lookup will silently miss.

### Lifetime of the table

Entries MUST expire on a timer. The timer is not optional: under squic's cookie
defence, and whenever an Initial is dropped for any reason, a validated key may
be recorded for a connection that never completes. Without expiry the table
grows for as long as the process runs, and is trivially filled by any peer that
can pass MAC1.

A second Initial bearing a DCID already in the table MUST be handled by
comparing the keys:

- **Same key.** An ordinary retransmission. The entry is unchanged; recording
  it again is idempotent.
- **Different key.** The DCID is ambiguous, and the server has no sound way to
  decide which claimant owns it. The entry MUST be poisoned: lookups for that
  DCID MUST fail for as long as it remains in the table, and MUST NOT return
  either key.

Poisoning rather than resolving is deliberate; see the security considerations.
The cost is one failed handshake, and the alternative is a wrong answer.

Implementations are free to choose the expiry structure. Two generations
swapped on a timer — the shape squic already uses for `cookie_secret` and
`prev_cookie_secret` — evicts in constant time without per-entry timestamps or
a sweep, and needs no task beyond the maintenance loop that already runs.

### API shape

The lookup SHOULD be a separate accessor rather than a change to `accept()`'s
return type:

```rust
pub fn peer_key(&self, incoming: &quinn::Incoming) -> Option<[u8; 32]>
```

This keeps existing embedders compiling, and leaves the caller to decide what a
missing entry means — where a tuple return would force the SIP to define what
`accept()` does on a poisoned or expired lookup.

### B2 — naming the key

B1 delivers an X25519 key, which R1 forbids presenting as an identity. To reach
an Ed25519 name, the caller states its identity and the server verifies the
claim by derivation: `ed25519_public_to_x25519(claimed)` must equal the
observed transport key. No signature is required, because MAC1 already proved
possession of the scalar the two keys share.

This is SIP-3, which is specified at the Exchange layer. Two consequences
follow and should not be glossed:

- It is a protocol exchange, not an accessor. The caller must send a claim
  message, so a plain sQUIC server does not get an identity for free — it must
  implement the claim itself, or ask something that has.
- SIP-3 exists only to repair B1's shortfall against R1. Under Mechanism A
  there is nothing for it to repair.

### The Go problem

**quic-go v0.59.0 does not expose the original destination connection ID**, so
B1 does not currently clear R6.

- `origDestConnID` is unexported (`connection.go:130`), and `ConnectionState`
  carries no connection ID field.
- `Transport.ConnContext` — the only hook that runs while the Initial is being
  handled — receives a `*ClientInfo` carrying `RemoteAddr` and `AddrVerified`
  and nothing else (`interface.go:183`). Not the CID, and the address is the
  join key this mechanism forbids.
- Correlating by read order is impossible by construction: received packets
  pass through a buffered channel and Initials are handled on a separate
  goroutine (`server.go:65,285,394`), so the code that validates a packet and
  the code that accepts the connection are deliberately decoupled.

One route exists. `config.Tracer` is invoked with the post-`ConnContext`
context and with `connID` set to `origDestConnID` (`server.go:804-810`), so a
mutable holder injected in `ConnContext`, filled by the tracer, and retrieved
through `Conn.Context()` would carry the key across. That uses the qlog tracer
as an identity channel, and R6 excludes it for exactly that reason.

B1 therefore reaches Active only by upstreaming an accessor to quic-go, or by
forking it.

## Comparison

|                                    | A — TLS client auth                 | B — DCID join (+ SIP-3)                  |
| ---------------------------------- | ----------------------------------- | ---------------------------------------- |
| Satisfies R1 alone                 | yes                                 | no — needs SIP-3                         |
| Key delivered                      | Ed25519                             | X25519, named later by claim             |
| Wire change                        | ~340 bytes, no extra RTT            | none                                     |
| Implementations must move together | yes                                 | no                                       |
| Rust public API                    | none — `peer_identity()` exists     | new accessor                             |
| Go public API (R6)                 | standard                            | unavailable; needs upstreaming or a fork |
| Per-handshake server state         | none                                | table entry, expiry and poisoning rules  |
| Identity visible to a passive observer | no — encrypted handshake flight | yes — X25519 key is plaintext in Initial |
| Identity available                 | after handshake                     | at accept (X25519); after claim (Ed25519)|
| Documents needed                   | this one                            | this one and SIP-3                       |
| Callers with no identity           | reported absent                     | X25519 key with no name                  |

## Rationale

**Why state requirements before mechanisms.** The first draft of this SIP
specified the DCID join and treated it as the definition of the goal. That made
an X25519 key look like an answer, and pushed the actual question — how does an
application learn a name it can act on — into a second document, where it read
as a follow-on rather than as the unfinished half. Requirements first make the
shortfall visible in the same place as the design.

**Why the DCID and not the source address.** The address is available and
tempting, and it is wrong: it is not stable across migration, and the failure
mode is attributing a connection to the wrong peer rather than failing to find
one. The DCID is chosen by the client, is present in the very packet being
validated, and is exposed by the QUIC layer at accept.

**Why not keep the application-layer challenge.** sqsshd's Ed25519 challenge is
a hand-rolled TLS client authentication. Mechanism A replaces it with the
standard one. Mechanism B cannot replace it until SIP-3 ships behind it, since
until then sqsshd is handed a key it cannot match against `authorized_keys`.

**Why no mechanism reports a converted key.** Converting an observed X25519 key
into a plausible Ed25519 key would be lying about what was proven: the map
admits two preimages, and for an ephemeral caller it admits none. R1 forbids it
for that reason and not for tidiness.

## Compatibility

**Mechanism A** changes the wire. Old and new peers do not interoperate in the
direction that matters: a server requiring a client certificate will fail
handshakes from clients that do not send one, so both implementations and the
deployed clients must move together. No embedder API breaks.

**Mechanism B** changes no wire bytes — the X25519 key is already transmitted
and already verified, and B1 only exposes existing information. It adds an
accessor rather than breaking one, so a single implementation can ship it
alone. SIP-3's claim message is a wire addition at the Exchange layer, carried
inside an established connection rather than in the handshake.

## Security considerations

### Applying to both mechanisms

**Neither makes the transport more trustworthy.** They make what it already
proves legible. MAC1 verification is unchanged, and a caller that could not
previously authenticate still cannot.

**Identity is not authorisation** (R4). An application must still decide
whether the named identity may do what it is asking. Exposing a name makes the
two easier to conflate, and implementations should document the distinction.

**Branching on identity introduces timing.** A server with a whitelist already
responds differently to known and unknown keys, which is the intent. A service
that now varies its behaviour by identity may introduce differences that were
not there before.

**The X25519 secret is signing-equivalent to an Ed25519 private key.** Both
derive from one scalar, and an Ed25519 signature needs only the scalar. These
mechanisms expose *public* keys and so add no risk themselves, but the
corresponding secret — which the transport holds for the life of every
connection — is as sensitive as a signing key, not merely a session key.

**Small-order keys must be rejected** (R5).

### Mechanism B only

**The join table is attacker-reachable.** Any peer that can pass MAC1 can add
an entry. The expiry requirement is a security requirement, not housekeeping.

**A contested DCID must not be resolved, only refused.** An attacker who can
observe a victim's Initial learns its DCID, and can send its own Initial
carrying the same DCID and its own key. If the table resolves the collision by
any rule — first write wins, last write wins — then one of the two connections
is attributed to the wrong identity, and which one depends on packet arrival
order the attacker partly controls. Neither rule is safe: last-write lets the
attacker overwrite the victim, and first-write lets the attacker pre-empt a
victim whose Initial it can anticipate or delay.

This is why the specification poisons the entry instead. A failed lookup is a
denial of service against a single handshake, which an attacker positioned to
see the DCID could accomplish anyway by dropping packets. A successful lookup
returning the wrong key is a misidentification the application has no way to
detect, and it is the one outcome the transport must never produce.

Two limits are worth stating, so the severity is not overread. The attacker
must pass MAC1 in its own right, so it must hold a key the server accepts —
under a whitelist, this is an escalation available to an already-authorised
peer, not to a stranger. And it must learn the DCID, which for a first Initial
is at least eight random bytes, so in practice it must be on-path. Accidental
collision between honest clients is negligible at that width, and costs those
clients a handshake rather than their identity.

### Mechanism A only

**Identity is not disclosed to observers.** The client's Certificate and
CertificateVerify travel in the encrypted handshake flight, so a passive
observer does not learn who is connecting. This is a genuine improvement over
the status quo, not merely parity: squic's X25519 client key is appended to the
Initial in plaintext and read straight from the datagram, so a stable
per-client identifier is already visible on the wire to anyone watching, and
Mechanism B leaves it that way.

**A certificate is a reusable artifact.** It is self-signed, long-lived and
carries no audience binding, so possession of a client's certificate alone
proves nothing — CertificateVerify, which is bound to the handshake transcript,
is what proves possession. Implementations MUST NOT accept an identity on the
strength of a presented certificate without a valid CertificateVerify.

## Open questions

**Whether the wire change is acceptable.** The usual answer is no, and the
usual answer is calibrated for protocols with strangers on them. This one has
neither: squic is pre-1.0, both implementations are ours, the deployed surface
is one server and a handful of clients, and the two implementations have
already been changed in lockstep twice this month. Against that, Mechanism B
could ship in Rust alone within a week, where Mechanism A cannot ship until Go
moves too.

**Whether Mechanism A should also bind the certificate key to the MAC1 key.**
Requiring `ed25519_public_to_x25519(certificate key)` to equal the transport
key is tempting, and it would need the very join table Mechanism A exists to
avoid — the TLS verifier runs inside the crypto stack with no access to the
MAC1 key. It is also unnecessary for authentication: the certificate proves
possession of the Ed25519 key by itself, so a caller cannot claim an identity
it does not hold, whatever key it used for MAC1. Leaving it unchecked does
decouple the whitelist (X25519, a denial-of-service gate) from identity
(Ed25519, an authorisation input). That is a housekeeping wart rather than a
vulnerability, but this SIP should choose out loud rather than leave it implied.

**Whether R6 should be satisfied by upstreaming.** Exposing the original
destination connection ID is a small, uncontroversial addition to quic-go's
public API, and proposing it upstream would settle R6 for Mechanism B. That is
a slower path than adopting Mechanism A, but it is not a closed one, and the
choice should not be made as though it were.

## Reference implementation

None yet. SIP-4 depends on this SIP being resolved either way. SIP-3 is
Mechanism B's second half and is contingent on Mechanism B being chosen; if
Mechanism A is adopted, SIP-3 should be withdrawn rather than implemented.
