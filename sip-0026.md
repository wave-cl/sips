## Abstract

An identity publishes what it offers — ALPN, service type, version — and others
query it.

An earlier draft of this SIP argued for its own withdrawal, on the grounds that
capability belonged in a signed sqns record rather than in the exchange. SIP-28
moves resolution itself into the exchange, which dissolves that objection —
capability now sits beside the endpoints it describes. The original reasoning is
kept below, because it remains the right test to apply.

## Motivation

Knowing where a service is and knowing what it speaks are different questions.
sqns answers the first. Nothing answers the second: a caller must already know
that a key on port 22 speaks `sqssh/1`, and a rolling upgrade is invisible.

## The boundary problem

The intended split was that sqns says *where* and the exchange says *what*.
Examined against sqns as it actually exists, that split mostly does not hold.

An sqns `Record` carries `key`, `delegation`, `serial`, `issued_at`, `ttl` and
a body, and a `Live` body carries endpoints. Crucially, a `Live` record is
signed by **the service key, not the identity key** — `expected_signer()`
returns `self.key` for `Live`, reserving the offline identity key for
retirement. The service key is online by definition; it is what the service
uses to answer.

So the argument that produced SIP-4 does not apply here. A beacon cannot live
in sqns because heartbeats cannot be signed by an offline key. Capability
**can** be signed, by a key that is already online, and put in a record that is
signed, replicated, cached with a TTL, and — decisively — still readable when
the service is down.

An exchange answer has none of those properties. It is transport-authenticated
rather than self-authenticating, held by one operator, and meaningless when the
subject is offline. For static facts about a service, that is worse in every
dimension.

### What would remain

Only state that changes faster than it is worth re-signing and republishing,
and that is meaningless when the service is offline. Plausibly: current load,
readiness during a rolling restart, a version that changes between record
publications.

That residue is thin, and it overlaps SIP-4 — a beacon already proves the
service is up, and `flags` could carry readiness without a new mechanism.

## Recommendation, revised

The argument above was decisive only while resolution lived in sqns. Once
endpoints are published to the exchange unsigned and transport-authenticated
(SIP-28), capability has the same provenance as the address it accompanies, and
splitting them across two services would be the odd choice.

Capability should therefore be published alongside endpoints, in the same
message and with the same expiry, and returned in the same reply. This SIP
becomes a small extension of SIP-28 rather than a competing mechanism.

What survives from the original objection is the test, which is still worth
applying to every proposed field: **why can this not simply be published as part
of the endpoint set?** A field that needs different durability, a different
signer or a different lifetime does not belong here.

## Rationale

Recorded rather than deleted because the reasoning is the useful part. The
temptation to put service metadata in an exchange — where it is easy, needs no
signature and no format revision — is real, and the cost is losing every
property that makes sqns records worth having. A future proposal will meet the
same temptation.

## Specification

Capability is a field of SIP-28's `Publish`, carried in the same message, with
the same expiry, and returned in the same reply:

```
Publish  | type: u8 = 0x10 | ttl_secs: u32 | count: u8 | endpoint × count
         | capabilities: u8 | (len: u8 | utf8) × capabilities |

Resolved | found: u8 | count: u8 | endpoint × count
         | published_at | expires_at | last_seen | now
         | capabilities: u8 | (len: u8 | utf8) × capabilities |
```

Each capability is free UTF-8 — an ALPN, a service name, a version — bounded at
8 per identity and 64 bytes each. **The whole list is replaced with the
publication**, exactly as the endpoint set is, and for the same reason: a merge
would leave a version string standing after the service it described was
upgraded, which is the case this SIP exists to make visible.

Nothing is added to SIP-28's routes, its store, its lifetime or its trust
boundary. That is the claim "a small extension" is meant to be checkable
against.

## Compatibility

An extension of SIP-28's messages, and older publishers omit the field. A
capability list is optional: an identity may say where it is without saying what
it speaks, which is what every publisher did before this.

## Security considerations

Advertising capability advertises attack surface: a version string tells an
attacker which vulnerabilities apply. That is true wherever the data lives, but
an exchange makes it queryable for every identity at once, which a distributed
set of signed records does not.

**Nothing here is signed and nothing here should be believed on its own.** A
capability is a claim by the identity about itself, relayed by an exchange that
did not check it and could not. It is a routing hint — which of several
endpoints to try first, whether to expect a protocol at all — and never an
authorisation. An implementation that granted anything on the strength of an
advertised capability would be trusting a self-assertion twice removed.

## Reference implementation

`sqex` 0.33.0, as the extension the recommendation above describes: a field on
SIP-28's `Publish` and `Resolved`, held in the same store with the same expiry,
and `sqex resolve publish --capability`.

**The residue turned out to be exactly what was predicted.** Nothing was added
beyond ALPN, service name and version, because everything else that was
proposed failed the test: readiness belongs in SIP-4's beacon flags, which
already carry it and change faster than a publication; load is meaningless when
the subject is offline and is not worth a mechanism that is meaningless then
too.
