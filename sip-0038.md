## Abstract

An exchange holds a directory of names — short labels like `c` — each bound to
one account. A client resolves `c@example.com` by finding the domain's exchange
(SIP-33), asking it for the account behind `c`, and then treating that account
exactly as it would a key typed out in full: its devices come from SIP-22, its
endpoints from SIP-28. A name is claimed by its holder where an operator allows
it (open registration) or assigned by an administrator where they do not
(closed). The binding is asserted by the exchange, not signed by the account,
and this SIP is explicit about what that costs.

## Motivation

Every identity in this stack is a 32-byte Ed25519 key, and the only way to name
one is to quote all 44 base58 characters of it. That is fine for a machine and
unusable between people: it cannot be read down a phone, typed without error, or
remembered. The gap is a human-memorable handle that resolves to a key, scoped
to a domain somebody is authoritative for — the shape `user@domain` has had
since 1971 and that everyone already knows how to hand to a stranger.

The pieces to resolve one are already here and this SIP mostly wires them
together.

- **SIP-33** turns a domain into an exchange: `_sqex.<domain>` over DNSSEC gives
  the exchange's key and address, pinned on first contact. So the `@domain` half
  is solved, and an exchange serves exactly the one domain its record names.
- **SIP-22** turns an account into its devices, and **SIP-28** turns a key into
  its endpoints. So once a name resolves to an *account*, everything downstream
  — which is where multi-device lives — already works. Binding a name to a
  device would have to be redone every time somebody replaced a phone; binding
  it to the account, which is what SIP-22 revocation and enrolment already
  manage, means a name survives the devices under it.

What is missing is the one hop in the middle: name → account. That is a small,
persistent, per-domain map, and it is what this document specifies.

It is deliberately its own SIP and not a corner of SIP-28. SIP-28 resolves a key
you already hold to where it is right now, and does so from memory because an
address is only interesting while it is fresh — a restart that forgets is
telling the truth. A name is the opposite: it is the durable thing, the identity
a person keeps across address changes and device swaps, and an exchange that
forgot its names on restart would be useless. The two have opposite lifetimes
and belong in different stores.

## Specification

All integers are unsigned big-endian. Every operation is bound to the caller's
transport identity (SIP-3); a connection carrying no identity is refused, as
everywhere in the exchange. The exchange resolves that transport identity to an
**account** the way every other account-addressed route does (SIP-22): the
caller's device maps to the account that registered it, and a device that
belongs to no account is its own account.

A **name** is bound to an account, never to a device. Names are scoped to the
single domain this exchange serves; there is no cross-exchange namespace.

### Names

A name is a label in the grammar

```
name  = let-dig [ *(let-dig / "-") let-dig ]
let-dig = %x61-7A / %x30-39          ; a-z 0-9
```

between 1 and 63 bytes in its canonical form. The exchange **canonicalises by
ASCII-lowercasing** before it validates, compares or stores anything, so `C` and
`c` are the same name; after folding, a name matching the grammar above is
valid and anything else is refused as malformed. Hyphens may appear only
between two other characters, never leading or trailing.

The grammar is ASCII and DNS-label-shaped on purpose. It admits no `@`, no `.`,
no `/`, no whitespace and no non-ASCII byte, so `name@domain` parses without
ambiguity, a name can never be mistaken for a path or a key, and **there is no
confusable or homograph surface** — the failure a Unicode namespace has to spend
a normalisation-and-scripts mechanism to contain, this one does not have because
it excludes the characters that create it. Unicode with NFC normalisation was
considered and rejected; see Rationale.

### The name route

Four messages on `POST /name`, distinguished by a leading type byte. This is a
namespace of its own and does not share numbers with any other route.

```
Claim    | type: u8 = 0x01 | name_len: u8 | name |
Release  | type: u8 = 0x02 | name_len: u8 | name |
Resolve  | type: u8 = 0x03 | name_len: u8 | name |
Reverse  | type: u8 = 0x04 | account: [32] |
```

Replies carry the exchange's clock, `now`, for the reason SIP-4 gives: staleness
is computed against the observer's clock, never the consumer's.

```
ClaimAck | outcome: u8 | now: u64 |
Ack      | now: u64 |
Resolved | found: u8 | now: u64
         | [ account: [32] | registered_at: u64 | last_active: u64
             | expires_at: u64 | flags: u8 ]        ; present iff found = 1
Names    | now: u64 | count: u16 | count × (len: u8 | name) |
```

`flags` bit 0 is set when the binding is **stale** — past `expires_at` but not
yet reclaimed (see *Leases*). Other bits are reserved and MUST be zero.
`expires_at` is zero for a binding that does not expire (an administrator's
assignment).

#### Claim — self-service registration

`Claim` is available only where the operator has enabled **open** registration
on this route (see *Registration modes*); elsewhere it returns `outcome = 3` and
does nothing.

It binds the caller's account to `name`. `outcome` reports what happened:

| `outcome` | meaning |
|---|---|
| 0 | granted — the name now resolves to the caller's account |
| 1 | taken — another account holds it and the binding is not stale |
| 2 | at capacity — the caller's account already holds `max_names_per_account` |
| 3 | open registration is not enabled on this route |

A `Claim` is **idempotent for the caller's own name**: re-claiming a name the
caller already holds succeeds and refreshes its lease (`last_active := now`),
which is how a holder renews. A `Claim` for a **stale** binding held by another
account succeeds and rebinds the name to the caller — that is what "stale" is
for. The per-account cap counts only bindings the account holds live or stale;
a refresh of an existing name does not count against it.

No signature is carried. The connection has already proved the account key
(MAC1 verified the device, SIP-3 exposes it, SIP-22 maps it), and a claim asserts
nothing beyond "this account wants this free name". This is the same reasoning
that lets SIP-28 publish endpoints unsigned.

An exchange MUST bound `Claim`s to a small number per connection per hour, so a
single caller cannot sweep the namespace or grind for lapsing names; the overrun
is refused silently as a rate limit, distinct from `outcome = 1`.

#### Release — giving up a name

`Release` removes the binding if the caller's account holds `name`, and is a
no-op otherwise. It returns `Ack` either way: the holder of a name is already
public (anyone may `Resolve` it), so a uniform reply here conceals nothing that
resolution does not already reveal. Administrative release is a separate,
authorised operation below.

#### Resolve — the public lookup

`Resolve` returns the account a name is bound to. It is answerable to any
authenticated caller: **the namespace is public by construction** — a name
exists to be found, and a directory that would not say whether a name is taken
would not be a directory.

- `now < expires_at`, or `expires_at = 0`: `found = 1`, `flags` clear — a live
  binding.
- `expires_at <= now`: `found = 1`, stale bit set — the lease has lapsed but no
  one has reclaimed the name. It still resolves, so a briefly-quiet account is
  not cut off mid-lapse, and the flag tells a consumer the answer is on notice.
- the name has been reclaimed by another account, or was never bound:
  `found = 0`.

A consumer that has resolved a name to an account MUST then treat the account as
it would any other: connect and pin its key (SIP-9/SIP-2), enumerate devices
(SIP-22), resolve endpoints (SIP-28). The name got it a key; it authenticates
the key itself.

#### Reverse — names for an account

`Reverse` returns every name the account holds, live or stale, oldest first. It
is public for the same reason `Resolve` is, and it is what a client uses to show
`c@example.com` in place of a key it has verified.

### Leases

An open-registered name carries a lease. `expires_at = last_active +
name_lease_secs`, where `name_lease_secs` is operator configuration (default
long — a matter of weeks, not hours; a name is not an address). `last_active` is
renewed by **any activity attributable to the account**:

- a beat (SIP-4) from any device of the account;
- a re-`Claim` of the name;
- a SIP-28 endpoint publication by the account.

Past `expires_at` the name is *stale*: it still resolves (with the flag) and the
holder may still renew it, but any other account's `Claim` now takes it. This is
the reclamation path for names whose owners are gone, and it is bounded by the
lease rather than left to an administrator.

The lease tracks the account's **devices'** liveness, and this is a real
limitation worth stating rather than hiding: an account key held in hardware
never beats on its own (SIP-11 is why), so a name held by an account whose
devices all go quiet will lapse on schedule. Renewing is one beat, one publish,
or one re-claim from any device — cheap for anyone still present, and absent for
exactly the accounts reclamation exists to reclaim from.

An administrator's assignment does not carry a lease (`expires_at = 0`) and does
not expire; the operator who set it is the one who removes it.

### Registration modes

Which of the above an operator offers is policy, set per this route, following
the per-route enforcement SIP-24 established so that one deployment can run an
open directory and a closed roster side by side.

| `name_registration` | `Claim` | administrator ops |
|---|---|---|
| `open` | anyone may claim a free or stale name | also available |
| `closed` | refused (`outcome = 3`) | the only way a name is bound |
| `off` | refused | refused — the route is disabled entirely |

### Administration

Three operations, carried in a SIP-10 signed transaction and subject to its
verification in full. They extend the exchange's `Op` set, which admission
(SIP-24) took through tag `0x0b`.

| Tag | Operation |
|---|---|
| 0x0c | `NameAssign { name, account }` — bind a name, in any mode |
| 0x0d | `NameRelease(name)` — free a name, in any mode |
| 0x0e | `NameList` — read the directory |

Their transaction payloads, in the shape SIP-10 already uses (a tag byte, then
fixed-width fields, then any variable-length tail):

```
NameAssign  | 0x0c | account: [32] | name_len: u8 | name |
NameRelease | 0x0d | name_len: u8 | name |
NameList    | 0x0e |
```

`NameAssign` binds `name` to `account` regardless of the registration mode and
regardless of any existing binding: it is the override, and it is how names are
handed out in a closed deployment and how a squatted or misassigned name is
corrected in an open one. It records provenance — the administrator who signed
it, the account, the time — as `AdmissionApprove` does. An assignment does not
count against `max_names_per_account`: the cap governs self-service, and an
administrator's decision is not self-service.

`NameRelease` frees any name, open- or administrator-bound. `NameList` returns
the directory: for each binding, the name, the account, whether it is
open-leased or administrator-assigned, `registered_at`, `last_active` and
`expires_at`.

**Administrator here means an exchange administrator** — an identity on the list
SIP-10 transactions are checked against, the same authority SIP-24 admission and
the managed whitelist answer to. It does **not** mean a channel administrator
(SIP-16), a role anyone acquires by creating a room; conflating the two would
let anyone who made a chat room hand out names in the domain.

### Limits

| Limit | Value |
|---|---|
| Name length | 1–63 bytes, canonical form |
| `max_names_per_account` | operator config; a zero cap is rejected at load |
| `name_lease_secs` | operator config, default long (weeks) |
| `Claim`s accepted per connection per hour | small, operator-bounded |

Each is enforced silently against what the exchange stores; none changes the
shape of a reply except `Claim`'s own `outcome`, which is public information
already.

## Rationale

**Why a name binds to an account, not a device.** The account is the durable
identity; devices come and go under it and SIP-22 already manages that churn.
Binding to a device would make a name something you lose with a phone, and would
need re-pointing on every enrolment. Binding to the account makes multi-device
support fall out of SIP-22 rather than be re-solved here — the entire reason the
name layer is small.

**Why exchange-asserted and not account-signed.** An account could sign "I claim
`c`", and the exchange could store and serve that signature so a consumer could
verify the account consented to the name. That is strictly stronger and it was
rejected for this version deliberately, on the same grounds SIP-28 gives for its
own unsigned publication: the exchange already authenticates every caller, a
second signature scheme is a second format and a second verification path and a
second thing to get wrong, and SIP-1 exists because a signature mechanism that
never worked went unnoticed for months. The trust this concedes is bounded and
named in Security considerations, and the signed form is recorded there as the
upgrade path for a deployment that needs it. It is a genuine trade, not an
oversight.

**Why the namespace is public, against the corpus.** SIP-4, SIP-5, SIP-12 and
SIP-24 all go to lengths to answer identically whatever they decide, so that
asking discloses nothing. This SIP does the opposite and must justify it: those
mechanisms hide whether a *particular party* exists or is admitted, which is a
secret the asker has not earned. A name directory exists precisely to disclose
that `c` is taken and by whom — that is the service. There is no secret being
protected by refusing to answer, only a directory made useless. The privacy that
remains — who asks about whom — is real and is treated as SIP-28 treats the same
leak.

**Why leases, and why they track device liveness.** Open registration without
expiry is a landgrab: the good names go first and stay gone. A lease bounds that
without an administrator adjudicating every lapse, and tying it to SIP-4 reuses
the liveness signal the exchange already has rather than inventing a heartbeat
for names. The cost — a hardware-only account must have a device renew for it —
is stated plainly rather than engineered around, because the accounts that
cannot manage one renewal in weeks are the ones reclamation is for.

**Why not fold this into SIP-33 / DNS.** DNS already carries `_sqex.<domain>`,
and per-user names could be `_sqex-c.<domain>` TXT records. That was rejected:
it makes every name a zone edit, puts the whole directory in the registrar's
trust root rather than only the bootstrap, cannot express a lease or a
self-service claim, and cannot couple to SIP-4 liveness. DNS is the right place
for the one record that finds the exchange and the wrong place for the exchange's
own mutable directory.

**Relationship to SIP-27.** SIP-27 lets an issuer vouch that a subject is known
by some name — a subjective, per-issuer statement with no uniqueness. This SIP is
the objective, per-domain, unique binding. They are complementary: SIP-27 is how
one identity tells another "I know this key as Alice"; this is how a domain says
"`alice` here is this key". A consumer worried about a dishonest exchange
substituting a key (below) can use SIP-27 vouches to cross-check the binding.

## Compatibility

New route and three new SIP-10 operation tags (`0x0c`–`0x0e`), where `0x0c`
onward were unused. No existing wire format changes, so an exchange without this
SIP simply does not offer the route and its administration tags decode as unknown
and are refused, exactly as they are today. A client built for it discovers the
absence as a route that is not served; there is no flag day and the two
implementations need not move together for anything else.

Requires SIP-3 for the authenticated caller and SIP-22 to resolve it to an
account; SIP-4 for the lease; SIP-10 for administration; SIP-33 for the
`@domain` half of a resolvable name; and SIP-28 as the natural next hop a
resolved account is handed to. It reads none of `sqns`.

## Security considerations

**The binding is trusted for authenticity, and this is stronger trust than
SIP-28 asks.** In SIP-28 a consumer pins the key it looked up, so a dishonest
exchange returning a wrong address only causes a failed handshake — a denial, not
an impersonation. Here the exchange asserts *which key* a name means, and the
consumer has no independent check: an exchange that returns an attacker's account
`K'` for `c` sends the consumer to talk to `K'` — which pins perfectly well,
because it really is `K'` — under the belief that it is `c`. That is a
man-in-the-middle on the *name binding*, and the key pinning that backstops
SIP-28 does not catch it, because the substitution happened before the key was
known.

What bounds this is the same concession SIP-33 already makes and states: if a
name is to mean anything, someone must be authoritative for it, and for
`c@example.com` that someone is whoever runs `example.com`'s exchange. A consumer
resolving a name there is trusting that operator for its namespace, exactly as it
already trusts them, via DNSSEC and the first-contact pin, to be the exchange at
all. The exposure is therefore *the operator*, not a network attacker: DNSSEC and
the pin keep a third party from answering in the operator's place.

Two mitigations are worth naming. Out-of-band verification (a SIP-27 vouch, or a
safety-number comparison once connected) detects a substituted binding, because
the account key can be confirmed through a second channel. And the
**account-signed claim** rejected in Rationale would remove the operator's
ability to invent a binding at all — the exchange could then only serve claims
the account actually signed — and is the recommended upgrade for a deployment
that will not trust its operator this far.

**A dishonest or compromised exchange is also a denial position**, silently: it
can refuse to resolve a name, or resolve it as absent, and a consumer cannot
distinguish that from a name never claimed. Consumers with strong requirements
should not depend on a single exchange for a binding they cannot independently
verify.

**Query privacy.** The exchange observes every `Resolve` and `Reverse`,
attributed to an authenticated caller, and so learns who is looking up whom —
the communication graph before any communication. This is the same leak SIP-28
carries and is not mitigated here; an unsigned per-domain directory cannot be
replicated or self-hosted away (SIP-35 carries signed artifacts and this produces
none), so an operator should disclose it rather than let it be discovered.

**Squatting and exhaustion.** Open registration invites both: claiming the good
names, and claiming many names to deny them to others. The per-account cap bounds
the second, the lease returns abandoned names to the pool, the per-connection
rate limit stops a sweep or a grind for lapsing names, and administrative
`NameAssign`/`NameRelease` is the override for the cases policy cannot reach.
None of these makes open registration appropriate for a namespace whose names
carry real-world value; that is what closed mode is for, and an operator should
choose it deliberately.

**Reclamation transfers a handle, not an identity.** When a stale name is
reclaimed, anyone who cached the old binding and does not re-resolve will reach
the wrong account — and, because the account key changed under a stable name,
will do so believing nothing changed. This is the standing hazard of any name
that can change hands, email included. The stale flag exists so that a consumer
can notice a binding on notice and re-verify before relying on it, and clients
SHOULD re-resolve rather than cache a name-to-key mapping indefinitely.

## Reference implementation

None yet. A Standards Track SIP cannot reach Active without one; the intended
shape is a `name` route and store in `sqex` (`sqex-proto::name` for the four
messages, a persistent `sqexd::name` table beside the device registry, the three
`Op` tags dispatched beside SIP-24's, and `sqex name` / `sqex admin name` in the
CLI), with `name@domain` resolution taught to the client after SIP-33 discovery.
