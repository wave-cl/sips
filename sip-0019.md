## Abstract

What a channel entry actually contains: a message with text, attachments,
mentions and link previews; a reaction to an earlier message; an edit; a
redaction; or a channel's name and topic. Each is a type byte and a payload, and
**a type a reader does not know is ignored rather than refused**, which is what
allows a new kind of message to be added without a flag day. Authority over
edits and redactions is checked by the receiver, because in a private channel the
exchange sees only ciphertext and cannot check anything.

## Motivation

SIP-16 carries an opaque body and says so. SIP-17 seals it. SIP-18 gives it
somewhere to put a video. None of them says what a message *is*, and two people
running different clients need to agree on that before anything works.

This is the same relationship SIP-15 has to SIP-12: a payload format inside a
carriage that never inspects it. The separation is worth keeping — an exchange
implementing SIP-16 correctly needs to know nothing in this document, and this
document can change without an exchange changing at all.

The one thing that genuinely needs writing down, beyond the layouts, is who is
allowed to modify a message. In a public channel the exchange could enforce that
an edit comes from the author, because it can read both. In a private channel it
cannot, and building the rule at the exchange would mean it only works where it
is least needed. So the rule lives with the receiver, exactly as SIP-13 places
proof verification with the members for the same reason.

## Specification

All integers are unsigned big-endian. A message is the plaintext of a SIP-16
entry body: in a public channel it is stored as it appears here; in a private one
it is sealed under SIP-17 first. The entry's `account`, `device`, `seq` and
`posted` come from SIP-16 and are not repeated here; where this document speaks
of who sent something it means the **account**, since a person may use more than
one client.

### Bodies

```
Body | type: u8 | payload |
```

| `type` | Meaning | Payload |
|---|---|---|
| 0x01 | Post | `part_count: u8 \| part × count` |
| 0x02 | Reaction | `target: u64 \| op: u8 \| len: u8 \| emoji` |
| 0x03 | Edit | `target: u64 \| part_count: u8 \| part × count` |
| 0x04 | Redact | `target: u64` |
| 0x05 | Metadata | `name_len: u8 \| name \| topic_len: u16 \| topic \| has_avatar: u8 \| Attachment?` |

**A body whose `type` a reader does not know MUST be ignored, not refused.** It
is well-formed; it is simply from a later version of this document. That is what
reserves the space for a new kind of message — a poll, a location, a call record
— without a flag day, and it is the only reason such a thing can be added at
all. An implementation SHOULD have a test that pins it: a body with an unknown
type byte decodes to "nothing to show" rather than an error.

A body that is malformed — truncated, a length that overruns, invalid UTF-8
where UTF-8 is required — is an error and MUST be reported as one. The
distinction matters: "I do not know this" and "this is broken" are different
facts, and collapsing them hides real corruption behind a forward-compatibility
rule.

### Parts

A `Post` is a sequence of parts, in the order the sender intends them shown.

```
Part | kind: u8 | len: u32 | body |
```

| `kind` | Meaning | Body | Limit |
|---|---|---|---|
| 0x01 | Text | UTF-8 | 16 KiB, at most one |
| 0x02 | Attachment | a SIP-18 reference | 4 |
| 0x03 | Link preview | see below | 4 |
| 0x04 | Reply | `target: u64` | at most one |
| 0x05 | Mention | `identity[32]` | 32 |

An unknown `kind` MUST be skipped — `len` is there so a reader can step over a
part it does not understand — and the rest of the post displayed. A post with
no parts a reader understood is not an empty post: a client SHOULD say that the
message contained something it could not display, rather than showing a blank or
showing nothing.

`Text` is plain UTF-8. **No markup is defined**, and a client MUST NOT be
assumed to interpret any. If a formatting scheme is wanted later it belongs in a
new part kind, not in a reinterpretation of this one — retroactively deciding
that `Text` is markup changes the meaning of every message ever sent, including
the ones where an asterisk was an asterisk.

```
Link | url_len: u16 | url | title_len: u16 | title
     | desc_len: u16 | desc | has_image: u8 | Attachment? |
```

`url`, `title` and `desc` are UTF-8. `has_image` is 1 when a SIP-18 attachment
reference follows, giving the preview image, and 0 when it does not. A link
preview is composed **by the sender's client**, never by the exchange; see
Security considerations. A reader MUST show the `url` and MUST NOT present
`title` or `desc` in a way that could be mistaken for the destination's own
claim about itself, because the sender chose both.

`Mention` names an identity. It carries no display name — a name is whatever the
reader's client calls that key, and shipping one inside the message would let a
sender put any text they liked where a reader expects an identity.

### Referring to an earlier message

`target` is the SIP-16 sequence number of the entry being replied to, reacted
to, edited or redacted.

A sequence number works here because everything one refers to has already been
accepted, and is therefore already numbered: a reply is to something read, and
an edit or a redaction is to something the sender saw stored. There is no case
in which a client must name a message the exchange has not yet numbered.

A reference to an entry the reader does not hold — pruned, or before the reader
joined — MUST be ignored for `Reaction`, `Edit` and `Redact`, because the
authority check below cannot be performed without it. A `Reply` whose target is
missing SHOULD still be shown, marked as replying to something unavailable.

### Reactions

`op` is `0x01` to add and `0x02` to remove. `emoji` is UTF-8 of at most 32
bytes, which is room for a sequence with modifiers and joiners. A receiver
SHOULD require it to be a single extended grapheme cluster and MAY ignore
anything else; a reaction is not a second channel for text.

A reaction is keyed on `(sender, target, emoji)`. Adding one that exists changes
nothing, removing one that does not exist changes nothing, and both are ordinary
rather than errors.

### Edits, redactions, and who may make them

Neither can be checked by the exchange in a private channel, so both are checked
by every receiver, against the SIP-16 entry `account` of the entry and of its
target. Note that this is the **account** and not the device: a person may edit
from a different client than they posted from, and requiring the same device
would break that for no gain.

- An `Edit` MUST be ignored unless its account is the account of `target`.
- An `Edit` SHOULD be ignored if it was posted more than `EDIT_WINDOW` after
  `target`, comparing the two entries' `posted` values.
- A `Redact` MUST be accepted only from the account of `target`, or from an
  account the channel lists as an admin.
- Where two edits target the same entry, the one with the higher `seq` wins.

These comparisons are between public identities, not secrets, so **constant-time
comparison is not required** — noted explicitly because SIP-13 requires it for
proofs and a reader moving between the two documents should know why the
requirement is absent rather than assume it was forgotten.

An edited message SHOULD be shown as edited. Presenting an edit as though it
were the original hides that the text changed after it was read, which is the
part a reader would want to know.

**`Redact` does not by itself remove anything.** It is the notification that
tells clients to show a message as deleted; the removal is SIP-16's
`POST /channel/redact`, which the exchange can authorise because the sender of
an entry and the channel's admins are facts it holds, and which works in a
private channel where the exchange cannot read this body at all. A client
deleting a message issues both, and detaches any attachment (SIP-18).

### Metadata

A `Metadata` body sets a channel's name and topic. It exists because a private
channel's name is not stored at the exchange (SIP-16), so it travels sealed like
everything else.

`has_avatar` is 1 when a SIP-18 attachment reference follows, giving the group's
picture, and 0 when it does not. A group avatar is a blob reference where a
personal one (SIP-21) is inline bytes, and the difference is not arbitrary: a
group avatar *is* in a channel, so it prunes with the channel like any other
attachment, whereas a profile belongs to no channel and has nothing to prune
against.

A receiver MUST ignore a `Metadata` body from an identity the channel does not
list as an admin, and takes the one with the highest `seq` as current. In a
public channel the name and topic at the exchange are authoritative and a
`Metadata` body MUST be ignored, so the directory and the conversation cannot
disagree.

### Signals

Signals are relayed by SIP-16 and never stored. They use their own type space.

```
Signal | kind: u8 | body |
```

| `kind` | Meaning | Body |
|---|---|---|
| 0x01 | Typing | `state: u8` — 0 stopped, 1 typing |

`0x02` is reserved: it was a read marker in an earlier draft of this document,
and is now SIP-16's durable cursor instead. A receiver MUST ignore it, as it
ignores any unknown kind.

Typing is the only signal, and it is the only one that should be. A read marker
looks like its neighbour and is not: reading is durable state somebody wants
back tomorrow, which makes it a cursor at the exchange (SIP-16), while typing is
worthless a minute later and would be actively wrong to store. The test is
whether anybody would want to ask the question again later.

A typing signal SHOULD be repeated no more often than every few seconds while
typing continues, and a client MUST treat one as expired after `SIGNAL_TTL` even
without a stopped signal, because the sender may simply have closed the lid.

**Signals travel in the clear**, unsealed, even in a private channel. A client
that sends none is fully conformant, and each SHOULD be individually switchable
off. The reasoning is in Security considerations; it is a deliberate
choice and a small one, but it is a choice.

### Limits

Recommended values, alongside SIP-16's 32 KiB entry body, which binds first:

| Limit | Value |
|---|---|
| `Text` | 16 KiB |
| Parts per post | 32 |
| Attachments per post | 4 |
| Link previews per post | 4 |
| Mentions per post | 32 |
| `emoji` | 32 bytes |
| `EDIT_WINDOW` | 24 hours |
| `url` / `title` / `desc` | 2 KiB / 256 / 1 KiB |
| `name` / `topic` | 64 / 256 bytes |

## Rationale

**Why a sequence number and not a message id chosen by the sender.** A
client-chosen identifier is the obvious alternative and is what most systems
use, because it lets a sender name a message before the server has seen it. It
was rejected because nothing here needs that: every reference is to something
already accepted. And it costs more than it looks — an identifier chosen by a
sender must be qualified by that sender, or one member can mint an identifier
that collides with another's message and quietly redirect replies to it. The
sequence number is assigned by one party, is unique by construction, and needs
no qualifier.

**Why an edit has a window at all.** Without one, a message from a year ago can
be rewritten in place, long after everybody who was going to read it has. The
number is a policy rather than a guarantee — the two systems most people are
arriving from picked fifteen minutes and twenty-four hours respectively, and
neither can stop a client that ignores the rule, because the enforcement is a
receiver declining to display something. Twenty-four hours is chosen as the
looser of the two: an edit window that expires while somebody is asleep produces
a typo nobody can fix.

**Edit history is already preserved, and costs nothing.** Because an edit is an
appended entry rather than a mutation, the original and every revision are
separate entries with their own sequence numbers, and a client can show what a
message used to say by reading the log it already has. This falls out of the
next paragraph's decision rather than being designed for, and it is worth
stating so a reader does not add a mechanism that exists.

**Why reactions and edits are entries rather than mutations.** The exchange
would have to be able to find and rewrite the target, which in a private channel
it cannot read. Appending is also what makes the log replayable: a client that
fetches a range and folds it forward arrives at the same state as one that has
been connected throughout.

**Why authority is checked by receivers rather than by the exchange.** Because
the exchange can only do it in a public channel, and a rule that holds where it
is least needed is worse than no rule, since it invites the assumption that it
holds everywhere. SIP-13 placed proof verification with the members on exactly
this reasoning.

**Why an unknown body type is ignored and an unknown part is skipped.** These
are different mechanisms for the same promise at two scales. A body is
all-or-nothing — an unrecognised kind of message has nothing to show. A part is
one element of a message that otherwise displays fine, so `len` lets a reader
step over it and keep the text. SIP-15 proved the body-level version works: it
reserved its type space, and a comfort-noise frame was added to a running system
without a flag day.

**Why no markup.** Every markup scheme is a parser running on hostile input and
a set of edge cases two clients will disagree about, and adopting one
retroactively changes what old messages said. Leaving `Text` plain keeps this
SIP small and leaves the decision to whoever has a reason to make it, at the
cost of bold text for now.

**Why link previews are made by the sender.** See Security considerations —
this is the entry that most looks like an implementation detail and is not.

**Why mentions carry no display name.** A name in the message is a name the
sender controls, and a client that renders it is rendering attacker-chosen text
in the place a reader looks for identity. The key is the name; how it is
displayed is the reader's client's business.

**What is deliberately not here.** Threads, pinned messages, polls, formatted
text, forwarding provenance, disappearing messages, per-message expiry. Each is
a plausible addition and none is needed to hold a conversation. The type space
is where they go, and the ignore rule is what makes adding them cheap. A first
version that shipped all of them would have specified several of them wrongly.

## Compatibility

New format, no existing wire touched. SIP-16 carries this body opaquely and
SIP-17 seals it; neither changes.

Between clients, the ignore rules give one-directional compatibility for
everything added later: an older client shown a newer message kind displays
nothing for it and continues, and an older client shown a newer part kind
displays the parts it knows. Neither errors and neither disconnects. Everything
in **this** version is required of every implementation — the ignore rules cover
what comes after it, not a client that declines to implement `Reaction` today.

No flag day, and none will be needed for an addition. A change to the meaning of
an existing type would need one, and would be a new SIP replacing this one, as
SIP-15 replaced SIP-14 for the same reason.

## Security considerations

**A link preview is composed by the sender, and this is the point.** An exchange
that fetched URLs to build previews would tell every linked host that a message
mentioning it had been posted, and would do so from an address identifying the
exchange rather than any reader — turning a link in a private conversation into
a callback with a timestamp. It would also make a URL in a message an
instruction to the exchange to make a request, which is a server-side request
forgery primitive handed to every member. So the exchange never fetches.

The consequence is that `title`, `desc` and the preview image are attacker-
chosen. A malicious sender can attach any title to any URL. A client MUST show
the actual `url` and MUST NOT let the preview stand in for it.

**Redaction is a request, not erasure.** SIP-16's operation genuinely removes
the body at the exchange, and a paired SIP-18 detach removes the attachment —
that part is real. What is not real is any effect on copies already delivered. A
client that already displayed the message can keep it, a client written to be
dishonest certainly will, and anyone may have photographed the screen. An
interface that presents redaction as deletion is telling its user something
false about a message that has already left.

**An edit changes what was read.** Anyone who read the original saw different
text from anyone reading now, and only the marking makes that visible. A client
that hides the edit marker, or does not keep the original, removes the reader's
ability to know.

**Typing is unsealed on purpose.** A typing signal says you are at the keyboard
now, in the clear, to the exchange as well as to the channel. Sealing it would
need a nonce space separate from the entries' or risk reusing one, which is a
great deal of machinery guarding very little: the exchange learns the same fact
from the post a second later. The residual disclosure is about presence rather
than content, and it is real — a typing signal that is never followed by a
message says something a person may not have meant to say. It SHOULD be
switchable off, and an implementation that never sends one is conformant.
Read state is no longer here at all; it is a SIP-16 cursor, and its disclosures
are that document's to state.

**Mentions are a notification primitive and therefore an attention primitive.**
Any member can mention any identity, including everyone in the channel, as often
as the rate limits allow. The limit of 32 bounds one message. Nothing here
bounds a member sending many, and a client SHOULD let a person mute a channel or
an identity.

**Everything in a public channel is public, including reactions.** A reaction
carries the reacting identity in the clear, in a channel anybody can join. It is
a small, durable, attributable statement of opinion, and it will be read that
way.

**Emoji are text, and text renders.** A reaction is a short UTF-8 string
displayed in a small space, which is a well-worn path to layout attacks with
combining characters and bidirectional overrides. The 32-byte cap and the
single-grapheme recommendation bound it. A client MUST NOT assume the string is
harmless because it is short.

## Reference implementation

Implemented in [sqex](https://github.com/wave-cl/sqex) v0.9.0:

- `sqex-proto::message` holds `Post`, `Body` and the part types, and decodes by
  ignoring what it does not recognise — which is the rule this SIP rests on, so
  it is tested directly rather than assumed: an unknown body type, an unknown
  part kind, a post of nothing but unknown parts, and unknown parts not counting
  against any cap.
- `sqex-proto::timeline` is the client-side reader: it folds posts, edits,
  reactions and redactions into what a person sees, and reports an entry it
  could not open as unreadable rather than as absent.

The exchange has no module for this SIP and no route, and that is the point: an
implementer looking for the server side of this document will not find one, and
if they do find one, something has gone wrong.

**It does not follow that the exchange cannot read a message, and an earlier
version of this paragraph said so and was wrong.** In a private channel every
structure here travels inside a SIP-17 sealed body and a message is an opaque
run of bytes. In a **public** channel epoch 0 means the body is not sealed —
SIP-16 says so plainly — so the exchange holds a SIP-19 message in the clear and
could parse it with this document in hand. It has no reason to and no code that
does, but the reason is that anybody may join a public channel and would
therefore hold any key it used. Encrypting anyway would produce something that
looked end-to-end and was not, which is a worse failure than storing plaintext
and saying so.

`Timeline` reads the entry `kind` before it tries to open anything. That is not
a detail: a system entry is unsealed by construction, and a reader that fed one
to the cipher would report a gap in the conversation where none exists.

Integration tests render a real conversation end to end through a live exchange
— text, a reply, a reaction, an edit and a redaction — and confirm that a forged
edit is ignored by the reader, because the exchange cannot check the author and
the reader can.
