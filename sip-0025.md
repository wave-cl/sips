## Abstract

Two identities behind NAT ask an exchange to introduce them. It tells each the
other's observed address and coordinates a simultaneous connection attempt, so
they can establish a direct sQUIC connection without either being reachable
from outside.

## Motivation

sQUIC is UDP, which makes hole punching viable, and the exchange is already
in the ideal position: every bound identity connects to it, so it observes
everyone's real source address. Nothing else in the stack can pair two peers
who are both unreachable.

## Specification

All integers are unsigned big-endian.

```
Introduce  | type: u8 = 0x01 | peer[32] | wait_secs: u16 |

Introduced | ready: u8 | kind: u8 | addr[16] | port: u16
           | start_at: u64 | now: u64 |
```

Both parties connect and request introduction to the other's Ed25519 identity.
When both requests are outstanding the exchange answers each with the other's
observed address and a start time, and both begin connecting then.

### Consent, which is the whole design

**An introduction is served only when both parties have asked**, independently.
Until then the answer discloses nothing: not the address, and **not that anybody
asked**, which would itself be a signal about somebody who has not consented. A
waiting answer is byte-for-byte the same length as a ready one, so the size of
the reply says nothing either.

A standing "introducible to anyone" mode is **rejected**, and this settles the
question the sketch left open. Such a mode makes the exchange a location service
for every identity that enables it: an address is disclosed to whoever asks, and
the asker needs no relationship of any kind. SIP-4 declines to publish addresses
for exactly this reason and its argument applies unchanged. An identity that
wants to be reachable without an introduction should publish endpoints under
SIP-28, where the disclosure is deliberate, bounded by a TTL, and its own act.

An identity cannot ask to meet itself. That introduces a caller to its own
address for nothing and is the degenerate case a rule keyed on a pair must
exclude on purpose.

### The address is observed, never asserted

The address disclosed is the one the exchange saw the connection come from. A
caller-supplied address would make this route a way to aim a coordinated pair of
simultaneous connections at somebody who never asked for them — which is the
shape a reflection abuse takes, and is what "provided the requests are genuinely
independent" in the security section is protecting.

### Timing

The request is a **long poll**. The first party to ask holds it open for up to
`wait_secs`, and the second party's request wakes it, so both are answered
within a wake-up of each other. Polling would have worked and would have put the
two answers as far apart as the poll interval, which is the one thing a
coordinated start cannot afford.

`start_at` is a moment on **the exchange's clock**, and `now` is that clock, so
each side computes its own offset rather than assuming three clocks agree. This
is SIP-4's rule for staleness applied to a start time, and for the same reason.

**Both sides are told the same moment.** Whichever request completes the pair
computes it; the other reads it back. A second caller told a later start than
the first was already given would defeat the point of coordinating at all.

A request whose partner never arrives is answered, after the wait, with the same
silence it began with. There is no failure to report, because nothing was
disclosed.

### What this traverses, and what it does not

Stated rather than implied, because implying universality here would be the
error the sketch warned against.

- **Endpoint-independent mapping** — a NAT that reuses one external port for a
  given internal socket whatever the destination — is what this needs, and is
  the common case for home routers.
- **Symmetric NAT**, which allocates a fresh external port per destination,
  generally defeats it: the port the exchange observed is not the port the peer
  will see, so the mapping being reused is not the mapping being punched.
  Nothing here works around that and nothing should pretend to.
- **Carrier-grade NAT** behaves as symmetric often enough that it should be
  assumed to.
- Where either side is directly reachable, an introduction is unnecessary:
  SIP-28 publishes the address and the peer dials it.

### Failure and fallback

[SIP-12](sip-0012.md) is the fallback and already exists: the exchange carries
the session instead of introducing the peers. It needs no transport change and
works behind symmetric NAT, at the cost of relaying the traffic.

The two are complementary rather than alternatives, and an implementation should
**punch where it can and relay where it cannot**. This document does not specify
the decision between them; a client that tried both and used whichever completed
would be within it.

## Rationale

**Introduction presupposes prior knowledge.** A sQUIC server refuses anyone
who does not already hold its public key, so an introduced peer must already
know the other's identity. The exchange therefore reveals an address, never a
key, and cannot introduce strangers. That is a limitation of the design and
also its safety property.

## Compatibility

New protocol. Requires SIP-2 for the authenticated caller. Nothing existing
changes shape, and an exchange without the route refuses it as it refuses any
unknown path.

## Security considerations

**Address disclosure is the entire mechanism**, so consent is not a detail. An
identity that can request introduction to anyone can locate anyone bound to the
exchange.

**Amplification.** Coordinated simultaneous connections to an address supplied
by a third party is a shape worth examining for reflection abuse: the exchange
must not be usable to point traffic at an address that did not ask for it.
Requiring both sides to have requested addresses this, provided the requests
are genuinely independent — and the implementation keeps them so by never
letting one request create the other, and by disclosing only the address it
observed rather than any address a caller named.

**The exchange learns who wants to talk to whom**, and unlike SIP-5 it learns
it even when no message is ever sent.

## Reference implementation

**Implemented in `sqex` 0.34.0 on squic v0.26.0 / squic-go v0.71.0, and this SIP
stays Draft anyway.** Everything above is built and tested, two peers who both
ask are told where the other is and when to begin, and they then connect
directly with the exchange out of the path. What is missing is not code — see
below.

`sqex-proto::rendezvous`, `sqexd::rendezvous`, `sqex meet`, and in the transport
two options that did not exist when this was written:

- **`local_bind`** — a dial that leaves from a chosen local port. This was the
  blocker. `dial` otherwise binds `:0`, so every attempt makes a fresh mapping
  the peer has never been told about.
- **`punch`** — a one-byte datagram to each named address right after binding,
  from both `dial` and `listen`, because a NAT delivers nothing inbound until
  something has gone out. The byte is `0x00`: a short header for a connection
  nobody has, dropped in silence by every squic endpoint and never answered. It
  is bounded at four targets and three datagrams, since it is a send primitive
  with a caller-supplied destination and that is the shape a reflection abuse
  takes. It amplifies nothing.

### One port, and what that costs

The address an exchange observes is the mapping a *socket* made, so the
connection that gets introduced and the connection that punches have to leave
from the same port. `sqex meet` drops the exchange connection and rebinds, which
works because a NAT keeps a mapping alive for tens of seconds after the last
packet.

**Holding it open would be better and is not possible.** Two QUIC endpoints
cannot share a socket, so a peer that kept its exchange connection while
accepting a punched one needs a single endpoint that both dials and accepts —
and that endpoint must add an envelope on send and validate-and-strip one on
receive, keyed differently in each direction. Those are two separate wrappers
today with two separate cookie paths. It buys robustness rather than capability,
which is why it is not here.

Simultaneous open is out for the same reason. One side dials and the other
listens, chosen by the lower key — the tiebreak SIP-12 already uses to decide
which peer is `first`, so there is one convention and not two.

### Why this is still Draft

**The property that matters cannot be demonstrated from a desk.** The tests put
two peers through a real exchange and have them connect on the ports it
observed, which proves the coordination produces a usable address and that a
connection leaves from the port that was introduced. On loopback there is no
NAT. Whether any of it survives one is a question for two peers behind two real
NATs of known type, and that is evidence rather than code.

Promoting this needs somebody to run `sqex meet` from two homes. Until then the
honest status is: built, tested as far as this can be tested, unproven where it
counts.

Meanwhile SIP-12 relays, works behind symmetric NAT today, and needs none of
this.
