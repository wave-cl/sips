## Abstract

A service on sQUIC often needs an administrator to authorise an action by a key
the transport cannot vouch for — a YubiKey signs Ed25519 but never releases the
seed sQUIC needs for its X25519 handshake, so admin authority cannot ride on the
connection's `peer_key`. This SIP defines `sqnr-tx-v1`: a generic, signed
**transaction** — an ordered batch of *opaque* operations, each carrying the
bytes a server will act on plus a one-line human summary — signed as a single
Ed25519 signature over a domain-separated hash. The signer never parses a
payload, so a new server command never changes the signing format or the signing
tool. The signature is self-contained (it binds the server's key and a
single-use nonce), so authority is independent of the connection it arrives on.

## Motivation

Services built on sQUIC (sqex, and any that follow) need to let an operator
authorise administrative changes. SIP-2 and SIP-3 give a service the caller's
transport identity, but that is the wrong instrument here for two reasons.
First, the strongest operator credential is a hardware key: a YubiKey's OpenPGP
Authentication key produces raw Ed25519 signatures but never exports the seed,
and sQUIC's transport identity is the *same* seed in X25519 form — so a YubiKey
administrator has no stable transport key to be recognised by. Second, authority
that lives in the connection cannot be carried: it cannot be prepared offline,
relayed, or logged as a standalone artefact.

The obvious alternative is to bake the command set into the signer: a signed
`enum Action` shared by client and server. That was the first implementation. It
couples the signer to every service command — each new operation edits the
signer, retags it, and repoints every consumer — and it gives the operator no
built-in way to see what they are about to authorise. This SIP moves the command
set out of the signer entirely: the signer signs opaque bytes with human
context, and the *service* owns what those bytes mean.

The signer belongs in its own component (`sqnr`) rather than in sQUIC or in each
service: sQUIC is the transport and has no business with application authority,
and duplicating the envelope per service is exactly the "format that exists only
as code" this repo exists to prevent.

## Specification

All integers are unsigned big-endian. Byte offsets are exact; there is no
variable framing beyond the length prefixes named here.

### Types

A **transaction** is:

```
Transaction {
  server  : 32     // the target server's Ed25519 public key
  nonce   : 32     // a single-use challenge the server issued
  ops     : Operation[]
}

Operation {
  summary : string   // one-line human description, shown before signing
  detail  : string[] // optional extra context lines
  payload : bytes    // opaque to the signer; the server defines its meaning
}
```

`string` and `bytes` are each encoded as a 4-byte length followed by that many
bytes; `string` is UTF-8. The signer MUST NOT interpret `payload`.

### Canonical encoding

`encode(Transaction)` is the concatenation, in order:

```
server (32)
nonce  (32)
op_count (4)
  for each op, in order:
    summary_len (4) | summary bytes
    detail_count (4)
      for each line: line_len (4) | line bytes
    payload_len (4) | payload bytes
```

The encoding is canonical: there is exactly one byte string for a given
transaction, and it is both the wire form and the input to the hash below.

### What is signed

```
signing_input = TX_CONTEXT || SHA-256( encode(Transaction) )
TX_CONTEXT    = "sqnr-tx-v1"   (ASCII, 10 bytes, no terminator)
```

The signature is a raw RFC 8032 Ed25519 signature over `signing_input` (42
bytes). Signing a hash, not the encoding, keeps the signed message fixed-size
regardless of batch size — a hardware signer sees 42 bytes whether the batch has
one operation or sixty-four — and the domain tag makes an `sqnr-tx-v1` signature
unusable as a signature in any other context.

### Wire form

The signed transaction, e.g. an HTTP request body, is:

```
encode(Transaction)   // self-delimiting, per the counts above
admin     (32)        // the signer's Ed25519 public key
signature (64)
```

### Decoding bounds

A decoder MUST reject a transaction exceeding any of: `op_count` > 64, any
`detail_count` > 32, any `string` or `payload` length > 4096 for strings and
> 65536 for payloads, or trailing bytes after the signature. These bound the
work a network peer can impose; a service MAY set lower limits.

### Verification

A verifier, given the transaction bytes and its own Ed25519 key `server_key`,
MUST perform these checks and MUST stop at the first failure:

1. **Nonce.** `nonce` is one the server issued, has not consumed, and has not
   expired. Consume it now (single use). The nonce is obtained out of band
   before signing (e.g. `GET /admin/challenge` returning 32 random bytes with a
   short TTL); its issuance is a service detail, its single-use consumption is
   normative.
2. **Server binding.** `transaction.server == server_key`. This stops a
   transaction captured against one server from being replayed at another.
3. **Signature.** Ed25519-verify `signature` over `TX_CONTEXT || SHA-256(
   encode(transaction))` under `admin`.
4. **Authority.** `admin` is on the server's configured authority list
   (e.g. its admin keys). Membership and its meaning are a service policy;
   *that* it is checked is normative.
5. **Context binding.** For each operation, decode `payload` into the service's
   own operation type and re-render that operation's canonical summary; reject
   the transaction unless the rendered summary equals the signed `summary`. This
   makes the human text the operator approved provably correspond to what will
   execute.

### Application

On success the verifier applies the operations **atomically and in order**:
either all take effect or none do. A verifier MUST decode and check every
operation (steps 3–5 above cover the batch) before applying any, so that one
undecodable or mislabelled operation aborts the whole transaction with no
partial effect. Ordering within the batch is preserved.

The signer, before signing, SHOULD present `summary` and `detail` for every
operation to the operator, and — for a hardware backend — require the physical
confirmation (a touch) after presentation.

## Rationale

**Why opaque payloads.** The entire point is that the signer holds no command
vocabulary. If the signer knew the operations, every new one would change the
signer and its wire format; instead the format is frozen and services add
commands freely. This is the inversion of the rejected `enum Action` design,
where the shared signed type *was* the command set.

**Why hash-then-sign.** Ed25519 signs arbitrary-length messages, so signing the
encoding directly would work — but a hardware signer receives the message over
an APDU with practical size limits, and a batch has no fixed bound. Hashing
first makes the signed message a constant 42 bytes. The cost is assuming SHA-256
collision resistance, which is not in doubt at this security level.

**Why one signature for the whole batch.** The batch is the unit of operator
intent ("enable the whitelist and add these three peers"). One signature means
one hardware touch and one atomic outcome. Per-operation signatures were
rejected: they multiply touches and admit partial application, where a batch
half-succeeds and leaves the service in a state the operator never described.

**Why the summary is signed and the server re-checks it.** The operator must
know what they authorise, and that knowledge must be bound to the signature, so
`summary` is inside the hashed bytes. But binding alone only proves the operator
signed *some* text; it does not prove the text matches the payload. The service
re-renders the summary from the decoded payload and requires equality (step 5),
which closes the gap: display equals execution as long as client and server
share the same renderer, which they do by both depending on the service's
vocabulary crate.

**Why client-built and not server-proposed.** An alternative is the
hardware-wallet model: the client asks the server to prepare a transaction, the
server returns payload plus a rendered summary, and the signer signs what it is
shown. It keeps the signer generic too, but it makes the human context authored
by the very server the operator is administering, and it needs server-side
pending-transaction state. Client-built keeps authorship in the operator's own
tool and binds the server to execute exactly the signed payload; the server's
re-render (step 5) recovers the integrity check the server-proposed model would
have provided, without moving authorship.

**Why the server key and a nonce, not the transport.** Authority must be
carriable — preparable by a YubiKey that cannot make a transport key, and
verifiable regardless of which connection delivers it. Binding `server` defeats
cross-server replay; consuming a single-use `nonce` defeats same-server replay.
Neither depends on the connection, so the transport is free to be anonymous.

## Compatibility

`sqnr-tx-v1` replaces an earlier service-specific command envelope
(`sqex-admin-v1`, a signed `{action, nonce, server}`) that was removed before
any deployment, so there is no interop obligation to a previous format. The
version lives in the domain tag: a future incompatible change is a new tag
(`sqnr-tx-v2`) and a coordinated cutover for the services that use it, with no
silent ambiguity because the tag is part of every signed message.

The envelope is service-agnostic. Multiple services can share it; each supplies
its own payload vocabulary and its own authority policy. A signer implementation
and a verifier implementation interoperate on this section alone plus an agreed
payload meaning — the latter being the service's concern, not this SIP's.

## Security considerations

**Authority is a signature, not a connection.** A valid transaction proves the
holder of `admin`'s private key authorised exactly these operations for exactly
this server, and nothing about the connection is trusted. This is what lets a
hardware key be the credential; it also means the transport MUST NOT be relied
on for admin authority, only (optionally) for confidentiality.

**Replay is bound two ways.** The single-use nonce prevents re-submitting a
captured transaction to the same server; the `server` field prevents moving it
to another. A verifier that fails to consume the nonce exactly once, or fails to
compare `server`, reopens replay.

**Domain separation is load-bearing.** `TX_CONTEXT` ensures an `sqnr-tx-v1`
signature cannot be lifted into another Ed25519 context (or vice versa). A
verifier MUST include it in the signed input; omitting it would let a signature
minted for some other purpose under the same key be presented here.

**The operator sees what executes — under one assumption.** Step 5 guarantees
the signed summary matches the server's rendering of the payload. The residual
trust is in the operator's own signing tool to encode the payload it describes;
a compromised signer could encode payload X while displaying summary X' only if
the server's renderer also produced X' for X, which by construction it does not.
The guarantee therefore holds as long as client and server derive the summary
from the payload the same way.

**Confidentiality is not provided here.** `summary`, `detail`, and `payload` are
plaintext within the request; on sQUIC they are inside the encrypted connection,
but the receiving server sees them in full, and this SIP adds no secrecy of its
own. Payloads that name sensitive values expose them to the server (which is
acting on them anyway) and to anything with the decrypted request.

**Atomicity prevents partial-apply.** Because all operations are checked before
any are applied, a batch containing one malformed or mislabelled operation
leaves the service unchanged, rather than in a state that is a prefix of the
operator's intent.

**This does not constrain an authorised admin.** It authenticates *who* and
*what*, not whether the what is wise. Limiting what a given admin may do is a
service authority-policy concern (step 4), outside this envelope.

## Reference implementation

Shipped:

- **Signer** — `sqnr` v0.2.0 (github.com/wave-cl/sqnr): the envelope and
  hash-then-sign in `sqnr-core/src/tx.rs` (`Operation`, `Transaction`,
  `SignedTransaction`, `TX_CONTEXT`), the software (encrypted or plaintext) and
  YubiKey backends, and `sqnr::flow::sign_and_submit` (challenge → review →
  sign → submit).
- **Verifier and a payload vocabulary** — `sqex` (github.com/wave-cl/sqex):
  `sqex-proto` supplies the `Op` vocabulary (opaque payload + rendered summary),
  and `sqexd` performs the five verification steps and the atomic apply,
  including the step-5 summary re-render. `sqex-cli` builds and signs
  transactions; the desktop GUI signs one-operation batches through the same
  flow.

Both are CI-green. Unit tests cover the encoding round-trip and rejection of a
tampered payload, a tampered summary, a wrong signer, a wrong server, and
trailing bytes; integration tests cover batch atomicity, summary-mismatch
rejection, replay rejection, and non-admin rejection over real HTTP/3.
