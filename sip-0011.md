## Abstract

An administrator whose key lives on a hardware token can sign but cannot serve
as a sQUIC transport identity: the token holds an Ed25519 key and never releases
the seed, and the transport needs that seed to perform its X25519 handshake. So
a hardware-backed identity can never appear on a service's transport whitelist
(SIP-2). This SIP documents the pattern that resolves it: the identity
**delegates** a separate, software-held key to act as its transport identity, by
signing a normal SIP-10 grant that authorises that key, and the service records
who delegated it. No new wire mechanism is introduced — the pattern composes
SIP-10 (the signed grant) with a small provenance record — and this document
exists to state the construction, its scope, and the alternatives that were
rejected.

## Motivation

Authority in this ecosystem splits cleanly: SIP-10 lets an administrator
*authorise actions* by signature, with no transport identity at all (a YubiKey
connects anonymously and signs). But *using* a service's protected endpoints is
gated the other way — on the transport key SIP-2 verified. A holder who wants
both roles hits a wall: the same hardware key that is perfect for signing cannot
be the transport key, because the token performs Ed25519 signatures but will not
give up the scalar the X25519 Diffie–Hellman needs, and the two keys are the
same scalar in different coordinates.

Later hardware does expose X25519 (OpenPGP encryption subkeys, and PIV on newer
firmware), but that does not close the gap: such a key is an *independently
generated* scalar, not the identity's, so its X25519 public would not match a
whitelist entry derived from the identity's Ed25519 key; the transport would
have to call the token for a Diffie–Hellman on every connection; and the stack
takes a raw private key, with no hook to defer that operation to a card. The
cheapest correct answer is not to put the hardware key on the wire at all, but
to let it *delegate*.

## Specification

This is a composition of existing mechanisms; the terms below name the roles.

- **Identity key** — an Ed25519 key (typically on a hardware token) that signs
  but is not used as a transport key. It is an administrator of the target
  service (its public key is in the service's admin list).
- **Delegate key** — a separate Ed25519 key held in software, whose forward-mapped
  X25519 (`ed25519_public_to_x25519`) its holder uses as the sQUIC client
  identity. This is an ordinary transport identity; nothing about it is special
  except that an identity vouched for it.

**The grant.** The identity authorises the delegate by signing a SIP-10
transaction that adds the delegate key to the service's managed set, optionally
carrying a human label. Because the transaction is a SIP-10 grant, it inherits
that SIP's guarantees end to end: single-use nonce, server binding, signature
over the batch, admin-list check, and atomic apply. The identity signs it while
connected anonymously (an ephemeral transport key); the delegate key is named
only as *data* inside the grant, never used to connect for the grant itself.

**Enforcement.** The service already gates its protected endpoints on the
transport key SIP-2 verified. The delegate later connects with its own key as
the sQUIC client identity, so the `peer_key` the service sees is the
forward-mapped X25519 of the delegate's Ed25519 — which the managed set contains
— and the connection is admitted. The identity key is never presented on that
connection.

**Provenance.** For each delegated key the service records, as state, at least:
the delegating identity (`added_by`), the optional `label`, and the time
(`added_at`). Provenance is informational — it does not affect gating — but it
makes the delegation *queryable*: a service or operator can list which keys a
given identity delegated.

**Revocation.** A delegation is undone by a signed grant that removes the
delegate key from the managed set. Because provenance records the delegating
identity, every key an identity delegated can be enumerated and removed together
— for instance when that identity is itself deauthorised. Revocation is service
state, not a credential expiry: this pattern carries no automatic time bound
(see Rationale for why, and Future work for what would add one).

**Scope.** As specified here the delegator is an *administrator* and the
delegate becomes a *whitelisted peer* of one service. The construction
generalises to any service that (a) accepts SIP-10 grants against an authority
list and (b) gates access on the SIP-2 transport key; the concrete realisation
today is sqex's connection whitelist.

## Rationale

**Why delegate rather than make the hardware key the transport key.** It cannot
be, for the reasons in Motivation: the token will not release the scalar the DH
needs, and a card-held X25519 key (where hardware supports one) is a different
scalar, unmatched to the identity and too slow to use per connection. Delegation
keeps the hardware key doing the one thing it is ideal for — signing — and puts
a cheap, disposable software key on the wire.

**Why a SIP-10 grant and not a new credential format.** The authority to add a
key to a service's set already exists as a SIP-10 operation. Reusing it means
the delegation is signed, replay-bound, and audited by machinery that is already
specified and implemented; a bespoke "delegation certificate" would re-solve all
of that. The delegation record *is* the whitelist entry plus its provenance.

**Why provenance instead of a standalone certificate.** The question a delegation
must answer operationally is "whose key is this, so I can revoke it when they
leave?" A server-side provenance field answers that with no new wire artifact
and no verifier to distribute. A portable, self-contained credential answers a
*different* question — verifiable by a party that never saw the grant — which no
current consumer needs.

**Why no expiry.** A time-bound credential implies a verifier that re-checks the
bound and a story for clock skew and renewal. The current need is "on until
revoked," which server state expresses directly. Adding expiry is deferred to the
portable-credential work below, where it belongs.

**Rejected alternatives.** Carrying the identity on the transport (SIP-3 style)
so the admin connects *as* the hardware key — rejected because the hardware key
still cannot do the transport DH; SIP-3 carries an identity for a key that *can*.
Giving every admin a fixed software transport key equal to their identity —
that is just a delegate without the provenance link, i.e. a worse version of this.
A portable signed delegation credential — deferred (Future work).

## Compatibility

This SIP is informational and additive. It introduces no wire format of its own;
it relies on SIP-10 (already Active and implemented) and on the provenance fields
a service records for its managed set. The only concrete wire element the pattern
needs beyond base SIP-10 is an optional label on the add operation, which is part
of the service's own opaque payload vocabulary, not of the signer. Nothing here
changes how existing peers interoperate.

## Security considerations

**A delegate key is lower-value than the identity, and contained.** Compromising
a delegate key lets an attacker *connect as a whitelisted peer* — it does not let
them sign grants, so they gain no administrative authority unless the delegate is
independently an admin. The exposure is bounded by what protected endpoints allow
a peer, and is revocable in one signed removal.

**The grant is only as strong as SIP-10.** All of the delegation's
authentication — that this identity, and only this identity, authorised this
delegate for this server, once — is SIP-10's. A verifier that weakens any SIP-10
check (nonce reuse, server binding, admin membership) weakens delegation with it.

**Provenance is not authorization.** `added_by` and `label` are recorded for
lifecycle and audit; they never gate. A wrong or forged label cannot admit a key
that gating would refuse, and cannot refuse one it would admit.

**A compromised identity can delegate attacker keys.** Delegation is an admin
power, so a stolen identity key has the same blast radius as any admin
compromise: it can whitelist keys the attacker holds. The audit log and the
provenance record are what make such additions visible and bulk-revocable after
the fact; they do not prevent them. Protect the identity key accordingly
(hardware is the point).

**The delegate key is a transport secret at rest.** Where it must persist (a
long-lived whitelisted device), it should be protected as any transport key is —
`0600`, correct owner, platform secret storage for an unattended holder — and
kept ephemeral wherever a persistent identity is not actually needed.

**No automatic expiry.** A delegate stays valid until removed. An operator who
needs time-bounded access must revoke explicitly; this pattern does not lapse on
its own.

## Reference implementation

Shipped in [sqex](https://github.com/wave-cl/sqex):

- An administrator (software key or YubiKey) delegates a device key with
  `sqex admin whitelist add <delegate-key> --label <name>`, which is a SIP-10
  grant signed by the identity.
- `sqexd` records `added_by` (the signing admin), `label`, and `added_at` on the
  whitelist entry (`crates/sqexd/src/state.rs`), and returns them from
  `whitelist list`; the label rides in the `sqex-proto` add payload.
- The delegate then connects with its own key as the sQUIC client identity and is
  admitted on protected endpoints by the SIP-2 `peer_key` check.
- Revoke with `sqex admin whitelist remove <delegate-key>`; provenance makes the
  keys a given identity delegated enumerable for bulk revocation.

## Future work

A **portable delegation credential** — a signed, self-contained
`{ identity, delegate, scope, not_after }` artifact that a service verifies
without having seen the grant, with expiry and explicit scope — would serve the
case this pattern does not: delegation checked by a party that holds no
server-side record. It is deliberately not specified here; it should be its own
Standards Track SIP, taken up when a second consumer needs it.
